# record_actions_code_api — 측정 방법서

`record_actions_code_api.py`의 기능·휴먼화 원리·요율을 한곳에 정리한 문서.
코드 독스트링·`rates.json` 주석·CHANGELOG에 분산된 내용의 통합본이며,
수치·규칙의 원 출처는 각 § 표기를 따라 `../CHANGELOG.md`에서 찾는다.

## 1. 기능 개요

Claude Code 세션 기록(`.jsonl`) 1개를 받아 **LLM 호출 0회, 완전 결정론**
(같은 입력 = 같은 결과)으로 다음을 계산한다:

```
speedup = human_min(분자) ÷ agent_min(분모)

분자 human_min = "일을 아는 사람이 직행했다면" 걸렸을 분 (휴먼화 ON 기준)
분모 agent_min = AI 경로의 추정 비용 = 기계(machine) + 추정 사람 감독(hitl)
                 (§49 용어: 동작 카운트는 실측이나 요율 다수가 seed라
                  "실제 비용"이 아니라 추정 비용 — instruct만 실측 보정)
```

- 분자·분모 모두 세션 기록의 **단서(무엇이 만들어졌고 읽혔나) × 요율표**로
  계산한다. wall-clock(세션에 흐른 시간)은 쓰지 않는다 — 사람 노동은
  세션 밖에서 몰아 할 수 있어 시간 측정으로 못 잡는다(측정 기조).
- 병렬 서브에이전트 기록(isSidechain)은 분자·분모 모두 제외.
- 초소형 세션(검토·입력 100단어 미만 그리고 산출물 50단어 미만)은
  측정 제외(`excluded`) — 완료조건 고정비로 5~7배 역부풀림 실측(§9).

```python
from record_actions_code_api import measure, measure_batch
r = measure("session.jsonl")                      # rw ON · act ON (기본)
r = measure("session.jsonl", humanize_rw=False)   # rw OFF · act ON
r = measure("session.jsonl", humanize_act=False)  # rw ON · act OFF
r = measure("session.jsonl", humanize_rw=False, humanize_act=False)  # 로레코드
r = measure("session.jsonl", include_think=False)  # 전략 생각(§3) 미계상
```

전략 생각(think, §3)은 **기본 ON**이며 휴먼화 2축과 독립 — 위 4조합
모두에 동일하게 가산된다(끄려면 `include_think=False` / CLI `--nothink`).

조합 순서 규약(모든 표·리포트 공통): **rw ON·act ON → rw OFF·act ON →
rw ON·act OFF → rw OFF·act OFF(로레코드)**. 휴먼화를 끌수록 "AI 궤적을
사람이 그대로 따라 한 셈"에 가까워지며, 항목별로 ON ≤ OFF 단조성이
구조적으로 보장된다(§43·§46 클램프).

## 2. 휴먼화 3축 — 어떻게 깎는가

공통 원리: **"결말에 기여한 것만 사람의 노동이다."** AI의 전수 탐색·
시행착오·번복을 걷어내고, 직행하는 사람의 최소 경로로 환산한다.
판정은 전부 코드 실측(결정론) — 아래 신호들이 근거다.

### 2.1 읽기 — 3등급 분해 (humanize_rw, §13~15·25~27)

AI가 읽은 파일(조회형 도구·셸 sed/cat류 읽기 포함, §27·§47)을 등급 분류:

| 등급 | 판정 | 요율 |
|---|---|---|
| 기여(DEEP) | 5신호 중 1개+: ① 이후 편집 ② 마무리 답변에 이름 언급 ③ 같은 구간 2회+ 재방문 ④ 탐색 착지(턴의 마지막 검색 직후 첫 읽기) ⑤ 내용 겹침(6단어 연속 조각·변별 식별자가 답변에 등장) | 핵심 블록만 정독, 나머지 훑기 |
| 훑은 후보(SKIM) | 비기여 파일이 항해 중(그 턴의 마지막 기여 읽기 이전)에 읽힘 | 정독의 1/20 |
| 헛읽기(WASTE) | 비기여 파일이 기여 확보 이후에만 읽힘 | **0** — 사람은 열지도 않음 |

기여 파일도 전량 정독이 아니다 — 200단어 블록으로 갈라 증거(변별 식별자
2개+, 또는 답변·편집 원문과 6단어 겹침)가 닿은 블록만 정독, 나머지는
훑기(§26 구간·블록 분해). 같은 구간 재읽기는 단어수 1회만 집계.

### 2.2 쓰기 — 순계 재생 (humanize_rw, §31)

"결말에 살아남은 단어만 노동" — 쓰기 순서열을 재생해 순계를 구한다:

- 세션이 만든 파일(Write 기점): 편집을 실제 재생해 최종본 복원 —
  만들었다 갈아엎은 왕복은 자동 0. 순계 전체 = 신규 작성(draft).
- 기존 파일(Edit 기점): 이후 편집의 원문이 앞서 써넣은 문구를 덮으면
  왕복으로 폐기. 부분 겹침은 놓치는 보수적(덜 깎는) 근사. 순계 = 수정(edit).
- 실패한 편집(툴 에러)은 제외. 산출물이 없는 보고형 세션은 마무리
  답변(또는 StructuredOutput 보고, §33)이 draft.

### 2.3 행동 — 건수 순계 (humanize_act, §46~48)

읽기·쓰기의 원리를 건수형 행동에 적용:

- **검색 = 착지-기여 문서당 1건** — 검색 끝에 기여(DEEP) 파일에 도달한
  횟수만 센다. 쿼리 다듬기(항해 검색)는 그 1건의 요율에 흡수, 착지 없는
  검색은 자동 0. 셸 속 grep·find류도 검색으로 재분류(§47).
- **실행 = 정규화 명령 신원당 1건** — 같은 명령 반복(편집→재실행 왕복)은
  신원 1개로 접힘. 실패 호출(툴 에러)은 순계에서 상쇄(§48). 셸 속
  sed·cat류는 조회형 읽기로 재분류, 리다이렉트(>)·히어독(<<)·sed -i는
  실행 잔류(§47).
- 클램프: 항목별 하한 1(흔적 있으면 최소 1건) · 상한 기록 호출 수.
- 마무리 verify 1건(산출물 있을 때)은 켬/끔 공통(§43 — 역전 방지).

끄면(act OFF = 로레코드): 행동 횟수를 기록 그대로(검색 호출 수·실행
호출 수) — "AI가 한 행동을 사람이 똑같이 했다면".

## 3. 전략 생각(think) — 분자의 판단 노동 (§53, 기본 ON)

휴먼화 2축이 AI의 장황함을 **깎는** 장치라면, think는 분자에 빠져 있던
판단 노동을 **보충하는** 장치다. 도입 전의 분자는 "정답을 아는 사람이
정답으로 직행"만 계상해 판단 노동이 깊은 세션에서 과소였다(§6 한계 4번).

### 3.1 근거 원리 — 왜 생각 전량이 아니라 선별인가

1. **작업자는 실무 도구 사용에 생각을 쓰지 않는다.** 분자의 사람은 "일을
   아는 사람"(숙련 가정) — 도구를 어떻게 쓸지, 다음 호출로 무엇을 볼지
   같은 조작 판단은 숙련자에게 자동화된 동작이라 계상하지 않는다. AI의
   생각은 도구 호출 사이사이마다 발생하므로 이 몫을 걸러야 한다.
2. **사람 고민은 문제를 어떻게 풀지 전략 짤 때 든다.** 과제를 받았을 때
   접근을 설계하는 순간이 사람 판단 노동의 실체다. 따라서 계상 대상은
   **지시 직후의 생각**이다.

이 원리로 "생각량이 사람 고민 시간에 비례하는가"라는 비례성 문제도
좁혀진다: 전량 비례 가정은 근거가 없지만(실측 반증 — 아래 §3.3 기각 대안), 전략
생각으로 선별하면 세션 내부 실측이 비례의 근거를 제공한다.

### 3.2 선별 방법 (결정론, LLM 0회)

```
지시      = user 메시지 − 도구 결과 회신(tool_result) − meta − 사이드체인
전략 지점 = 지시 직후 첫 assistant 메시지에 생각 흔적이 있는 경우
생각량    = usage.output_tokens_details.thinking_tokens
            (2026-08-12 Claude Code 업데이트부터 기록 — 생각 내용은
             여전히 빈 문자열이므로 §52의 "내용 측정 불가"는 그대로)
think(min) = Σ 전략 지점 생각 토큰 × 0.75(토큰→단어) × 0.0025분/단어
```

- 요율 0.0025분/단어 = **사람 생각 속도를 정독의 3배(400wpm 상당)로
  가정한 seed**. 건당 환산 약 2.7분으로, 독립 대안이었던 건수형(전략
  지점당 2분)과 수렴 — 서로 다른 두 셈법이 같은 자리에 떨어진다.
- **구 포맷은 미계상 (§55)**: 2026-08-12 이전 기록은 생각 블록의 존재만
  남고 토큰 수가 없다. 전략 지점 감지는 되지만 **양을 모르므로 계상하지
  않는다**(지점 수는 `fallback_points`로 보고만 한다). 이전에는 지점 수 ×
  실측 평균 1,454토큰으로 대체했으나 폐기 — 그 방식은 생각의 양이 아니라
  지시 건수를 재는 것이 되고(계상 토큰 대 전략 지점 수 상관 0.99),
  토큰이 실제로 기록된 세션에 같은 단가를 적용해보면 소형 세션이 실측의
  7~27배(중앙 7.2배)로 부풀려졌다. 모르는 값은 0으로 두고 과소를 택한다
  — 즉 **think 보정은 신 포맷 기록을 가진 세션에서만 발생**하며, 구
  기록만 있는 세션의 분자는 생각 미계상 값과 같다.
- 같은 메시지의 스트리밍 중복 기록은 메시지 id로 1회만 집계.

### 3.3 실측 효과 (2026-08-21, §53)

선별이 실제로 도구 잔생각을 걸러낸다: 신 포맷 51세션에서 전체 생각 토큰
890,127 중 **68%(609,412)가 지시 직후에 몰리고**, 도구 호출 동반
메시지의 생각(전체의 56%)은 위치 선별만으로 자연 배제된다.

- **기각된 대안 — 전량 × 정독 요율**: 분자 +103%, 생각 몫이 새 분자의
  중앙값 70%로 측정을 지배. 소형 세션은 사람 시간 9.8분에 생각 78.6분이
  붙어 8배 폭등. 생각량이 과제가 아니라 설정(reasoning effort)의
  속성이기도 해서 기각.
- **채택안 효과**: 신 포맷 51세션 전체 효율 1.89 → 2.31 (분자 +22%).
- **구 포맷 미계상의 효과 (§55, 이 PC 57세션 재측정)**: 대체 계상을
  끄면 think 몫이 분자의 12.0% → 1.8%, 전체 효율 2.68 → 2.40 (생각
  미계상 기준선 2.36). 값이 바뀐 세션은 47/57이고 효율 하락 중앙값
  0.33. 신 포맷 기록만 있는 세션은 값 불변. 생각량이 실제로 기록된
  세션에서는 생각이 적은 쪽 효율 +2.4%, 많은 쪽 +12.9%로 보정이
  생각량을 따라간다 — 대체 계상 시절에는 이 차이가 뭉개져 분위별
  +8~18%로 순서가 어긋나 있었다.
- **비례성의 내부 근거**: 도구를 쓰며 일하는 세션은 전략 지점당
  1,053~1,440토큰으로 세션이 달라도 안정적("전략 1회의 기본 단가"),
  도구 없이 판단만 하고 답하는 세션은 지점당 9천~13천 토큰(10배).
  즉 전략 생각의 양이 판단 깊이를 따라간다 — **고민이 깊은 세션일수록
  보정이 커진다**(판단 중심 세션 +180~250%, 일 세션 +11~29%).
  직행 가정의 과소가 가장 심하던 곳이 정확히 그 판단 중심 세션이다.

### 3.4 켬/끔과 한계

- `include_think=True` 기본 — 기존 소비자가 파일만 갈아끼우면 생각
  계상이 켜진 채 동작한다. 끄기: `include_think=False` / CLI `--nothink`.
- 휴먼화 2축과 독립: 4조합 모두에 동일 가산 → 항목별 ON ≤ OFF
  단조성(§43) 불변.
- 한계는 §6 (9번 항목): 요율 seed, reasoning effort 의존, 중간 재전략
  미계상.

## 4. 요율표 (rates.json)

절대값 주의: **P50 seed가 다수** — 실측 보정된 것은 표기함. 절대값보다
세션 간 상대 비교 용도(agent-effort/README.md 한계 절).

### 4.1 분자 — 사람 요율 (human 카드 중 이 API가 쓰는 것)

| 행동 | 단위 | 분/단위 | 출처 |
|---|---|---|---|
| read (정독) | 단어 | 0.005 | seed (§23~24에서 1/5 보정 이력) |
| skim (훑기) | 단어 | 0.00025 (정독의 1/20) | seed (human_reading_model, §26) |
| draft (신규 작성) | 단어 | 0.05 | seed |
| edit (수정) | 단어 | 0.02 | seed |
| search (검색) | 건 | 2.0 | seed |
| execute (실행) | 건 | 2.0 | seed |
| verify (확인) | 건 | 3.0 | seed |
| think (전략 생각) | 단어 (생각 토큰×0.75) | 0.0025 (정독의 3배, 400wpm 상당) | seed (§53, §3) |

분자 = Σ(등급별 읽은 단어 + 입력 단어)×읽기 요율 + 순계 draft/edit×쓰기
요율 + 순계 행동 건수×건당 요율 + 전략 생각 단어×think 요율(§3).

### 4.2 분모 — AI 기계 요율 (agent 카드)

| 행동 | 단위 | 분/단위 |
|---|---|---|
| execute | 도구 호출 | 0.3 |
| read | 결과 단어 | 0.0005 |
| draft | 출력 단어 (§52: 답변 + **파일 본문·서브에이전트 지시문** 포함 — 셸 명령 텍스트는 execute에 포함으로 보고 제외) | 0.002 |

### 4.3 분모 — 사람 감독(hitl) 요율

| 항목 | 계산 | 출처 |
|---|---|---|
| instruct (지시) | 건당 0.5분 + 단어당 0.05분 (60단어 상한 — 붙여넣기 과금 방지) | **실측 보정** (지시 1,456건, 2026-08-16) |
| review (검토) | **턴 확인 모델 (§50)** — 사람은 AI 출력을 전량 정독하지 않는다. 확인 시점 = 실질 지시 턴(5단어 이상, §49 문턱과 동일) + 세션 끝. 시점마다: 대화는 결론(직전 답변)만 단어당 0.008(정독, **건별 300단어 상한 §51 — 초과분은 훑기로**), 나머지 진행 보고는 단어당 0.002(훑기) / 산출물은 그 구간에 코드 변경 있으면 **동작 확인 1회 2.0** + 변경된 코드·문서 내용물 단어당 0.002(훑기) + 문서·기타 파일당 0.5(표본 확인). 구 문서 전량 정독(0.008/단어)·파일당/에피소드당 코드 과금 폐지 | seed |
| 검증 위임 강등 | 확인 시점의 테스트 상태가 통과면 그 시점의 동작 확인 2.0 → "결과 서명" 0.3으로, 커버리지(또는 통과 수÷기대 수) 비례 강등 (§19). 마지막 테스트 결과 **이후 수정된** 파일은 검증 분율에서 제외 (§49) | seed |
| correct (교정) | 사용자 중단(interrupt)당 4.0분. 정의: 끊고 다시 방향 잡는 **재정향 추가 비용** — 새 지시 작성은 instruct가 별도 계상(중복 아님, 상호배타 감지). **불확실 요율** — 민감도 항목(§49). interrupt 직후 첫 지시는 corrective_instructions로 표시만(과금 없음) | seed |

검토는 **누적** 기준(Edit 수정 단어 누적) — AI가 내놓는 것을 살펴보는
노동은 번복분까지 실재하므로 분자의 순계와 다른 것이 맞다(분모는 AI
경로의 추정 총비용, 분자는 직행 가정).

## 6. 한계 (해석 주의)

1. **사람 실측 정답 0건** — 모든 절대값의 상한. 상대 비교·구간
   (휴먼화 ON~OFF) 제시가 안전하다.
2. **추정÷추정** — 분자·분모 모두 요율 기반. 요율 민감도에 결론이
   좌우될 수 있다.
3. **산출물 장황함 왜곡** — 과정 장황함(헛읽기·번복·재실행)은 휴먼화가
   걷어내 정상 벌점이지만, **살아남은 산출물**이 필요 이상 크면(사람이
   코드 한 줄로 해결할 것을 모듈로 구현) 분자가 분모보다 빨리 커져
   효율이 부풀 수 있다. 측정기는 "그 분량이 필요했는가"를 판정하지
   않는다.
4. 판단 노동 과소 — verify가 규모 무관 고정 1건. §53의 전략 생각
   계상(§3)이 상당 부분 보정하나, 실행 단계 판단(verify 몫)은 여전히
   고정 1건이다.
5. 여러 세션 파일로 이어진 작업은 기여 승격이 파일 경계를 못 넘는다(§17).
6. **발화형 교정 미감지 (§49)** — correct는 interrupt만 센다. 끊기 없이
   말로 바로잡는 교정("아니 그게 아니라…")은 결정론으로 못 갈라 지시로만
   계상 — 교정 노동 과소 방향. interrupt당 4.0분의 과대 가능성과 반대
   방향으로 공존하므로 순편향 미상 — seed 민감도 병기가 이를 커버한다.
7. 결론 승격 문턱(5단어)은 seed — 짧은 승인("좋아 커밋해") 직전의 진짜
   결론도 훑기로 강등되는 과소 방향 트레이드오프(§49). 결론 정독의
   건별 300단어 상한(§51)도 seed — 실측 분포(결론 평균 173단어)에서는
   전체 정독 단어의 6%만 잘리는 방어 장치 수준.
8. **기계 몫의 thinking 미계상 (§52)** — 내부 사고 블록은 기록에 내용이
   저장되지 않아(전수 빈 문자열) 단어×요율로 측정 불가. 파일 본문·
   서브에이전트 지시문 보충(§52) 후에도 요율 환산이 실측 가동시간보다
   약 14% 작은 잔여 격차의 주 원인 — 기계 몫은 약간 보수적(과소)이다.
   (2026-08-12 신 포맷부터 토큰 **수**는 기록되므로(§53) 분모 보충
   여지가 생겼으나 미적용 — 분자 think와 달리 분모는 전량이 대상이라
   별도 설계 필요.)
9. **전략 생각(think)의 seed 성격 (§53)** — ① 요율 0.0025분/단어(정독의
   3배)는 사람 숙고 속도의 실측 근거가 없는 seed — 민감도 대상.
   ② 생각량은 모델의 reasoning effort 설정에 의존 — 같은 과제도 설정에
   따라 토큰이 달라진다(세션 간 비교 시 설정 차이가 섞일 수 있음).
   ③ 막힌 뒤 도구 사용 중간에 다시 전략을 짜는 재전략 생각은 "지시
   직후" 선별에 안 잡힘 — 과소 방향(발화형 교정 미감지 6번과 같은 부류).
   ④ 구 포맷(2026-08-12 이전) 기록은 생각량이 없어 **미계상**(§55) —
   그 세션들의 분자는 판단 노동만큼 과소다. 대체 단가로 때우던 방식은
   지시 건수를 재는 셈이라 폐기했다. 신 포맷 기록이 쌓일수록 해소되는
   한계이며, 세션 간 비교 시 **구·신 포맷이 섞이면 신 포맷 세션만
   보정을 받는다**는 점에 주의.

## 7. 사람 요율의 외부 연구 근거

`rates.json`의 사람 요율은 작업별 사람 실측 정답에서 직접 추정한 값이 아니라
seed가 다수다. 다만 읽기·작성·타이핑·검색은 인간 수행 연구와 대응시켜
현재 값의 규모가 현실 범위에 있는지 확인할 수 있다.

근거 수준은 다음처럼 구분한다.

- **직접 실증**: 현재 측정 단위와 상당히 유사한 인간 과제의 실측값이 존재.
- **인접 실증**: 관련 인간 수행 실측값은 있으나 현재 행동과 과제가 완전히 같지는 않음.
- **모델 가정**: 일반적인 단일 인간 속도로 환원하기 어렵고 현재 값은 seed로 봐야 함.

| 행동 | 현재 요율 | 속도로 환산 | 외부 근거 | 근거 수준 |
|---|---:|---:|---|---|
| read | 0.005분/단어 | **200 wpm** | 성인 영어 비문학 묵독 메타분석 평균 238 wpm, 일반 성인 주요 범위 175~300 wpm [R1] | **직접 실증** |
| skim | 0.00025분/단어 | 문서 기준 **4,000 wpm 상당** | 실제 skimming은 일반 묵독의 약 2~4배까지 가능하나 이해도가 낮아짐 [R2] | **모델 가정 — 선택 읽기로 해석** |
| draft | 0.05분/단어 | **20 wpm** | 실제 메시지를 구성하며 작성한 keyboard composition 연구에서 약 19 corrected wpm [R3] | **직접 실증** |

### 7.1 read — 200 wpm

Brysbaert의 읽기 속도 메타분석은 **190개 연구, 18,573명**을 종합해
성인의 영어 비문학 묵독 평균을 **238 wpm**, 일반적인 주요 범위를
**175~300 wpm**으로 추정한다. 현재 200 wpm은 이 범위 안이며 평균보다
약간 보수적이다. 따라서 `read = 0.005분/단어`는 외부 인간 연구로 가장
직접 방어할 수 있는 요율이다.

### 7.2 skim — "4,000 wpm"이 아니라 5% 선택 읽기

`skim = read의 1/20`을 문자 그대로 읽기 속도로 환산하면 4,000 wpm이지만,
이를 사람이 실제로 4,000단어를 읽고 이해한다는 뜻으로 해석하면 안 된다.

읽기 연구에서는 skimming이 일반 묵독보다 약 **2~4배 빠를 수 있지만
이해도와 정확도가 떨어지며**, 효과적인 skimming은 중요한 구간을 선택해
읽는 행동에 가깝다.

따라서 본 측정기의 `1/20`은 다음과 같이 해석한다.

> **전체 문서를 4,000 wpm으로 읽는다는 뜻이 아니라, 직행하는 사람은 비기여
> 텍스트 대부분을 건너뛰고 전체 단어의 약 5%에 해당하는 비용만 쓴다는 뜻이다.**

즉 **5%는 인간 연구에서 측정된 보편적 선택률이 아니라 현재 휴먼화 모델의
비용 등가 해석**이다. 이 표현이 실제 인간 읽기 연구와 충돌하지 않는다.

### 7.3 draft — 20 wpm

Karat et al.의 CHI 연구는 사용자가 주어진 내용을 베껴 쓰는 transcription과
직접 내용을 만들어 쓰는 composition을 구분했다. Composition은 업무·사회적
메시지에 대한 짧은 답변을 직접 구성하는 과제였으며, 이 연구의 keyboard
composition 결과는 약 **19 corrected wpm**으로 보고됐다. 현재
`draft = 20 wpm`과 거의 일치한다.

따라서 draft는 단순 키 입력 속도가 아니라 **무엇을 쓸지 생각하면서 최종
문장을 생산하는 속도**로 설명하는 것이 맞다.

### 7.4 edit — 50 wpm

Dhakal et al.은 **168,960명, 136,857,600 keystroke**를 분석했고 평균
타이핑 속도를 **51.56 wpm**으로 보고했다. 현재 `edit = 50 wpm`과 수치상
거의 같다.

다만 이 연구는 주어진 문장을 입력하는 text-entry 과제이며, 기존 문장을
이해하고 수정 방향을 판단하는 편집 과제 자체를 측정한 것은 아니다.
따라서 **50 wpm은 수정 문구를 실제로 입력하는 처리량의 실증 anchor**로
사용하되, edit 전체의 직접 실측값이라고 주장하지 않는다.

또한 WPM은 통상 5 characters를 1 word로 환산하는 관례가 있으므로,
현재 구현의 단어 집계 방식이 공백 기준이라면 한국어·코드에서는 절대값을
직접 동일시하지 않는다.

### 7.5 search — 2분/기여 착지

Aula et al.의 Google 연구에서 성공한 정보검색 과제는 평균 **176.2초
(2.94분)**가 걸렸고 평균 **4.98개 query**가 사용됐다.

현재 측정기는 query 하나마다 2분을 부과하지 않고 **여러 query refinement를
거쳐 실제 기여 문서에 착지한 search episode 하나**에 2분을 부과한다.
따라서 연구의 2.94분과 정확히 같은 값은 아니지만 같은 크기이며, 단순
검색 호출당 요율보다 현재 정의와 더 잘 대응한다.

### 7.6 execute·review·verify — 인간 상수가 아니라 episode 비용

HCI의 Keystroke-Level Model에서는 숙련 사용자의 키 입력·포인팅·명령
실행 같은 저수준 조작은 대체로 초 단위로 모델링한다.

따라서 `execute = 2분/건`을 **명령을 입력하고 실행 버튼을 누르는 시간**으로
설명하면 근거가 맞지 않는다. 본 측정에서는 다음이 합쳐진 **execution
episode 비용**으로 해석한다.

```text
무엇을 실행할지 판단 → 명령 구성 → 실행 → 결과 확인
```

review도 동일하다. NASA의 software inspection 지침은 inspection별 총 투입
시간과 참여자가 개별 검토에 쓴 시간을 실제 데이터로 기록하도록 한다.
이는 리뷰 비용이 고정 인간 상수라기보다 대상과 검토 수준에 따라 달라지는
작업이라는 해석과 맞는다.

hitl 코드 검토의 턴 확인 과금(§50, §4.3)도 같은 근거 위에 있다 —
modern code review 연구(Google의 대규모 change 분석 등)는 review를
"파일 하나"가 아니라 **변경(change) 단위 활동**으로 다루므로, 기본
"돌려 확인" 비용은 사람이 실제로 멈춰서 살펴보는 **확인 시점(실질 지시
턴·세션 끝)당 1회**만 계상하고, 파일 수는 내용물 훑기 단어로만 반영한다.
구 파일당 고정비는 저장소의 파일 분할 방식이 hitl을 좌우하는 편향이라
폐지했다(§49에서 에피소드화 → §50에서 턴 확인으로 일반화).

따라서 `review 125 wpm`, `execute 2분`, `verify 3분`, `correct 4분`은
현재 단계에서는 **실증 인간 평균이 아니라 모델링 seed**로 유지한다.

### 7.7 외부 설명 시 권장 표기

요율의 근거를 외부에 설명할 때는 다음과 같이 구분한다.

- **문헌 직접 anchor:** read 200 wpm, draft 20 wpm
- **문헌 인접 anchor:** edit 50 wpm, search 2분/기여 착지
- **모델링 seed:** skim 1/20, execute 2분, review 요율, verify 3분, correct 4분,
  think 0.0025분/단어(§53)
- skim 1/20은 **4,000 wpm 인간 독해 주장**이 아니라 **비기여 텍스트를
  대부분 건너뛴 선택적 읽기의 비용 근사**
- 외부 문헌은 현재 요율이 인간 수행 범위에서 크게 이탈하지 않는지 확인하는
  anchor일 뿐, 이 측정기와 동일 과제를 사람이 수행한 ground truth는 아니다.

따라서 §6의 **"사람 실측 정답 0건" 한계는 그대로 유지**한다. 향후 동일
작업을 사람에게 직접 수행시킨 paired measurement가 확보되면 해당 실측이
외부 문헌보다 우선한다.
