1m 26s 동안 처리함

결론부터 말씀드리면, HITL 요율 전체의 크기는 대체로 리즈너블합니다. 다만 현재 가장 취약한 부분은 review 코드 파일당 2분과 correct 4분/interrupt입니다. 숫자 자체보다 과금 단위가 실제 감독 노동과 어긋날 가능성이 큽니다.

항목	판단	이유

instruct: 0.5분 + 0.05분/단어, 60단어 cap	적정	1,456건 실측 보정이므로 HITL 중 가장 강한 항목. 20단어 지시는 1.5분, 60단어 이상은 최대 3.5분이라 규모도 자연스러움
문서 review: 0.008분/단어	적정~보수적	125 wpm은 일반 묵독 200~238 wpm보다 느려 “검토하며 읽기”라는 정의와 잘 맞음
진행문 review: 0.002분/단어	적정	500 wpm 상당이라 정독이 아니라 훑기 비용으로 해석하면 무리가 적음
코드 review: 파일당 2분 + 0.002분/단어	수정 권고	파일 개수가 노동량을 결정하는 구조가 가장 문제
테스트 통과 시 2.0 → 0.3분	방향은 적정, 수치는 seed	자동 검증이 사람 부담을 낮춘다는 방향은 맞지만 coverage와 사람 검토시간이 선형으로 대체된다는 근거는 약함
correct: 4분/interrupt	수정 권고	단순 한 줄 교정과 방향 전환을 동일하게 4분 처리하며, instruct와 중복 과금될 가능성


특히 코드 review의 파일당 2분은 바꾸는 게 좋습니다. 같은 500줄 변경도 한 파일이면 기본 2분, 10개 파일이면 기본 20분입니다. 즉 에이전트 성능이 아니라 저장소의 파일 분할 방식이 speedup을 움직입니다. 실제 modern code review도 “파일 하나”보다는 변경 단위 중심의 활동입니다. Google의 대규모 code review 연구는 900만 건의 변경을 분석하는 식으로 review를 change 중심으로 다루고 있고, 리뷰 후 사람이 쓰는 active shepherding time도 review comment 수에 따라 거의 선형적으로 증가하는 것으로 보고합니다.  NASA의 formal inspection 자료 역시 검토량·검토속도·맥락에 따라 effort가 크게 달라짐을 보여주며, 보편적인 “파일당 몇 분” 상수를 지지하지는 않습니다. 

그래서 지금 당장 최소 수정한다면 코드 파일당 2분을 코드 review episode당 2분으로 옮기는 것을 권합니다. 예를 들어 한 세션에서 7개 코드 파일을 만들었더라도 사용자가 한 번에 결과를 검토한다면 기본비는 2분 한 번만 부과하고, 변경된 코드량에 대한 0.002분/단어를 누적합니다. 기존 요율의 절대 규모를 건드리지 않으면서 파일 구조 편향만 제거할 수 있습니다.

2.0 → 0.3분 테스트 강등도 같은 방식으로 episode의 기본 검증비에 한 번 적용하는 편이 낫습니다. 테스트·coverage가 코드 리뷰에서 실제로 유용한 신호라는 산업 연구는 있지만, coverage 80%면 사람 검토비도 정확히 80% 가까이 줄어든다는 실증 근거는 없습니다. Google도 coverage를 changeset/code review에 활용하지만 그런 선형 치환 관계를 주장하지는 않습니다.  따라서 현재 방식은 충분히 쓸 수 있으나 명시적으로 modeling seed로 남겨두는 게 맞습니다.

correct = 4분/interrupt는 조금 과합니다. 개발 작업에서 interruption과 context switching에 실제 인지 비용이 있다는 점은 잘 확인되어 있습니다. Microsoft 연구에서도 개발자는 코드에 대한 mental model을 유지하기 때문에 interruption 후 복귀가 부담이 된다고 보고했고, 후속 연구들도 작업 복잡도와 interruption 종류에 따라 비용이 크게 달라진다고 봅니다.  문제는 Claude를 보다가 “아니, 이 함수 말고 저 함수”라고 즉시 고치는 것과 30분짜리 작업 방향을 폐기시키는 것을 똑같이 4분으로 보는 것입니다.

더구나 interrupt 메시지 자체가 instruct에도 잡힌다면 20단어 교정 하나가 instruct 1.5분 + correct 4분 = 5.5분이 됩니다. 이 경우 상당히 공격적인 HITL 벌점입니다. 저는 correct 4분을 없애기보다는 “추가 재정향 비용”이라고 정의해서 1~4분 범위의 seed로 민감도 분석하는 것을 권합니다. 결정론을 유지해야 한다면 당장은 4분을 유지하되 외부 보고에서는 가장 불확실한 요율 중 하나로 표시하는 편이 안전합니다.

또 하나는 용어입니다. 현재 문서의

> AI 경로의 실제 비용 = 기계 + 사람 감독



에서 기계 비용뿐 아니라 review·correct도 대부분 모델 요율로 추정하므로, 엄밀히는 “AI 경로의 추정 비용” 또는 **“추정 active human supervision cost”**가 맞습니다. instruct처럼 실제 보정된 항목과 seed review를 모두 “실제 비용”으로 묶으면 외부 검토에서 공격받기 쉽습니다.

최종적으로 제가 등급을 매기면 instruct A / 문서 review B+ / 진행 review B / 코드 review C / 테스트 강등 B- / correct C+ 정도입니다. 전체 모델을 갈아엎을 수준은 아니고, ① 코드의 per-file 고정비를 per-review-episode로 변경, ② correct 4분을 민감도 항목으로 격하하는 두 가지만 해도 HITL 쪽은 상당히 방어력이 좋아집니다.

그리고 최종 리포트에서는 speedup 본값과 함께 HITL 요율 0.5배 / 1배 / 2배 민감도를 같이 내는 게 좋습니다. 현재 남아 있는 seed 불확실성을 숨기지 않으면서도 “요율을 두 배 흔들어도 세션 간 상대 순위가 유지되는가”를 바로 보여줄 수 있습니다.
