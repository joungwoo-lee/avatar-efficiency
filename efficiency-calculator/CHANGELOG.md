사고 → 원인 → 수정 순으로 누적 기록. 상세 근거는 각 폴더 문서 참조.

## 1. 분자 재개발 — 방법론 v0.5→v0.6 (human-effort/requirement-based)

- 3계층 분리 구현: LLM은 수량만 / catalog.json이 시간분포 / 코드가 Monte Carlo로
  P50·P80을 최종 분포에서 1회 산출. LLM의 시간 출력은 검증기가 재귀 제거.
- **인플레이션 사고와 통제** (메일 회신 338.8분 → 16.1분, 상세: doc/DESIGN.md §2.3):
  - 기준 노동 명문화: 배제는 생성형 AI뿐(도구 전부 사용) + 합리적 최단 경로
  - 요구사항 발명 금지(중간 활동의 산출물 승격 차단), 분해 상한, 습관성 QA 금지
  - 경량 Work Unit 6종(잔일 보기), 수량 단위 일치 강제, conflicts_with 중복 제거
  - "자동화→시스템 구축" 오독 차단: 운영/구축 구분 + SW 라우팅 교차검문
    (RCA 세션 3연속 SW 항목 0건)
  - Pass D(독립 재검토, 깎기만 가능) — critic=True 옵션
- 입력 케이스 분리: 아바타 정의서(A-avatar, 변환)와 트랜스크립트(§23, 복원)를
  별도 1단계로, 2단계부터 공용(estimate_from_requirements).

## 2. 구조 재편 — efficiency/ 통합과 용도별 API

- human-effort(분자)·agent-effort(분모)·counterfactual-api(아바타 사전 API)
  + session-api(세션 사후 API, 신설)로 정리. 규칙: 부품 + 용도별 조합.
- 분자 방식 3종을 이름·폴더로 분리 (혼동 방지):

| 공식 이름 | 폴더 | 흐름 |
|---|---|---|
| **요구사항·산출물 방식** (기준 자) | `human-effort/requirement-based/` | 할일 추출 → 산출물 단위(명사) × 카탈로그 분포 → Monte Carlo |
| **요구사항·행동 방식** (신방식) | `human-effort/requirement-actions/` | 할일 추출 → 사람 행동(동사) × 요율, 숫자는 닻으로 코드 확정 |
| **세션기록·행동 방식** (교차확인) | `human-effort/record-actions/` | 기록 신호에서 바로 사람 행동 시뮬 × 요율 (+하이브리드 옵션) |

공용 부품(할일 추출기·정규화·LLM 시뮬)은 `human-effort/shared/`.

## 3. 분모 측정 기조 확정 (agent-effort)

- 프레임: **사람·AI 협업의 양측 에포트를 같은 단위(분)로 합산**
  — agent_min = 사람 감독(hitl) + AI 실소모.
- hitl은 wall-clock이 아니라 **단서 × 요율** (검토·후작업은 세션 밖에서 몰아
  할 수 있어 세션 시간으로 못 잡음). 타임스탬프는 요율 값 보정 재료로만.
- 병렬 서브에이전트는 실소모 시간에 가산 금지 (자원량 옵션만).
- 분모는 LLM 0회·결정론 (죽은 LLM 주소로 실행 증명).

## 4. 요율 실측 보정 1호 — hitl.instruct (rates.json)

- 트랜스크립트 타임스탬프(직전 응답→지시 간격) 1,456건 분석: net 중앙값 0.61분,
  구 3.0분/건은 2~5배 과대. 100단어+ 지시는 붙여넣기 증거로 상한 필요.
- 실측 경로: `instruct = 0.5분(생각 여유) + 0.05분 × min(단어수, 60)`,
  사전 경로: 건당 1.7분(실측 평균). 효과: 6세션 종합 speedup 2.38→3.22x.

## 5. 신호 체계 — "어떻게 했나"는 빼고 "뭐가 만들어졌나·요구됐나"는 넣기

정규화(shared/transcript_requirements)가 기록에서 결정론 추출하는 신호:
- [산출물 규모] 작성 단어 순계 (반복 재작성 중복 제거)
- [입력 자료 규모] 사용자 제공 텍스트량 / [조사 자료 규모] 검토된 자료량(상한 명시)
- [대화 보고 규모] 파일 없으면 보고가 산출물
- [작업 구조 참고] 검토 파일 목록·탐색/실행 여부·지시 왕복 — 횟수 베끼기 금지 경고
- 도구 사용 통계는 기본 제외 (경로 베끼기 오염 실측 확인; 규모 신호 없이는
  측정 붕괴도 실측 확인 — 13.8h 작업이 54분)

## 6. 숫자 닻 — 편차 제거 (requirement-actions)

- LLM은 행동 종류만, 규모 숫자는 코드가 조정: **명시 수량은 목표, 실측치는
  상한만**(AI의 과대 읽기·장황함을 사람 견적에 상속시키지 않음 — 초과분만
  절단, 미달은 LLM의 선별 추정 존중). 검증 건수=완료조건 개수(목표).
- **할일 기반 읽기 수요**: 할일에 자료 건수가 있으면(출처 10건 등) 사람 읽기
  목표 = 건수 × 건당 선별 정독량(seed 300단어, human_reading_model) — 사람은
  필요한 부분만 찾아 읽는다는 행태를 수식화. AI가 백 페이지를 읽었어도 무관.
- 효과: 반복 실행 편차 ±0.1~4% (닻 이전 수 배). 이중 추출 대조안은 LLM 비용
  2배라 기각.

## 7. 용어 A/B — "요구사항" → "할일(완성해야 할 결과물)"

- '요구사항'은 SW 명세 프레임을 깨워 격식 과잉 유발(완료조건 17개 발명).
  '할일' 문구로 11개로 감소, 조사형 견적이 기준 자에 수렴, 악화 유형 없음.
- 프롬프트 표현만 교체, 스키마 필드명(requirements.v1)은 규약 유지.

## 8. 실측 대조 자산 (네 PC 세션 14개)

- 분자 두 자 대조: 합산 0.98배 수렴하나 유형별 0.2~2.7배 계통 괴리 —
  유형별 신뢰 자 규칙(문서·채점형은 요구사항·산출물 방식, 코드형 병행).
- 하이브리드(요구사항+기록) 실측: 조사형 0.64→0.88배 수렴, 악화 없음.

  장치가 핵심 통제임을 재확인.

## 9. 업무 종류별 효과 분석 (14세션, 요구사항 거침 vs 안 거침)

- 조사·분석형: 거치면 2~4배 상향 — 누락 노동 복원 (핵심 이득)
- 대형 코딩·문서형: 무차이(±20%) — 실측 닻이 지배
- 초소형·잡담: 거치면 5~7배 역부풀림 (완료조건 고정비) →
  **초소형 자동 제외 게이트 구현** (session-api: 검토·입력 <100단어 &
  산출물 <50단어면 측정 제외, force로 강제 가능)
- 번복·오해 많은 세션: 차이가 나야 하는 유형 — AI 사용에는 **의도 전달의
  어려움**이라는 고유 비용이 있어, 분모는 헛답·재지시를 전부 세고(효율 하락으로
  반영), 요구사항 거침은 번복 조각을 걸러 사람 견적을 보호, 안 거침은 헛발질
  오염 위험이라 부적합 (human-effort/README 참조)

## 10. 아바타 측정 분자를 요구사항·행동 방식으로 교체 (counterfactual-api)

- compat 기본 human_method="actions": 카드→할일(A-avatar) → 사람 행동 × human
  단가. **분자·분모가 같은 행동×단가 체계가 되어 speedup의 체계 불일치 편향
  구조적 소멸** — RCA 카드 실측: 산출물 방식 speedup 19.2x(다른 자) →
  행동 방식 2.2x(같은 자, 해석 가능). P80은 없음(점추정), 구 방식은
  human_method="workunit"으로 보존.
- 사전 측정은 실측 닻이 없어 카드 명시 수량·완료조건 닻만 작동 —
  카드에 수량을 적을수록 정확.

## 12. 아바타 측정 단일호출 복원 (integ-spec §3 정합)

- 아바타 카드는 이미 정리된 업무 정의 — 별도 할일 변환 호출은 군더더기라는
  지적에 따라, §3 스키마 그대로 **LLM 1회가 human/agent/hitl 세 경로를 같은
  완료상태 기준으로 함께 분해**하는 paths.py로 복원 (3회→1회). 그간의
  안전규칙(기준 인물·오독 방지·수량 근거·이중 계상 금지·선별적 읽기)은
  프롬프트 규칙으로 흡수. 분자·분모 동일 체계 유지.
- 실측: RCA 카드 human 49.5분/agent 24.9분/speedup 2.0x, 메일 카드 human
  17분(스펙 예시 수기검산 일치)/speedup 2.7x — 전부 LLM 1회.
- workunit 모드(분포 필요 시)만 3회.

## 13. 읽기량 항해 구조 환산 (AI 읽기 → 사람 읽기)

- 문제: 세션 기록 기반 측정에서 읽기 닻이 "AI가 읽은 총 단어수"의 상한 절단뿐
  — AI는 전수 탐색으로 수만 단어를 읽으므로 상한이 사실상 무의미, LLM 추정
  편차가 그대로 남았다. 근거 논문 "Strategic Navigation or Stochastic Search?":
  에이전트는 brute-force로 읽고, 사람은 전략적으로 항해한다.
- 해법: 비율 곱셈이 아니라 **구조 분해**. collect_record_stats가 기록에서
  결정론적으로(LLM 0회) 분류 —
  기여 자료(읽힌 파일 중 이후 편집됐거나 최종 답변에 이름 언급) × 정독 300단어
  + 훑은 후보(읽혔지만 결과에 안 쓰임) × 스캔 60단어 + 사용자 제공 입력.
- 닻 우선순위: 할일 명시 건수 > 항해 구조 환산 > 실측 상한만.
  rates.json human_reading_model에 skim_words_per_doc(60) 추가.
- 검증: 합성 기록(3파일 읽음, 1편집+1답변 인용 → 기여 2/훑기 1) 테스트 —
  AI가 5,000단어 읽어도 사람 읽기 = 2×300+1×60 = 660단어로 확정.

## 14. 기여 자료 판별 5신호 확장

- 문제: 초기 판별(편집 또는 최종 답변에 파일명 언급)은 "쓰기" 흔적만 봐서
  조사형 세션(편집 없음·이름 인용 드묾)이 기여 0건 — 전부 훑기 처리로 과소.
- 해법: "찾았다"의 흔적도 기록에 남는다는 지적에 따라 5신호로 확장
  (전부 도구 호출 기록의 코드 판별, LLM 0회):
  ① 편집 ② 어느 발언에든 이름 언급 ③ 재방문(2회 이상 읽음)
  ④ 탐색 종료 후 읽기(마지막 Glob/Grep/WebSearch 뒤의 읽기 = 목적지 도달;
     검색 없던 세션엔 미적용) ⑤ 내용 겹침(6단어 연속 조각·식별자가 최종
     답변에 등장 — 문자열 대조).
- 잔여 한계: 완전 패러프레이즈+1회 읽기+검색 지속은 못 잡음(보수 방향).
- 검증: 합성 기록 테스트(검색 후 읽은 2건 기여, 검색 전 1회 읽고 무흔적
  1건 훑기). 실세션 점검 — 스크린샷 진행 확인만 있던 세션은 기여 0건
  유지(정당: 문서 아님).
- **멀티턴 보정** (긴 대화 세션 점검에서 4결함 발견·수정):
  ① 신호④가 세션 전체 기준이라 초반 검색 한 번이 이후 모든 읽기를 기여로
    오염(과대)·뒤 턴의 새 검색이 앞 턴 발견을 삭제(과소) → **사용자 턴
    단위**로 판정 ② 신호③이 offset 다른 분할 이어읽기(AI 전수 읽기)를
    재방문으로 오인 → **같은 구간 재읽기만** 재방문 ③ 신호⑤가 마지막 답변만
    대조해 앞 턴 기여 누락 → **턴별 마무리 답변 전부** 대조 ④ 병렬
    서브에이전트 기록(isSidechain)이 집계에 합산 → 전체 제외(측정 기조 일치).
  멀티턴 합성 테스트로 4개 모두 검증.

## 15. 헛읽기(WASTE) 등급 도입 — 3등급 위상 재생

- 문제: 2등급(기여/훑기)이라 기여 확보 **후**의 시행착오 읽기에도 훑기
  60단어/건이 과금됐다 — 사람은 찾은 뒤에는 그 파일들을 열지도 않는다.
- 해법(외부 제안 로직 반영): 신호 판정은 미래 턴 포함 세션 전체로 끝낸 뒤,
  턴별 시간순 재생으로 "그 턴의 마지막 기여 읽기 이후에만 읽힌 비기여 파일"을
  WASTE(0)로 분류. 항해 중(기여 확보 전) 읽힌 비기여 파일만 SKIM(60).
  "충분한 기여 확보" 같은 판단어 대신 이 규칙으로 고정 — LLM 0회 결정론 유지.
- 동반 수정: 신호④를 "마지막 검색 뒤 모든 읽기"에서 **착지 1건**(검색 직후
  첫 읽기)으로 축소 — 전부 승격시키면 WASTE 구분이 불가능해지는 충돌 해소.
- 제안 로직과의 잔여 차이(미채택): 목표 기준 Episode 분할(의미 판단이라
  턴 근사 유지), content fingerprint(경로+구간 키로 갈음).

## 16. LLM 대조 검증 실험 + 세션 내부 부산물 제외

- 검증: 실세션 3개(읽은 파일 38~54개)를 코드와 독립 LLM 심판(신호 규칙 미제공,

## 18. 산출물 유형별 검토 모델 (분모 hitl.review)

- 문제: 검토 = "AI 채팅 보고 전량 × 단일 요율(0.006)"뿐 — 파일 산출물(코드·
  문서) 검토가 계상 누락이고, 보고는 선별 없이 전량 과금.
- 지적: 검토 방식은 산출물이 정한다 — 코드면 동작을 돌려봐야 하고,
  문서·PPT면 내용을 봐야 한다.
- 해법(hitl_review_model, 결정론·LLM 0회): 확장자로 유형 판별 —
  코드 = 파일당 실행 확인 2.0분 + 변경분 훑기 0.002분/단어 (내용 통독 아님),
  문서 = 내용 정독 0.008분/단어, 설정·데이터 = 파일당 표본 확인 0.5분,
  채팅 보고 = 결론(턴 마무리 답변) 정독 0.008 + 진행 보고 훑기 0.002.
  Write 전체 재작성은 마지막 판만 과금(재작성 중복 방지), Edit는 누적.
- 전부 seed 요율(미보정) — instruct처럼 실측 보정 대상 (미해결 5번과 연동).
- 실측: 자동 반복 대형 세션 감독 304→520분(누락되던 코드 22파일·문서
  16,109단어 검토 편입), 수기검산 테스트 2건.

## 19. 검증 위임 강등 — 테스트 자동화가 없애는 사람 노동의 계산

- 문제 제기: 사람 병목이 진짜 병목 — 테스트까지 자동화된 플로우면 사람의
  동작 확인 노동이 사라지는데 분모가 이를 못 봤다.
- 해법(결정론, LLM 0회): 기록에서 테스트 실행 명령(pytest 등)과 그 출력의
  통과/실패·통과 건수·커버리지를 파싱. 마지막 실행이 통과 상태면 코드 검토
  요율을 "직접 돌려 확인(2.0분/파일)" → "결과 서명(0.3분/파일)"으로 강등.
- **이분법 금지**: 강등 폭은 실질 규모에 비례 — 커버리지 % 실측 우선, 없으면
  통과 테스트 수 ÷ (수정 코드 파일 수 × 기대 3건/파일). 형식 유닛테스트
  1건으로는 할인이 거의 없고, 실패 상태로 끝나면 강등 0.
- 없앤 노동은 automation_saved_min 필드로 정량 출력 — 인아웃 계약 안에서
  완결(사람 개입 장치 없음). 문서형 검토는 강등 없음(자동 검증 불가).
- 한계 명시: 테스트의 실질성(assert 없는 스모크 통과)은 코드로 못 잼 —
  개수·커버리지는 근사.
- 실측: 테스트 258건 통과 세션 — 코드 22파일 검토 강등, 없앤 노동 37.4분.
  테스트 없는 세션 0분. 수기검산 3케이스(충분/형식/실패) 테스트.

## 20. 구방식(record-actions)에도 닻 이식 + 할일 중간층 가치 대조 실험

- 조치: `primitive_effort.estimate_human_min`이 `record_stats`를 받아 신방식과
  동일한 닻(derive_anchors/apply_anchors — 항해 구조 읽기량, 산출물 상한,
  검증 건수)을 적용. api.py record-actions 경로에 stats 연결. 이제 두 방식의
  차이는 "할일 중간층을 거치느냐"만 남는다 — 숫자 결정권은 양쪽 다 코드.
- 실험: 실세션 3건(중형 설정수정 / 대형 코드패키지 / 소형 리뷰의견) ×
  2방식 × 행동분해 2반복, 독립 LLM(병렬 서브에이전트) 대조.
- 결과:
  - **읽기: 완전 수렴** — 닻이 양쪽 read를 동일 값(450/2,437/839단어)으로
    확정. 읽기 측은 중간층 가치 없음(코드 닻이 이미 해결).
  - **쓰기: 4~5배 발산** — 대형 세션에서 구방식 draft=14,700단어(AI 산출
    전량 상속) → 913~1,073분; 신방식은 할일 스코프로 draft 300+edit 위주
    → 209~214분. 실측 산출물량 닻은 **상한**이라 "AI가 쓴 만큼 사람도 쓴다"
    는 과대를 못 자름 — 할일 중간층이 유일한 스코프 필터.
  - **대화 오염**: 구방식은 세션 대화 형태를 노동으로 상속(communicate
    12~42건, execute 15~18건); 신방식은 할일에 없으면 안 잡음(execute 2~11).
  - 반복 안정성: 신방식 ±1~9%, 구방식 ±0~8% — 닻 통일 후엔 비차별.
- 효율(speedup = 분자÷분모, 분모는 실측 공통):

  | 세션 | agent_min | 구 분자→효율 | 신 분자→효율 |
  |---|---|---|---|
  | S1 설정수정(중형) | 9.6 | 42.4 → 4.4배 | 27.3 → 2.8배 |
  | S2 코드패키지(대형) | 297.3 | 993.2 → 3.3배 | 211.7 → **0.7배** |
  | S3 리뷰의견(소형) | 7.3 | 45.5 → 6.3배 | 81.7 → 11.3배 |

  구방식은 산출물 많은 세션의 효율을 부풀리고(S2: AI 이득 없는 세션이 3.3배로
  둔갑), 산출물 없는 답변형 세션의 판단 노동을 깎는다(S3). 중간층이 효율
  판정의 방향 자체를 바꾼다.
- **판정: 중간층 가치 있음** — 읽기가 아니라 **쓰기 스코프와 AI 경로 오염
  차단**에 있다. 미해결 3(AI 장황함)의 방어선이 바로 이 층. record-actions는
  기준선으로 유지하되 측정 기본값은 req-actions 유지.

## 23. 읽기 닻을 건수×300에서 등급별 실측 단어 × 등급 요율로 교체

- 지적: 코드가 파일별 읽기량을 실측하는데 왜 건당 고정 300단어를 쓰나 —
  전수 읽기의 대부분을 탐색의 낮은 요율로 빼고, 기여 조건을 통과한 것만
  실측량 그대로 정독 요율로 계산하라.
- 조치 (두 방식 공통 — 닻 기계가 공용이므로 한 곳 수정):
  - `collect_record_stats`: 파일별 실측 읽은 단어수 추적(`deep_words`/
    `skim_words`/`waste_words`), 같은 구간(fp+offset) 재읽기는 1회만 집계.
  - `derive_anchors`: 읽기 닻 = 기여 실측 단어 그대로(정독) + 훑기 실측 단어
    × 탐색요율/정독요율 + 헛읽기 0 + 입력. 탐색요율 `skim_min_per_word`
    0.0005(정독 0.005의 1/10, seed) rates.json 신설.
  - 우선순위 개편: 실측 등급(1순위) > 할일 건수×300(읽기 본문 미기록 시
    폴백) > 실측 상한만. 건수×300은 실측 단어를 잴 수 없을 때만 잔존.
  - 프롬프트 3곳(할일 행동분해·단일호출·record-actions) 갱신: "읽기 규모는
    시스템이 실측 등급으로 확정, 비율 임의 결정 금지" — 구 3~7할 휴리스틱
    문구 삭제.
- 테스트: 실측 등급 경로 신규(기여 1,200단어 정독 + 훑기 1,300×0.1 = 닻
  1,330, 재읽기 중복 제거 검증). 기존 건수 테스트는 폴백 경로로 재해석.
- 실세션 확인 (§20의 3세션 재계산): 읽기 닻 S1 450→349(기여 1파일 실측
  199단어 — 300 고정치가 과대였음), S2 2,437→14,383(기여 6파일 실측
  13,746단어 — 300 고정치가 대폭 과소였음), S3 불변(파일 읽기 없는 답변형
  — 입력 839단어만). 건당 300은 방향까지 틀리는 고정치였고, 실측 등급이
  세션마다 제 값을 잡는다.

## 24. 건수 환산 폴백 폐지 · 정독 요율 1/5 보정 · max_tokens 8,000 통일

- **폴백 폐지**: 읽기 본문이 기록에 없어 실측 단어가 0이면 구조 닻을 만들지
  않는다 — 잴 수 없는 입력에 건당 고정치(300/60)를 곱해 숫자를 지어내는 것
  자체가 근거 없음. 실측 총량 상한 경로로 떨어진다. 실전 Claude Code
  기록에는 읽기 결과 본문이 항상 남으므로 폴백은 사실상 사문이었다.
  `skim_words_per_doc` 키 삭제. (할일 명시 건수 닻 — "출처 10건"×300 — 은
  읽기 기록이 아예 없을 때의 정규 경로로 유지.)
- ~~정독 요율 1/5 인하~~ → **원복** (같은 날): "통독 요율 1/5" 지시를
  human.read 인하로 해석해 0.005→0.001 적용했으나 지시 해석 오류로 판명 —
  0.005/0.0005(탐색)로 되돌림. 어느 요율을 내릴지는 재지시 대기.
- **max_tokens 통일**: LLM 호출 기본값을 전 모듈 8,000으로 (기존 2,000~
  6,000 혼재 — 긴 세션의 행동 목록·할일 목록이 잘릴 수 있었음).
  integ-spec 계약 표기도 8,000으로 갱신.
- 테스트 수기검산 갱신(정독 0.001 반영), 5종 전부 통과.

## 25. 기여 신호 과대 발화 수정 — "대부분 정독" 문제

- 지적: 등급을 나눠도 실측 결과 99% 이상이 정독 — 로직 의심.
- 신호별 귀속 분석(실세션)으로 범인 확정: **신호⑤ 식별자 매칭 고장.**
  8자 이상 `[A-Za-z_]` 정규식이 일반 영단어(Analysis, Accepted, Anthropic …)
  까지 "식별자"로 잡고, 그중 1개만 파일에 있어도 전체 정독 승격 —
  S2에서 읽은 6파일 전부가 ⑤로 승격됐고, 그중 2파일은 진짜 인용 증거
  (6단어 조각) 0회였다.
- 수정 (전부 결정론):
  - ⑤ 식별자를 구조적 토큰(`_`·`.`·`/` 포함)으로 한정 — 일반 영단어 배제.
  - 변별력 필터: 읽은 파일이 3개 이상일 때, 그중 2개 이하에만 나오는
    식별자만 증거 인정 — max_tokens·complete_json 같은 공용 어휘가 모든
    파일을 승격시키는 것 차단.
  - 매치 2개 이상 요구(우연 일치 방지). 6단어 조각 1회는 그대로 인정.
  - ② 이름 언급을 턴 마무리 답변으로 한정 — 진행 나레이션("이제 X를
    읽겠습니다")은 기여 증거가 아님.
- 효과(실세션 S2): 정독 6건 13,746단어 → 정독 4건 13,038 + 훑기 1건 260
  + 헛읽기 1건 448. 공용 어휘로만 이어졌던 estimator.py·onprem_llm_sim.py
  가 헛읽기·훑기로 강등.
- 남은 한계(미해결 7 신설): 편집·인용된 기여 파일은 실측 전체 단어가
  정독 과금 — 사람은 기여 파일도 필요한 구간만 읽는다. 파일 내부의
  구간 수준 정독/훑기 분해가 다음 지렛대.

## 26. 구간·블록 분해 — "사람은 전략적 탐색 후 핵심만 읽는다"

- 지정: 훑기가 정독보다 훨씬 많아야 하고, 훑기 속도는 정독의 10배보다
  빨라야 한다. 이 PC 세션들로 비율 실측 후 로직 재설계.
- 실측(이 PC 9세션, 200KB+): §25 수정 후에도 **정독 비중 95%** — 기여
  파일이면 실측 전량 정독 과금하는 파일 단위 구조가 원인.
- 재설계 (전부 결정론, LLM 0회):
  - 기여 파일 안을 읽기 구간(offset) → 200단어 블록으로 분해. **증거가
    닿은 블록만 정독**: 변별 식별자 2개+ / 6단어 조각이 마무리 답변 또는
    그 파일의 편집 원문(Edit old_string+new_string)과 직접 겹침.
    나머지 블록은 훑기.
  - Write 전체 본문은 편집 증거 불인정 — 파일 재작성이 전 블록을 정독으로
    물들임. 착지·재방문 구간 통째 정독 경로도 제거(파일 승격 신호로만).
  - 훑기 요율 0.0005 → **0.00025 (정독의 1/20)**.
- 비율 변화(같은 9세션): 정독 95% → 69%(블록 도입) → 56%(Write 증거
  제거·식별자 2+) → **51%** (세션별 29~78%). 정독으로 남은 단어는 전부
  "답변에 인용됐거나 편집 지점 주변" — 증거 기반.
- **분자 읽기 시간 효과**: AI가 읽은 실측량은 그대로 두고 사람 환산만
  바뀐다 — 9세션 합계 읽기 환산 875분 → 488분 (**44% 감소, 약 절반**).
  정독 등가 단어로는 174,970 → 97,670. 원인 분해: 정독 단어 절반이
  훑기로 강등(구조) + 훑기 요율 1/10→1/20(요율).
- 검증: 블록 분해 수기검산 테스트(alpha 200 정독 + beta 1000 훑기),
  5종 스위트 통과. 미해결 7(구간 수준 분해) 해소.

## 27. 조회형 읽기 일반화 — 파일 아닌 자료(지라 티켓 등)도 같은 자로

- 지적: 지라 티켓을 스킬·MCP로 읽어도 기록에 흔적이 남는데 파일만 등급
  분해되고 있었다 — 티켓 읽기는 총량 상한으로만 잡히고 구조 변환 누락.
- 조치 (결정론, LLM 0회): 결과 본문 50단어 이상인 비실행·비검색 도구
  호출을 읽기로 인정. 신원 = 도구명+정규화 인자(같은 인자 재호출 = 재방문
  ③ + 중복 제거). 검색형 이름(search/list/query/find)은 탐색 신호(④의
  기준점). 신호② = 인자 속 id성 토큰(티켓 키)이 마무리 답변에 등장.
  ⑤ 내용 겹침·블록 분해·위상 재생(훑기/헛읽기)은 파일과 동일 경로.
  ①(편집)은 조회형 미적용 — 갱신 도구와 조회 신원을 잇는 결정론 규칙이
  없어 보수적 생략.
- 실행형 대량 출력(Bash 로그 등)·짧은 상태 응답(50단어 미만)은 읽기 아님.
- 검증: 합성 테스트(검색→착지 티켓 기여 / 후속 티켓 헛읽기 / Bash·ack
  제외). 실세션 9개 회귀 — 비율 안정(정독 50%), 5종 스위트 통과.

## 28. 쓰기 분류(draft/edit) 닻 통일 — 신구 대조 방향 불일치의 주범 제거

- 지적(10세션 브레이크다운 대조): read는 닻으로 동일한데 신구 결과가
  양방향으로 갈림. 근인 = draft/edit 분류가 LLM 재량 — 신방식은 수정으로,
  구방식은 신규 작성+대화 답변까지 draft로 계상. 요율이 2.5배 차이
  (draft 0.05 vs edit 0.02)라 분류 재량이 그대로 금액 편차가 됨.
- 조치:
  - **분류 결정권 회수**: 도구 기록이 분류의 진실 — Write 최종본 = 신규
    작성(out_draft_words), Edit new_string 누적 = 수정(out_edit_words)을
    실측 집계. 쓰기 총량은 기존 원칙(명시=목표, 실측=상한) 그대로 정하고,
    draft:edit 배분은 실측 비율로 재배분(LLM 분류 덮어씀, LLM에 없는
    쪽은 추가). 닻 기계 공용이라 두 방식 동시 통일.
  - **대화 왕복 communicate 금지**: record-actions 프롬프트에 명시 —
    사람 혼자 시나리오에는 사용자↔AI 대화가 없다. communicate는 할일
    자체가 소통 산출물(메일 발송 등)일 때만.
- 남김: verify 차이(신방식 완료조건 1:1 vs 구방식 재량)는 할일 중간층
  유무의 본질적 차이라 통일 대상 아님 — 완료조건 근거가 있는 신방식이 기준.
- 검증: 분할 재배분 수기검산(실측 200:300, LLM 전량 draft 900 → draft
  200+edit 300=16.0분), 5종 스위트 통과.

## 29. 비교 불변식 req ≤ rec — staged 프롬프트의 궤적 상속 구멍 봉합

- 원칙 명문화: record-actions는 AI가 한 행동을 따라가며 사람 궤적을 시뮬,
  req-actions는 궤적(의도 전달 실패로 인한 수정 왕복)을 따라가지 않고 최종
  결과물로 직행 — 따라서 같은 세션에서 **req-actions ≤ record-actions**.
- 점검 결과: 단일호출(single, 기본) 프롬프트는 부합. staged 경로 2곳이 구멍:
  - 행동 분해(`requirement_actions.build_prompt`)에 "최종본 직행·산출물당
    draft/edit 1항목·건수형 할일당 1~2건(총 ≤ 할일×3)·대화 communicate 금지"
    조항이 전부 없었음 — record-actions 프롬프트(§28에서 강화)보다 오히려
    느슨해 불변식 역전 가능.
  - 할일 추출(`transcript_requirements`)에 완료조건 상한이 없어 격식 과잉
    (A/B 실측 17개)이 verify 닻으로 직결 — record-actions에는 verify 닻이
    없어 이 부풀림은 req만 위로 민다.
- 조치: staged 행동 분해에 위 4조항 이식(단일호출과 통일), 할일 추출에
  "수용기준은 명시된 것만·할일당 최대 2개" + "고쳐진 지시는 처음부터 최종
  상태로 요구된 것으로 본다" 추가. 단일호출 2단계에도 지시 수정 왕복 배제를
  명시(기존 문구는 AI 도구 시행착오만 가리킴). PROMPT_DESIGN §② 갱신.
- 프롬프트만으로는 부족(하이쿠가 건수 규칙 무시하는 것 실측) — 코드 층 3건 추가:
  - **건수형 상한 `cap_count_actions`**: 건수형 총 건수 ≤ 할일 수 × 3
    (verify는 예산 포함·축소 제외, 나머지 비례 축소). req-actions 전용.
  - **verify 닻 목표→상한**: 완료조건 개수는 상한 목록 — 초과만 절단, 누락
    미추가. 목표 강제는 소형 세션 6분/2건 고정비로 rec(verify 닻 없음)보다
    커지는 역전을 실측으로 냄. §28의 "verify는 신방식 기준" 판단을 불변식
    우선으로 개정.
  - **보고형 쓰기 상한 `answer_words`**: 명시 수량·파일 산출물이 둘 다 없으면
    마지막 턴 마무리 답변 실측이 쓰기 상한 — staged에서 draft 1,500단어
    발명(실제 보고 95단어) 실측. 닻 기계 공용이라 두 방식 대칭 적용.
- 검증: 소형 실세션 2건(답변형·수정형) × 두 방식 × 하이쿠 실호출.
  수정 전 req>rec 역전 재현(답변형 16.5>15.2, staged 85.5>5.2, 수정형
  10.1>7.1) → 수정 후 전부 성립: 답변형 single 3회(13.2≤13.2 / 13.2≤18.2 /
  14.7≤15.2), staged 13.2≤16.2, 최종 상태 재확인 수정형 7.1≤13.1·답변형
  10.2≤13.2. 건수형도 원칙 방향(예: 수정형 execute req 1건 vs rec 4건 —
  rec는 AI의 반복 실행 흔적을 상속). 단위 테스트 49건 통과. 잔여 한계:
  두 분자가 각각 LLM 1회 추정이라 런 노이즈로 근소 역전 가능성은
  남음(체계 편향은 제거).

## 30. 명시 수량 닻에 실측 천장 — LLM 위조 수량으로 인한 쓰기 뻥튀기 차단

- 사고(세션 9ede454a, 외부 대조로 발견): LLM이 세션 요약의 [조사 자료 규모]
  1,419단어를 할일 카드의 "분량" 칸에 옮겨 적음 → derive_anchors가 explicit
  으로 신뢰 → apply_anchors가 양방향 목표로 draft 26→1,419 확대 → 26단어
  답변 세션이 req 82.9분(rec 11.3분의 7.3배)으로 계산. 불변식(§29) 위반의
  남은 최대 구멍.
- 원인: 명시 수량 신뢰는 staged 설계 가정("사용자가 요구사항에 적은 분량 +
  증거 연결")인데, single 모드의 todos.quantities는 LLM이 내부 정리한
  값이라 신뢰 근거가 다름에도 같은 등급을 받았고, 우선순위가 실측 상한보다
  높아 상한이 발동 기회조차 없었다. 프롬프트 조항("기록에 적힌 숫자만")은
  1,419가 실제로 기록에 적힌 숫자라 못 막음.
- 조치: 쓰기 실측(artifact_words, 없으면 answer_words)이 존재하면 명시
  수량도 그 실측을 못 넘는다 — 초과분은 실측 상한(measured)으로 강등.
  명시의 정당한 역할(AI 장황함을 요구 분량으로 끌어내림)은 유지, 위쪽만
  차단. 실측이 둘 다 0일 때만 명시 단독 신뢰(기존 계약).
- 검증: 사고 재현 모의(가짜 1,419 명시 + 실측 26) 70.95분 → 1.3분.
  단위 테스트 신규 2건 포함 59건 통과. session-api 픽스처(명시 2000 vs
  실측 60)는 새 계약(60 상한)으로 갱신 — 픽스처 자체가 위조 시나리오였음.

## 31. 쓰기 순계 재생 — 위임 왕복(만들어보고 고치기)을 코드가 직접 제거

- 지적: 읽기는 코드가 헛짓을 식별해 빼는데(3등급), 쓰기 왕복("1차로
  만들어보게 하고 보면서 고치게 하기")은 LLM 프롬프트 순응에만 기대고
  실측 천장조차 Edit 누적이라 왕복이 천장에 포함 — 비대칭.
- 원리: 읽기와 동일 — **결말에 살아남은 단어만 노동이다.**
- 구현 (`collect_record_stats`, LLM 0회 결정론):
  - 세션이 만든 파일(Write 기점): Write/Edit 순서열을 실제 재생해 최종본
    복원 — 만들었다 갈아엎은 왕복은 자동 0. 사전 검증: 실세션 15개
    프로토타입에서 편집 재생 성공 66/66(100%), 왕복 8~10% 실측.
  - 기존 파일(Edit 기점): 바탕이 없어 정확 재생 불가 — 이후 편집 원문이
    앞서 써넣은 문구와 포함 관계면 덮어쓰임으로 폐기(부분 겹침은 놓치는
    보수적 근사, 천장이 후한 방향이라 안전).
  - 실패한 편집(tool_result is_error) 제외 — 종전엔 적용 안 된 new_string도
    세고 있었음. MultiEdit edits 배열 지원(종전 누락). 삭제(new="")도 반영.
  - §28 분할 의미 개정: draft = 생성 파일 순계(새 문서 완성), edit = 기존
    파일 순계(기존 문서 수정) — "Write=draft/Edit누적=edit"보다 사람 직관
    (신규 작성 vs 수정)에 정합.
- 적용 범위: 파일로 남는 작업 전반(코드·문서·보고서 동일 메커니즘).
  대화 보고는 answer_words(마지막 답변 = 순계 프록시)가 담당. 사각:
  Bash 경유 파일 생성, MCP 갱신 도구로 고치는 외부 산출물(지라 등).
- 한계: 살아남은 수정이 "AI 탓 왕복"인지 "사람도 했을 퇴고"인지는 재생으로
  구분 불가 — 그 판단은 할일 중간층 몫. 왕복 제거의 주력은 여전히 할일
  중간층이고, 본 장치는 천장을 정직하게 만드는 층.
- 검증: 재생 수기검산 테스트(생성 70/기존 5/실패 제외), 5종 스위트 50건
  통과. 실세션 재확인: d519b9b8 기록 6,021→순계 4,795(왕복 20% 제거).

## 32. record-actions w/o LLM API — 분자까지 LLM 0회 + 휴먼화 대조 옵션

- 신설: `session-api/record_actions_code_api.py` — 분자·분모 모두 코드 실측,
  완전 결정론. LLM의 잔여 역할(행동 종류 선택)을 고정 규칙으로 치환:
  read=항해 구조 환산, draft/edit=순계(§31, 파일 없으면 대화 보고),
  search/execute/verify=흔적 있으면 각 1건(seed).
- 대조 옵션 `humanize=False`(CLI `--raw`): 읽기 등급·쓰기 번복 소거를 끈
  옛 자(검토 전량 정독 + Write 마지막 판/Edit 누적). 건수형 규칙은 동일 —
  두 모드 차이 = "읽기 항해 구조 환산 + 쓰기 번복 소거"의 순효과.
- 이 PC 실세션 115개 전수 실행 (제외 25 초소형, 실패 0, 측정 90):
  - 휴먼화 ON : human 합산 19,961분, 전체효율 1.55x (세션 중앙값 1.98x)
  - 휴먼화 OFF: human 합산 25,186분, 전체효율 1.95x (중앙값 2.13x)
  - **휴먼화 기능이 사람 견적 21%를 걷어냄** — 없으면 효율이 26% 과대
    (1.95x vs 1.55x). AI가 헤맨 만큼 사람도 헤맸다고 치는 과대가 그 크기.
- 한계: 건수형 각 1건은 seed(판단 깊은 세션 과소 — 미해결 4와 동일 축).
  req-actions의 LLM 대체는 아님 — 의도·스코프 판단은 자연어라 코드 불가.
- 테스트: 켬/끔 대소·결정론·전용 API 계약 (test_record_actions_code_api).

## 39. rawrecord 모드 — 궤적 재연 자 + 3모드 비교 리포트

- `record_actions_code_api`에 humanize="rawrecord"(CLI --rawrecord) 추가:
  읽기·쓰기 원량(OFF와 동일)에 더해 **행동 횟수까지 세션 기록 그대로**
  (search=검색 호출 수, execute=실행 호출 수; verify는 기록에 대응 행동이
  없어 미계상) — "AI가 한 행동을 사람이 똑같이 했다면"의 자. 기본 동작
  불변(옵션을 몰라도 종전과 동일).
- 전 세션 리포트가 3모드 비교로 확장: ON/OFF/RAW 평균표(OFF−ON =
  읽기·쓰기 휴먼화 효과, RAW−ON = 휴먼화+궤적 상속 총효과), 효율 병기,
  디테일 표 RAW 열 추가.
- 실측(91세션): ON 221.2분 / OFF 278.9분 / RAW 435.6분 —
  RAW−ON +214.3분(+97%). 궤적 상속분(RAW−OFF ≈ 157분)이 읽기·쓰기
  휴먼화분(58분)의 2.7배: 행동 횟수 상속이 최대 왜곡원임을 정량 확인.
  효율은 ON 1.81 vs RAW 2.41 — 궤적 자로 재면 AI가 33% 더 잘해 보인다.

## 40. 휴먼화 옵션 2축 재편 — humanize_rw + humanize_act

- 재편: 단일 humanize(True/False/"rawrecord")를 직교 2축으로 —
  humanize_rw(읽기·쓰기: 등급 분해+번복 소거) / humanize_act(행동 건수:
  "흔적 있으면 1건"; OFF = 로레코드, 행동 횟수를 세션 기록 그대로).
  기본은 둘 다 ON(종전 기본과 동일 동작). act OFF가 구 rawrecord.
- 호환: measure(humanize=...) 구 인자·CLI --raw/--rawrecord 그대로 동작,
  반환에 humanize_rw/humanize_act 병기 + 구 표현("humanize") 유지.
  CLI 신규 --norw/--noact. 테스트로 신구 동등성 고정.
- 리포트 라벨 2축 표기로 갱신. 91세션 재실행 결과 종전과 동일
  (ON 221.4 / rw OFF 279.2 / 로레코드 435.9분).

- §42: 전 세션 리포트가 휴먼화 2축 4조합(rw×act)을 기본 출력 — 요약표,

  act 160.0min / rw 58.0min / 총 +98%.

## 46. 행동 순계 — act ON의 "흔적 있으면 1건"을 구조 분해로 교체

- 문제: act ON이 건수형(search·execute)을 무조건 1건으로 눌러 — 기여
  대상이 여럿인 세션에서도 검색·실행이 각 1건. 읽기(3등급)·쓰기(순계)가
  받은 구조 분해를 행동만 못 받았다.
- 교체(read/write 원리의 행동판, LLM 0회·결정론·임의 상수 0개):
  - 검색 = **착지-기여 문서당 1건** (신호④∩DEEP 재사용). 쿼리 다듬기
    (항해 검색)는 그 1건의 요율에 흡수 = 훑기 소액의 행동판, 착지 없는
    검색은 자동 0 = 헛읽기 0의 행동판.
  - 실행 = **정규화 명령 신원당 1건** (공백 압축 앞 120자 — 조회형 canon
    규약과 같은 눈금). 같은 명령 반복(편집→재실행 왕복)은 신원 1개로
    접힘 = 쓰기 순계 "살아남은 판만 노동"의 행동판. 명령이 조금 다른
    재시도는 각각 셈 — 덜 깎는 보수적 근사(§31과 같은 방향).
- 클램프: 하한 max(1,·) — 흔적 있으면 최소 1건(구 바닥값과 동일),
  상한 min(·, 호출 수) — 항목별 ON ≤ OFF 단조성 유지(§43 교훈).
  역전 불가를 구조로 보장.
- 수집부: collect_record_stats에 search_landing_docs(신호④∩기여),
  exec_net_calls(명령 신원 수) 추가 — 기존 키 불변.

## 47. 셸 속 검색·읽기 재분류 — 실행 축의 어휘 오염 제거

- 발견(§46 후속 실측): 실행 신원 상위가 grep -n 396종·sed -n 302종 —
  실행 축에 쌓인 건 반복 실행이 아니라 **셸로 한 검색·읽기**였다.
  신원을 굵게(앞 2토큰) 잡는 압축안은 기각 — 85% 압축의 정체가
  `cd 프로젝트 &&` 접두어와 grep 어휘가 만든 가짜 동일성(다른 일을
  같은 일로 오인)임을 실측으로 확인.
- 수리: classify_shell_command(§47) — Bash/PowerShell 명령을 &&·||·;·|
  조각별 첫 동사로 판정해 제 축으로:
  - 검색 동사(grep·rg·find·ls·where…) → 검색 축: 탐색 신호(④)로 착지
    로직 적용 — 이미 검증된 81~83% 압축이 셸 검색에도 작동.
  - 읽기 동사(sed·cat·head·tail·awk…) → 조회형 읽기(§27 경로): 결과
    본문 50단어↑면 읽기로 확정, 3등급 분해·재방문·착지 동일 적용.
  - 나머지·파일 리다이렉트(>)·히어독(<<)·sed -i → 실행 잔류 —

## 49. hitl 검토 리뷰 반영 — 코드 검토 에피소드화·강등 시점 보정·민감도 병기

외부 리뷰(session-api/review.md) + 자체 재검토의 종합 반영. 대상은 분모의
사람 감독(hitl) 산정(transcript_actual.py).

- **코드 검토 에피소드화**: 기본 "돌려 확인" 2.0분을 파일당 → 세션 검토
  에피소드당 1회로. 추가 파일은 맥락 이동 비용 0.3분/파일
  (code_extra_min_per_file). 근거: 파일당 고정비는 같은 500줄 변경도
  1파일이면 2분, 10파일이면 20분 — 에이전트 성능이 아니라 저장소의 파일
  분할 방식이 hitl·speedup을 좌우하는 편향. modern code review 연구는
  review를 파일이 아니라 change 중심 활동으로 다룸. 완전 균일 1회는 반대로
  과소라 파일당 소액 증분으로 파일 수 단조성 유지 — hitl 대체로 감소.
- **검증 위임 강등 보정 2건**: ① 강등은 에피소드 기본비에 적용(파일 수
  곱 제거). ② 마지막 테스트 결과 **이후 수정된** 파일은 검증 안 된
  상태이므로 검증 분율((n_code−dirty)/n_code)로 강등 폭을 깎음 — 사건
  순번(code_write_seq vs last_test_seq)으로 결정론 판정.
- **결론 승격 문턱**: 5단어 미만 짧은 이어가기 지시("계속해")는 직전
  답변을 결론(정독)으로 승격하지 않음 — 중간 보고 정독 과금 오차 제거.
  세션 마지막 답변은 문턱 무관 결론. 트레이드오프: 짧은 승인 직전의 진짜
  결론도 훑기로 강등(과소 방향) — 문턱은 seed.
- **correct 재정의**: interrupt당 4.0분은 "끊고 다시 방향 잡는 재정향
  추가 비용"으로 명문화(새 지시 작성은 instruct가 별도 계상 — 감지는
  상호배타라 같은 메시지의 중복 과금은 원래 없음. review.md의 "중복
  과금될 가능성" 표현은 이 점에서 부정확). 불확실 요율로 표시, 민감도
  항목. interrupt 직후 첫 지시는 corrective_instructions로 표시만.
  발화형 교정(끊기 없이 말로 바로잡기) 미감지는 한계 문서에 명시 —
  correct 과대 가능성과 반대 방향으로 공존, 순편향 미상.
- **seed 민감도 병기**: 전 세션 리포트에 미보정 seed(review·correct)만
  0.5×/1×/2×로 흔든 전체 효율 표 추가 — instruct(실측 보정)·기계 고정.
- **용어**: "AI 경로의 실제 비용" → "추정 비용" — 동작 카운트는 실측이나
  요율 다수가 seed이므로. 외부 검토 방어용 정직 표기.
- 순효과: 코드 다파일 세션에서 hitl 감소가 지배적 → speedup 상승.
  참값 대비 정확도 단정은 불가(발화형 교정 미감지 잔존) — 민감도 구간이
  그 불확실성을 드러냄.

## 50. 턴 확인 모델 — hitl 검토를 "전량 읽기"에서 "확인 시점 훑기"로

사용자 지적: 사람은 AI 답변을 전량 정독하지 않는다(훑기 + 결론 정독
정도). 그 턴에 시켜서 나온 새 산출물도 다 읽기보다 동작 확인 정도.
§49 에피소드화의 미해결 과제(에피소드 경계의 결정론적 정의)도 이것으로
해소 — **확인 시점 = 실질 지시 턴(5단어+, §49 결론 문턱과 동일 신호)
+ 세션 끝**.

- 확인 시점마다: 대화는 결론 정독 + 진행 훑기(기존 유지). 산출물은
  내용 전량 읽기 대신 ① 구간에 코드 변경 있으면 동작 확인 1회(2.0분,
  확인 시점의 테스트 상태로 §19 강등 — §49 dirty 파일 제외 유지)
  ② 변경된 코드·문서 내용물은 훑기 0.002/단어(공용) ③ 문서·기타
  파일당 표본 확인 0.5분.
- 폐지: 문서 전량 정독(doc_read 0.008/단어 — 최대 과대 원인, 4배 인하
  효과), §49 에피소드 기본비+추가 파일당 0.3(code_extra_min_per_file
  키 제거). report_deep 0.008은 대화 결론 정독 전용으로 존속.
- 방향: 문서형 세션 hitl 큰 폭 감소, 다턴 코드 세션은 확인 횟수만큼
  증가(감독 강도를 실제로 반영 — 밀착 개입 세션 ↑, 방치 세션 ↓).
- 구현: parse_actions가 확인 구간별 코드 변경·테스트 상태 스냅샷을
  code_check_events로 기록, actual_effort_minutes가 사건별 강등 적용.
  구 counts 호환 폴백(사건 목록 없으면 세션 전체 확인 1회 근사).

## 56. think 방법론·근거 가정 문서화 + 실측 수치 갱신

## 59. 번역 누락 5건 수리 — 서브에이전트 편입·실행 4토막·쓰기 종류 분해·
분모 긴 도구 대기·채널 결산

측정의 목표는 **"트랜스크립트를 보고 사람이 그 일을 했다면 얼마나 걸릴지로
번역"**하는 것이다. 이 관점으로 전 채널을 감사해 누락 5건을 찾아 고쳤다.
누락은 **전부 분자를 깎는 한 방향**이었다.

### 규칙 2개 (이걸 어긴 데서 구멍이 났다)

1. **병렬성은 분모만** — "서브에이전트는 병렬이라 실소모 시간에 못 더한다"는
   분모 규칙인데 분자에도 적용돼 있었다. 분자는 사람이고 사람에겐 병렬이 없다.
2. **통로 이름으로 면제하지 않는다** — 글이 Write로 나갔든 Bash 명령문으로
   나갔든 사람은 그걸 다 써야 한다.

### 수리 1 — 서브에이전트를 분자에 편입

`isSidechain` 필터가 세 파서 첫 줄에 있어 서브에이전트 기록이 전부 버려졌다.
`include_subagents=True` 옵션도 무력했다 — 파일을 읽어와도 안의 기록이 전부
사이드체인이라 통계가 0이 된다.

디스크 실측(원시 스캔): 서브 파일 573개·39,787줄, 도구 호출 12,428건
(메인 세션 전체가 13,688건), Write 본문 225,350단어.

- `collect_record_stats(jsonl_path, subagent_paths=None)` — 기본 자동 탐색
  (`{세션}/subagents/*.jsonl`), `[]`로 주면 구 동작.
- 메인+서브를 **시각 순 병합**해 한 스트림으로 재생 — 쓰기 순계가 파일별
  시간 순서열을 재생하므로 순서가 어긋나면 중복이 샌다(순계는 세션 전체에 한 번).
- 서브의 **지시문은 input_words에서, 보고문은 마무리 답변에서 제외** — AI가
  쓴 글을 사람 지시·결론으로 오인하면 안 된다.
- 분모는 그대로 제외(병렬).
- 메인 트랜스크립트에는 사이드체인 레코드가 0줄이라 이중계상 위험 없음(실측).

효과: 서브를 실제로 부린 세션에서 분자 1.5~2.2배, 배율 3.54 → 7.67배(최대).

### 수리 2 — 실행을 4토막으로 (건당 2.0분 폐지)

과금 대상 실행 5,736건의 48%가 즉석 스크립트(heredoc·`python -c`,
건당 평균 97단어)인데 `git status`와 같은 2.0분을 받고 있었다.

```
execute = 명령문 단어×0.05(첫 신원만) + 실측 대기 + 출력 판독(앞 200단어
          정독·나머지 훑기) + 기계 조작(새 0.25 / 재실행 0.1분)
```

- 구성·대기·판독은 전부 트랜스크립트 실측 → **seed가 하나 줄었다.**
- **출력 판독은 종전에 분자 전액 0원**이었다("실행형 도구는 읽기가 아님").
- act OFF(로레코드)는 매 호출을 새 명령으로 — ON ≤ OFF 단조성 유지.
- 재구성 밴드(하한~상한) 대비 종전 2.0분은 **정확히 하한**이었다.

### 수리 3 — 쓰기를 코드·문서·데이터로 분해 + 코드 요율 문헌 유도

실측 구성 코드 44% / 문서 31.5% / 데이터 24.4%가 한 요율(0.05)이었다.

- 코드 **0.08**(=152 LOC/h) — **문헌 유도**: Prechelt(IEEE Computer 2000,
  7개 언어 80개 구현)의 전체 작업 생산성 중앙값 22~31 LOC/h를 Xia et al.
  (IEEE TSE 2018, 개발자 79명·3,244시간)의 편집 시간 분율 13.9~15.3%로
  나눠 순수 편집 144~223 LOC/h → 0.054~0.084. 그 보수적 끝을 채택.
  나눗셈이 필요한 이유: 이해·탐색은 read·think 축이 따로 받으므로 전체
  작업 속도를 쓰기 요율에 넣으면 이중계상.
- 문서 0.05 (Karat 앵커 유지), 데이터 0.01(seed — 사람은 JSON을 손으로
  치지 않고 스크립트로 뽑는다), edit = 같은 종류 × 0.4(종전 비율 승계).
- 데이터 요율은 0.002~0.05로 25배 흔들어도 배율 5.25~5.77 — 영향 미미.

### 수리 4 — 분모에 긴 도구 실측 대기

건당 0.3분 고정은 0.5초 `git status`와 10분 벤치를 같은 값으로 만든다.
**30초 초과분만** 실측으로 가산(짧은 호출의 고정 과금과 겹치지 않게).
실측: 도구 13,798건 중 4.4%(606건)가 문턱 초과, 초과분 합 936분 = 분모의
6.5%. **5개 수정 중 유일하게 배율을 낮춘다.**

### 수리 5 — 채널 결산 (재발 방지)

세션에서 오간 글이 어느 축으로 갔는지 통로별로 결산해 `channel_audit`으로
낸다. 미계상 양이 2,000단어를 넘으면 `notes`에 자백. 이번 감사에서 드러난
미등록 채널: 셸 명령문 359,036단어 · 실행 출력 468,307단어 · 서브에이전트
전량 · 이미지 74개. 결산표가 있었으면 처음부터 보였다.

### 검토했으나 채택 안 함

- **도구 중간 생각 계상** — 실측상 생각 토큰의 74%가 여기 해당하나,
  ① 실행 4토막의 기계 조작분과 겹치고 ② 근거가 없어 보류. 크기는
  `think.mid_tokens`로 보고. 계상 시 전체 배율 +1.7%.

  1.5분은 실측 중앙값보다 낮은 하한. 올리면 +1.3%. 하한 성격 유지로 존치.

## 60. 분모 긴 도구 대기 철회 — 실측 대조로 무효 확인 (§59 수리 4 되돌림)

§59에서 "건당 0.3분 고정은 10분짜리 벤치를 18초로 친다"며 30초 초과분을
분모에 얹었다. **타임스탬프 실측과 대조하니 얹기 전이 더 정확했다.**

대조 방법 — 트랜스크립트에서 AI가 실제로 동작한 구간을 잰다:
사람 발화 직후 첫 레코드 ~ 다음 사람 발화 직전 마지막 레코드. 구간 안의
레코드 간격에 상한(15분)을 걸어 사람이 자리를 비운 정지 구간을 제거한다.
(상한 없이 재면 19,637분인데 그중 12,583분이 방치 시간이다.)

| | machine 합계 | 모델/실측 | 세션별 \|log오차\| | 허용범위(0.5~2.0배) |

## 62. AI 시간을 요율 계산에서 턴 실측으로

분모의 AI 몫을 `tool_calls × 0.3분 + 결과단어 × 0.0005 + 생성단어 × 0.002`로
추정하던 것을 **타임스탬프 실측**으로 바꾼다.

```
AI 시간 = Σ(턴)  [ AI를 깨운 입력 시각 → 그 턴의 마지막 AI 기록 시각 ]
```

- 깨운 입력 = tool_result가 아닌 user 레코드(사람 발화·배경작업 알림·
  시스템 주입·중단). AI 기록 = assistant 또는 tool_result가 든 user 레코드.
- 빼는 것 없음. 상한·계수·모델별 상수 없음.

### 왜 상한이 필요 없어졌나

처음엔 정체 구간 때문에 상한이 필요해 보였다(고정 60초 → 세션 p95 →
중앙값×K를 차례로 시도했고 전부 깨졌다: 표본 부족 25%, p95가 8.5시간이
되는 세션, 앞뒤 절반 3.4배 흔들림).

원인은 상한이 아니라 **엉뚱한 레코드를 세고 있던 것**이었다. 5분 이상 빈
간격 531건을 분해하니 354시간이 `system` 레코드(턴 끝 도장 —
`turn_duration`·`stop_hook_summary`) 뒤에 있었다. 그건 AI가 멈추고 사람을
기다리기 시작한 지점이라 그 뒤 빈 시간은 전부 사람이 자리 비운 시간이다.
도장을 빼니 남은 긴 간격은 최대 10분(도구 타임아웃)뿐이라 상한이 무의미해졌다.

두 번째 함정: 배경 작업 알림(`<task-notification>`)을 "사람 발화 아님"으로
걸러내면 알림이 몇 시간 뒤 와도 그 대기가 한 턴에 들어간다(실측 +2,346분).
**AI를 깨운 것이면 사람이든 알림이든 구간을 끊는다**로 해결.

### 정체를 더 빼지 않는 이유

턴 안의 빈 간격이 턴의 절반을 넘는 15건(262분)을 조사하니 **13건 108분이
진짜 도구 실행**이었다(10분짜리 넷은 Bash/PowerShell 타임아웃). 진짜 빈
대기는 2건 154분, 전체 5,375분의 2.9%. 정체 제거 규칙을 넣으면 얻는 것보다
날리는 것이 많다. 배경 서브에이전트가 도는 중이었는지는 서브에이전트 파일의
시각으로 확인 가능(실측 15건 중 1건 8분).

### 이식성

필요한 필드는 `type`·`timestamp`·`message.content`의 tool_result 여부뿐이고,
`assistant`(28,384건)·`user`(16,434건) 레코드의 timestamp 누락은 **0건**이다.
아는 종류만 세고 나머지는 무시하므로 새 레코드 종류가 생겨도 안 깨진다.
클로드 코드 26개 버전(2.1.215~2.1.233)에서 검증.

### 재측정 (AI 호출 세션 제외 70세션)

| | AI 시간 | 분모 | 전체 배율 | 세션 중앙 |
|---|---|---|---|---|
| 요율 계산(§62 이전) | 6,926분 | 13,603 | 4.43배 | 2.86배 |
| **턴 실측** | **5,375분** | **12,129** | **5.00배** | **4.10배** |

요율 계산은 실측의 1.29배였고 세션별로 1.25~3.94배로 흩어졌다(중앙 2.10배).

## 63. 규모 비례 확인 요율을 코드/문서로 분리

`code_skim_min_per_word` 0.002 하나를 코드·문서에 공용하던 것을 갈랐다.

    코드  0.002 → **0.005**   문서  (신설) **0.0025** = 분당 400단어

### 왜 갈랐나

같은 0.002가 두 대상에서 전혀 다른 뜻이 된다:

| | 뜻 |
|---|---|
| 문서 | 분당 500단어 — 훑기 속도. 말이 된다 |
| 코드 | 줄당 4.94단어라 **시간당 6,073줄** — 말이 안 된다 |

게다가 문서는 `code_run`(동작 확인 2.0분/시점)이 안 붙는다 — 돌려볼 게
없으니. 즉 문서는 이 항 하나가 확인의 전부인데 코드와 같은 값이었다.

### 코드 0.005 — 실측 유도

"코드를 고친 뒤 확인만 한" 짝 233개에서 확인의 사람 환산 비용을 직전 변경
단어로 나눴다:

| 직전 코드 변경 | 짝 수 | 확인 비용 중앙 | 단어당 |
|---|---|---|---|
| 1~200단어 | 46 | 7.5분 | 0.0882 |
| 200~600단어 | 57 | 7.9분 | 0.0214 |
| **600~1,500단어** | **65** | **4.8분** | **0.0050** |
| 1,500~4,000단어 | 49 | 4.6분 | 0.0023 |
| 4,000단어+ | 16 | 3.6분 | 0.0007 |

**실측은 선형 비례를 반박한다** — 변경이 20배 커져도 확인 비용은 7.5분 →
3.6분으로 오히려 줄고, 단어당 값은 100배 넘게 흩어진다. 확인은 "테스트
돌리고 결과 본다"라 규모와 거의 무관한 고정 작업이기 때문이다(문헌의
"고정비 + 체감"과 같은 방향, §59 참조).

그럼에도 선형을 유지한 것은 설계 결정이다(로그 형태는 채택 안 함). 계수는
표본이 가장 많은 구간(600~1,500단어, 65짝)의 중앙 0.0050을 골랐다. 고정비
몫은 `code_run` 2.0분/시점이 이미 받으므로 이 항은 그 위의 증가분이다.

### 문서 0.0025 — 정독의 2배 속도

분자 정독(human.read 0.005 = 분당 200단어)의 2배인 분당 400단어. 문서
검토는 정독이 아니라 의도와 맞나 훑어보는 것이라는 판단. 문서 단어가
189,198개라 영향은 작다(0.002→0.0025 시 +95분, 전체 효율 4.98→4.94배).

## 65. AI 시간 실측에 간격 상한 10분 — 방치가 통째로 흡수되던 결함 수리

잡혔다. `session_span_min` 13,139분의 91%다.

## 66. 요율 문헌 정합(훑기 450 wpm·수정 40 wpm) + Edit 변경 단어 기준 + 총량 분류를 파일 출처로 — 쓰기 ON>OFF 역전 16세션 해소

### 배경 — 휴머나이즈 켬/끔 감사에서 나온 세 가지

1. **쓰기 항목 ON > OFF 역전 16/55세션.** 세션이 Write로 만든 파일을 Edit로
   키우면, 순계(ON)는 최종본 전체를 신규(draft 1.0)로, 총량(OFF)은 도구명
   기준으로 Edit 몫을 수정(×0.4)으로 쳐서 OFF가 더 작아졌다. 예:
   `Write "a b" → Edit b→"b c"` = ON 3×1.0 > OFF 2×1.0 + 2×0.4. 같은 파일을
   두 모드가 다른 원리로 분류한 것이 원인이며, 휴머나이즈 축의 결함이 아니라
   **OFF 총량의 분류 결함**이다.
2. **Edit new_string의 31%가 앵커.** Edit 도구는 위치를 찍기 위해 바꾸지 않는
   줄도 old·new에 같이 싣는다(3,111건 239,342단어 중 74,294단어). 사람은
   편집기에서 그 줄을 다시 치지 않는데 양 모드 모두 수정 단어로 세었다.
   Edit 3,111건 중 순수 추가(old 단어를 하나도 지우지 않음) 24%, 교체 75%,
   삭제 1%.
3. **요율 근거.** 훑기 0.00025(=4,000 wpm)는 사람 읽기 속도로 방어가 안 되어
   "5% 비용 등가" 해석에 의존했고, 수정 0.02(=50 wpm)는 text-entry 타이핑
   앵커라 편집 과정 측정이 아니었다. `edit_factor 0.4`는 종전 비율 승계로
   근거 없음.

### 수리

- **`edit_delta(old, new)`** (requirement_actions.py): 단어열 diff로 3단어
  이상 연속 일치를 앵커로 빼고 `(added, removed, anchor)` 반환.
  `removed == 0`이면 순수 추가.
- **순계(ON)**: 기존 파일 분기가 new_string 전량 대신 `added`를 계상하고,
  순수 추가는 `out_draft`로 분류(종전 전량 `out_edit`). 생성 파일 분기는
  최종본 재생 그대로(앵커는 원래 안 들어갔다).
- **총량(OFF)**: 분류를 도구명 → **파일 출처** 기준으로. 세션이 만든 파일의
  Edit `added`는 draft, 기존 파일은 순수 추가 → draft / 교체 → edit.
  `gross_draft_by_kind`·`gross_edit_by_kind` 신설, rw OFF 분기의 전역 share
  비율 분배(종류 무관 희석, 그 자체로 −922분 과대) 폐지. `gross_write_by_kind`는
