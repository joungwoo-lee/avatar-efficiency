# §87 AI 시간(ai_wall_min) 재정의 — 방치만 빼고 일한 시간은 끝까지

## 기준

agent_min = **전체 러닝타임 − 방치 시간 − 사람이 쓴 시간** + hitl(횟수 × 요율).
입력은 트랜스크립트(메인 + 서브에이전트 jsonl)뿐.

## 현행(§65·§84)의 문제 — 이 PC 174세션 실측

기록 간격마다 10분 상한(`_AI_GAP_CAP_SEC`)을 일괄 적용한다. 상한이 막던 것과
잘못 자르던 것이 섞여 있었다.

| # | 문제 | 실측 |

## 규칙

- **R0 중복·역행**: `uuid`가 이미 나온 레코드는 통째로 건너뜀. 시각이 직전 AI
  시계(`turn_prev`)보다 이르면 간격 0, 시계는 뒤로 안 감.
- **R1 경계**: 도구 결과가 아닌 `user` 레코드는 `isMeta`·`isCompactSummary`도
  구간 경계 — 그 앞 공백은 AI 시간 아님(지시로는 안 셈, 기존대로).
- **R2 답 생성**: 직전 AI 시계 → assistant 레코드 간격은 **상한 없음**.
  단 `message.model == "<synthetic>"`은 AI 답이 아님 — 간격 미가산.
  `system` 레코드(api_error 재시도 등)는 시계로 안 씀 → 서버 과부하 재시도
  대기도 끝까지 들어간다.
- **R3 도구 대기**: 정상 결과(`is_error` 아님) + 제한 없는 도구 → **상한 없음**.
  상한 유지(10분): Claude Code가 실행 시간을 막는 도구(Bash·PowerShell·
  TaskOutput 등)·즉시 끝나는 파일 도구(Read·Edit·Write·Grep·Glob 등)
  — 이들이 10분 넘게 걸렸다면 방치·승인 대기뿐. 사람을 기다리는 도구
  (AskUserQuestion·ExitPlanMode)와 오류 결과도 상한 유지.
  승인 대기는 결정대로 최대 10분 포함(트랜스크립트에 승인 시각 없음).
- **R4 배경 대기**: 알림 `<status>completed</status>` → **상한 없음**.
  감시(Monitor) 이벤트 알림(`<status>` 없이 `<event>`) → **상한 없음**(§88 정정,
  아래). failed·killed·stopped → 10분 상한 유지. 이미 종료 알림을 받은
  task-id의 종료 알림 재도착은 대기 0(§93 정정, 아래). failed는 실측상 사용량
  한도로 5초 만에 멈춘 서브에이전트의 알림이 238분 뒤 도착한 사례가 있어
  일한 시간이 아님.
- 기록 간격을 이어 붙이는 구조는 그대로 → 같은 순간을 두 번 세지 않는다.

## 알려진 한계

- 사람에게 묻는 권한 설정에서 제한 없는 도구의 승인 대기가 10분을 넘고 정상
  결과로 끝나면 그 대기가 전부 들어간다(트랜스크립트로 구분 불가).
- 답 생성 중 PC 절전 등으로 끊긴 시간은 구분 불가 — 들어간다.

## 시험

기존 시험 전부 + 규칙별 시험(R0~R4) 추가. 174세션 현행/§87 비교.

## 정정 §88 (2026-09-28) — 감시(Monitor) 이벤트 알림은 상한 없음

리뷰에서 발견. §87 R4가 "상태 없음"을 failed·killed·stopped과 한 묶음으로
10분 상한에 두었는데, 이 PC 실측에서 `<status>` 없는 알림 62건은 **전부**
`Monitor` 도구의 진행 이벤트(`<event>`)였고 종료·타임아웃 알림은 0건.
AI가 걸어 둔 감시 대상(학습 실행·일괄 적용)이 돌던 시간이므로 기준(전체
러닝타임 − 방치 − 사람 시간)상 방치가 아니다. R4를 "completed 또는 `<status>`
없이 `<event>`가 있는 알림 → 상한 없음"으로 고침. `<status>`도 `<event>`도
없는 알림은 상한 유지.

- 영향(이 PC 전 세션): AI 시간 +180분(+1.8%), 바뀐 세션 2개 — 5d38d92b
  94.6 → 271.3분, b6dcc2fd 140.2 → 143.4분.
- 근거 검증: Claude Code 자체 `system/turn_duration`(durationMs)과 턴별
  대조 2,894턴 중 97%가 0.5분 이내 일치 — 간격 합산 방식 자체는 맞고,
  배경 대기를 세는 방향도 Claude Code 계측과 일치.
- 위 시뮬레이션 표의 수치는 CHANGELOG §87 최종치로 맞춤(초안 임시 복사본
  수치 9,554/16,645/6.57/84.78/84.60 → 9,559/16,651/6.58/84.79/84.62).

## 정정 §93 (2026-10-07) — 이미 끝난 작업의 완료 알림 재도착은 대기가 아니다

외부 보고로 발견. §87 R4가 `completed` 알림 앞 대기를 상한 없이 세면서, "완료
알림이 왔다 = 그때까지 작업이 돌았다"고 가정했다. 세션을 며칠 뒤 다시 열면
이미 끝난 작업의 완료 알림이 **다시** 온다. 새 기록(새 uuid)이라 R0이 못 거르고,
§84 때는 10분 상한이 가려 주던 것을 R4가 풀면서 드러났다.

- 보고 사례: 09-04 07:28 배경 서브에이전트 실행 → 07:31 완료 알림. 07:36 이후
  메인·서브 모두 활동 없음. 09-08 05:57 세션 재개 때 같은 task-id 완료 알림이 또
  옴 → 그 앞 약 4일이 AI 시간으로 잡힘(시험 재현: 7분이어야 할 것이 5,698분).
- 규칙: 종료 알림(`<status>`가 running·pending 아님)을 이미 받은 task-id의 종료
  알림은 대기 0 — 구간 경계로만 쓴다. 감사용 `bg_dup_events`·`bg_dup_skip_min`.
- 예외(정상 대기): 그 사이 메인이 `SendMessage`(`to`)·`Agent`(`resume`)로 그 작업을
  다시 돌렸으면 다음 종료 알림은 R4대로 센다. `to`가 이름이면 `Agent` 입력 `name`
  → 결과 `agentId`로 맞춘다. 보고자 제안("같은 task-id 두 번째 이후 완료 알림은
  안 센다")만으로는 이 정상 사례를 자른다 — 이 PC에서 같은 서브에이전트가 2~3번
  완료된 3건(a48273ca…·ab4eba7a…·af242255…)은 전부 그 사이 `SendMessage`가 있었다.
- 영향(이 PC 391파일): AI 시간 11,341.4분 → 11,341.4분, 재도착 0건 — 수치 불변.
- 한계: 감시(Monitor) `<event>` 알림의 재도착은 새 이벤트와 구분할 표지가 없어
  다루지 않는다(보고·실측 사례 없음).
