# §94 긴 대기 안전장치 — 10분을 넘는 부분은 증거가 있는 만큼만

## 문제

§87은 "방치가 섞일 수 있는 간격"에만 10분 상한을 남기고, 답 생성(R2)·제한 없는
도구의 정상 결과(R3)·배경 작업 완료와 감시 이벤트(R4, §88)는 상한 없이 센다.
이때 "완료 알림이 왔다 = 그때까지 작업이 돌았다"처럼 **신호를 그대로 믿었고,
신호를 확인하는 장치는 두지 않았다.**

그래서 모르는 경우가 하나 생기면 그 간격 전체가 샌다. §93 사례가 그랬다 — 이미
끝난 서브에이전트의 완료 알림이 세션 재개 때 다시 오자 4일(5,698분)이 AI 시간에
들어갔다. §93은 그 경우 하나만 막았다.

사람 쪽도 같은 구멍이 있다. §91은 MCP 등 포그라운드 도구의 정상 결과 대기를 AI
쪽 R3와 같은 규칙(상한 없음)으로 센다.

## 원칙

**기본은 10분 상한. 10분을 넘는 부분은 "그 시간에 AI가 시킨 일이 실제로 돌고
있었다"는 별도 기록(증거)과 겹치는 만큼만 센다.**

    센 시간 = max( min(간격, 10분), 간격 중 증거 구간과 겹친 길이 )

- 모르는 경우가 생겨도 간격 하나에서 새는 시간은 최대 10분이다(§87 이전 상한과 같다).
- 정상 작업은 증거가 있으면 §87처럼 끝까지 센다.
- 증거가 틀려도 그 증거의 길이까지만 샌다.

## 증거 (이미 있는 기록만 — 새 수집 장치 없음)

| # | 증거 | 구간 | 덮는 것 |
|---|---|---|---|
| E1 | Claude Code 턴 시간 기록 `system/turn_duration` | [기록 시각 − `durationMs`, 기록 시각] | 답 생성·포그라운드 도구 |
| E2 | 서브에이전트·워크플로 종료 알림의 `<duration_ms>` (`user`·`queue-operation`) | [알림 시각 − duration, 알림 시각] | 배경 서브에이전트 대기 |
| E3 | 포그라운드 `Agent` 결과 `toolUseResult.totalDurationMs` | [결과 시각 − duration, 결과 시각] | 포그라운드 서브에이전트 대기 |
| E4 | 배경 실행 판정기(§89 `BackgroundExecTracker`)의 정상 완료·감시 이벤트 구간 | [띄운 시각, 가장 이른 완료 신호] | 배경 명령·감시 대기 |
| E5 | 배경 서브에이전트 실행 구간 | [띄운 시각(`toolUseResult.isAsync`의 `agentId`) 또는 `SendMessage` 재개 시각, 가장 이른 종료 신호] | `duration_ms` 없는 서브에이전트 알림 |

증거는 메인 기록에서만 모은다. 여러 증거 구간은 합집합으로 쓴다(같은 순간을 두 번
세지 않는다).

## 이 PC 실측 (391파일, 설계 근거)

- 10분 넘게 상한 없이 센 간격 37건 — R4 34건(1,110.1분), R3 1건(10.2분), R2 2건(27.7분).
- E1(턴 시간 기록)은 배경 **명령** 대기를 덮지 않는다(겹침 0). 서브에이전트 대기는
  덮는다. 턴 시간 기록이 아예 없는 세션도 많다. → E1 하나로는 부족해 E2~E5를 둔다.
- 서브에이전트 R4 긴 대기는 전부 `duration_ms` ≥ 대기(예: 대기 59.3분 / 실행 59.4분,
  34.1 / 63.9). E2가 정상 작업을 자르지 않는다.
- 포그라운드 `Agent` 10.2분 = `totalDurationMs` 10.2분(E3).
- 배경 명령 대기(5시간 야간 배치 등)는 알림에 실행 시간이 없다 → E4로 덮는다.

## 적용 범위

- 분모(`parse_actions`): R2·R3·R4(완료·감시 이벤트)에서 10분을 넘는 간격. 간격을 셀
  때는 10분만 넣고 간격을 보관 → 파일을 다 읽은 뒤 증거와 겹친 만큼 더한다(턴 시간
  기록은 턴이 끝난 뒤에 나오므로).
- 분자(`collect_record_stats`): §91 포그라운드 도구 대기에서 10분을 넘는 부분 — 같은
  증거·같은 식. §89 배경 실행 구간은 이미 E4 자체(띄운 시각 → 가장 이른 완료 신호)라
  불변. Bash·PowerShell·`TaskOutput` 등 제한 도구는 원래 10분 상한이라 불변.
- 증거 판정은 `transcript_actual.py`의 공용 판정기 하나(`WaitEvidence`)로 양쪽이 같이 쓴다.
- §93(이미 끝난 작업의 종료 알림 재도착 = 대기 0)은 그대로 둔다.

## 감사 출력

- `long_gaps`: 10분 넘는 간격마다 {종류(R2·R3·R4), 시작, 끝, 간격 분, 증거 겹침 분, 센 분}.
- `unproven_cut_min`: 증거가 없어 잘린 시간 합.

## 남는 구멍

- 감시(Monitor)를 `persistent`로 띄우면 판정기 구간(E4)이 이벤트마다 이어져, 세션 재개
  때 이벤트 알림이 다시 오면 증거로 잡힌다(보고·실측 사례 없음). `timeout_ms`는 22건 중
  17건이 `persistent`라 상한 증거로 못 쓴다.
- 증거 자체가 틀린 경우(재전달 알림에 실린 `duration_ms` 등)는 그 길이까지 샌다.

## 시험

- 보고 사례: §93 없이도 4일 → 10분 이하(증거 없음), §93과 함께 0.
- 증거 없는 25분 답 생성 → 10분. 턴 시간 기록이 덮으면 25분.
- 포그라운드 MCP 60분: 턴 시간 기록 있으면 60분, 없으면 10분 — 분자·분모 같은 값.
- 배경 명령 5시간(E4) → 끝까지. 띄운 기록 없는 알림 → 10분.
- 서브에이전트: `duration_ms` 있음 → 그 길이까지, 없으면 E5 구간.
- 기존 시험 전부 통과(R2·R3 시험은 증거를 넣어 같은 값 확인).

## 구현 결과·검토 (2026-10-07)

구현하면서 위 설계에서 바뀐 점과 §87~§93 기조 검토 결과. 상세 표·수치는 CHANGELOG §94.

### 증거 조건 (설계에서 바뀐 점)

- 증거 시각은 그 일이 끝난 순간에 붙인다. E2(`duration_ms`)는 그 실행의 **첫** 종료 신호(보통 완료
  순간의 `queue-operation`)에만 붙인다 — 사용자 기록으로 늦게 배달되거나 재도착한 알림에 붙이면
  쉬던 시간대를 덮는다(공격 시험: 본문 다른 재도착이 25.5분까지 샘).
- E5(띄운·재개 시각 → 첫 완료 신호)는 E2가 없을 때만. 띄운 것과 끝난 것만 확인되고 그 사이 계속
  돌았는지는 모른다 — 실행 시간 기록이 있으면 그쪽(짧은 쪽)을 쓴다.
- E1(턴 시간)은 답 생성(R2)에는 쓰고, 도구 대기(R3·분자 §91)에는 그 동안 승인 창이 안 뜨는 권한
  모드(`bypassPermissions`·`dontAsk`)가 기록(`permissionMode`)으로 확인될 때만 쓴다. 배경 대기(R4)에는
  안 쓴다. 턴 시간은 승인 창에서 사람을 기다린 시간도 담기 때문이다.
- 장부 하나: `WaitEvidence`가 배경 작업의 시작·재개(`SendMessage`·`resume`, `Agent` 이름 대응)·종료·
  재도착과 메인 도구 대기 상태를 모두 추적한다. §93이 따로 하던 추적은 없앴다.

### 0으로 빼는 경우 — 확인 신호가 있을 때만

| 경우 | 확인 신호 | 확인 안 되면 |
|---|---|---|
| 쉬던 중에 온 깨운 입력(R1) 앞 공백 | `isMeta` + AI가 답을 끝냄 + 기다리는 도구·돌고 있는 배경 실행·서브에이전트 없음 | 10분 + 증거 |
| 이미 끝난 실행의 종료 알림 재도착(§93) | 같은 task-id·같은 본문, 그 사이 재개 없음 | 10분 + 증거 |
| 세션 이어 붙이기용 가짜 답 앞 공백 | `<synthetic>` + 본문 "No response requested." | 10분 + 증거(API 오류 답 등) |

압축 요약은 경계가 아니다 — 요약이 있다는 것 자체가 그 앞에서 AI가 압축하던 증거다.

  간격 두 개라 21분 이하).
