# diff-effort — 코드 라인 변경수 → 사람 노동 환산

`diff` 의 추가/삭제 라인 수만 가지고 "사람이 직접 짰다면 몇 분"을
환산하는 독립 모듈. 세션 트랜스크립트가 없을 때 쓴다.

```
python diff_effort.py 320 180
python diff_effort.py 20 400 --all-bands
python diff_effort.py 0 1200 --file-deleted 1200 --json
```

```python
from diff_effort import diff_effort
diff_effort(added=320, deleted=180)["minutes"]   # 724.5
```

## 1. 수식

```
부분삭제 = 삭제 − 파일통째삭제
순삭제   = max(0, 부분삭제 − 추가)

분 = 추가     × 2.26
   + 순삭제   × 1.30
   + 파일통째삭제 × 0.025
```

| 항 | 분/줄 | 줄/시간 | 뜻 |
|---|---|---|---|
| 작성 (`W_new`) | **2.26** | 26.5 | 코드를 짜는 전체 노동 |
| 삭제 (`W_del`) | **1.30** | 45.7 | 지울 코드를 이해하는 노동 |
| 폐기 (`W_scrap`) | 0.025 | 2,430 | 파일 통째 버리기 (읽지 않음) |

## 2. 근거

### 2.1 작성 2.26분/줄 — Prechelt [R8]

Prechelt 의 7개 언어 80개 구현 비교는 소스 생산성 중앙값을
**22~31 non-comment LOC/시간**으로 보고한다. 이 값은 **설계·작성·시험을
다 포함한** 전체 작업 시간 기준이다.

```
26.5 줄/시간 (밴드 중앙)  →  60 ÷ 26.5 = 2.26 분/줄
```

상식 대조: 하루 8시간이면 176~248줄/일. 업계 통념(하루 100~200줄)과
같은 크기다.

### 2.2 삭제 1.30분/줄 — Prechelt ÷ Xia 이해분율 [R8][R9]

지우는 일은 치는 일이 아니라 **이해하는 일**이다. 지워도 되는지
확인해야 지운다. Xia et al. 의 현장 연구(전문 개발자 79명, 3,244
작업시간)는 시간 배분을 이렇게 측정했다:

| 활동 | 비중 |
|---|---|
| 이해(comprehension) | ~58% |
| 탐색(navigation) | 18.4~22.5% |
| 편집(editing) | 13.9~15.3% |

전체 작업 속도를 이해 분율로 나누면 이해만 할 때의 속도가 나온다:

```
26.5 ÷ 0.58 = 45.7 줄/시간  →  60 ÷ 45.7 = 1.30 분/줄
```

### 2.3 파일 통째 폐기 0.025분/줄 — seed

파일이 통째로 사라진 삭제는 줄을 하나씩 판단한 게 아니다. 훑기 수준의
seed 값이며 **문헌 근거가 없다.** 영향이 작아서(1,200줄 삭제 = 30분)
정밀화 우선순위가 낮다.

### 2.4 순삭제 = max(0, 부분삭제 − 추가) — 교체 쌍 제거

`git diff` 는 한 줄을 고치면 `+1 / −1` 쌍으로 잡는다. 추가와 삭제를
둘 다 과금하면 **타이핑 한 번을 두 번 센다.** 그래서 겹치는 만큼을
빼고, 남은 순삭제만 삭제 요율로 받는다.

파일 통째 삭제는 대응하는 추가가 없으므로 이 쌍 제거에서 제외한다.

### 2.5 왜 규모에 정비례(선형)로 두나

줄 수가 늘면 줄당 비용도 늘어난다는 관측이 있다. Boehm 의 COCOMO II
는 공수를 `Effort = A x Size^E` 로 두고 지수 `E = 0.91 + 0.01 x SF합`
으로 계산하는데, 실무 범위에서 **E 는 1보다 크다(대략 1.01~1.26)**.
규모가 두 배면 공수는 두 배 넘게 든다는 뜻 — **규모의 불경제**다 [R11].

그런데 그 초선형의 실체는 **코드가 커져서**가 아니라 **사람이 여러
명이라서** 생긴다. Brooks 는 이를 의사소통 경로로 정식화했다: 인원 n
명이면 경로가 `n(n-1)/2` 개로 **제곱에 비례해** 늘어난다 [R12].
COCOMO II 의 지수를 밀어 올리는 척도인자(SF) 목록 자체가 그 증거다 —
`TEAM`(팀 응집도), `PMAT`(조직 프로세스 성숙도), `ARCH`(아키텍처
선행 해소), `PREC`(선례 없음). **전부 여러 사람이 같이 일할 때만
의미가 있는 항목**이고, 코드 자체의 성질이 아니다 [R11].

즉 대형 프로젝트 데이터에서 뽑은 초선형 계수는 **다인 협업
오버헤드**를 규모의 함수로 옮겨 적은 값이다.

이 모듈이 쓰는 Prechelt 의 값은 그런 데이터가 아니다. **개별 참가자가
같은 사양의 프로그램을 각자 혼자 구현한 80개 구현**의 생산성이다.
협업 오버헤드가 애초에 들어 있지 않다.

재는 대상도 마찬가지다. 이 모듈의 입력은 하나의 diff — **한 주체(사람
한 명 또는 에이전트 하나)가 만든 변경**이다. 인원이 늘어서 생기는
오버헤드가 발생할 자리가 없다.

**요율과 대상이 둘 다 단독 작업이므로 규모에 정비례로 둔다.** 초선형
계수를 얹으면 이 diff 에 존재하지 않는 협업 비용을 과금하게 된다.

덧붙여, Prechelt 자신이 이 데이터에서 "시간당 줄 수는 언어와 무관"이라는
규칙 — COCOMO 와 Capers Jones 의 함수점수 표가 깔고 있는 가정 — 이
성립함을 확인했다 [R8]. 단독 구현 범위 안에서는 줄당 비용이 상수로
다뤄도 되는 값이라는 뜻이다.

한 가지 결과: 아주 큰 변경을 현실에서는 여러 명이 나눠 했을 수 있고,
그렇다면 실제 투입 시간은 여기 나온 값보다 **크다.** 이 모듈의 값은
그 경우 하한으로 읽으면 된다.

## 3. 왜 기존 요율(0.08분/단어)을 안 쓰나

`../agent-effort/rates.json` 의 `human_write_model.code_min_per_word`
는 **0.08분/단어 = 152줄/시간**이다. 이 모듈의 26.5줄/시간과 5.7배
차이가 나는데, 틀린 게 아니라 **다른 것을 재고 있다.**

```
152 줄/시간 = 22~31 줄/시간 ÷ 편집 시간 분율 14.5%
```

세션 기반 측정기(`../session-api`)는 이해를 `read` 축, 탐색을 `search`
축, 숙고를 `think` 축이 **따로** 받는다. 그래서 쓰기 요율에 전체 작업
속도를 넣으면 이중계상이 된다. 그걸 피하려고 편집 분율로 나눠 놓은
값이 0.08이다 — **순수 타이핑 몫.**

diff 만 있으면 그 축들이 존재하지 않는다. 그러니 나눈 것을 도로 곱해
Prechelt 원값으로 복귀시킨다. 그게 2.26이다.

**따라서 `edit_factor` 0.4 도 적용하지 않는다.** 0.4는 "수정은 신규보다
덜 친다"는 타이핑 비율인데, 전체 작업 관점에서는 기존 코드 수정이
오히려 비싸다(이해 몫 58%). Prechelt 는 백지에서 짠 측정이라 이해 몫이
이미 들어 있다.

## 3.5 CSV 배치 — `csv_report.py`

한 줄에 한 사람씩 담긴 사용량 CSV 를 읽어 **사람마다** 환산·지표를 낸다.

```
python csv_report.py usage.csv
python csv_report.py usage.csv --band slow --sort x_user
python csv_report.py usage.csv --out report.csv
python csv_report.py usage.csv --json
```

필수 컬럼: `employee_id` · `lines_added` · `lines_removed` ·
`cli_active_sec` · `user_active_sec` · `total_cost`. (없으면 어떤 게
없는지 알려주고 종료한다.)

| 지표 | 정의 | 단위 |
|---|---|---|
| `effort_min` | `diff_effort(lines_added, lines_removed)` | 분 |
| `x_total` | `effort_min ÷ ((cli_active_sec + user_active_sec) / 60)` | 배 |
| `x_user` | `effort_min ÷ (user_active_sec / 60)` | 배 |
| `min_per_usd` | `effort_min ÷ total_cost` | 분/$ |

출력 예:

```
band=mid  (요율: 작성 2.264분/줄, 삭제 1.313분/줄)
employee_id      added    removed   effort_min   effort_h    x_total     x_user  min_per_usd
--------------------------------------------------------------------------------------------
oseok.kim       179887      25046     407291.3     6788.2       27.8      660.4         38.3
jane.doe         20000      31000      59728.3      995.5       35.1      298.6         49.8
zero.user            0          0          0.0        0.0          -          -            -
--------------------------------------------------------------------------------------------
TOTAL(n=3)      199887      56046     467019.6     7783.7       28.5      571.8         39.4
```

전 인원 합산은 표 아래에 식과 함께 따로 찍는다:

```
[전체 합산 TOTAL(n=3)]
  사람노동 합                       467019.6 분  (7783.7 시간)
  CC+사용자 세션시간 합              16362.0 분  (272.7 시간)
  사용자 세션시간 합                   816.8 분  (13.6 시간)
  달러비용 합                       11839.20 $
  ----
  사람노동합 / (CC+사용자)세션시간합 = 28.54 배
  사람노동합 / 사용자세션시간합      = 571.80 배
  사람노동합 / 달러비용합            = 39.45 분/$
```

- 분모가 0이면 `-` 로 두고 계산하지 않는다. 정렬해도 그런 줄은 항상 끝.
- 합산 비율은 **합계 ÷ 합계**다. 사람별 비율의 평균이 아니다 — 라인 수가
  많은 사람이 그만큼 더 반영되는 게 맞다. `--no-total` 로 끌 수 있다.
- `--file-deleted-col` 로 '파일 통째 삭제' 라인 수 컬럼을 지정할 수 있다.
  없으면 0으로 두므로 순삭제가 전부 비싼 쪽(1.30분/줄) 요율을 받는다.

**이 CSV 를 그대로 쓸 때의 함정 (§4 와 별도로 여기서만 생기는 것)**

1. **교체 쌍 제거가 사람 단위 총합에 걸린다.** `max(0, 삭제 − 추가)` 는
   원래 커밋 단위 연산이다. 한 사람의 1년치 총합에 걸면 대개
   `추가 >> 삭제` 라 **삭제 몫이 통째로 0이 된다.** 위 예의 oseok.kim
   도 25,046줄 삭제가 전부 교체 쌍으로 흡수됐다. 커밋별 추가/삭제가
   있으면 커밋마다 계산해 더하는 쪽이 정확하다.
2. **원시 라인 수는 주석·빈 줄·자동생성 파일을 포함한다.** 위 예에서
   `effort_h = 6,788시간`인데 같은 행의 `user_active_sec` 은 10.3시간이다
   — 660배. 이 격차의 지배적 원인이 미필터 라인 수다. 절대 시간으로
   읽지 말 것.

즉 이 스크립트의 출력은 **사람 간 상대 비교**(누가 더 많이 만들었나,
1달러가 누구에게서 더 많은 산출을 샀나)로만 읽는 게 맞다.

## 4. 한계 — 쓰기 전에 읽을 것

1. **세션 측정기와 섞으면 안 된다.** 이 모듈의 결과를
   `record_actions_code_api` 의 분자에 더하면 이해·탐색을 두 번 센다.
   둘 중 하나만 쓴다.
2. **주석·빈 줄 제외.** Prechelt 는 non-comment LOC 기준이다. diff 라인
   수를 그대로 넣으면 20~30% 과대.
3. **밴드를 같이 낼 것.** 22~31줄/시간이면 결과가 ±20% 흔들린다.
   `--all-bands` 또는 `diff_effort_band()` 를 쓴다.
4. **라인 수는 노동의 대리 지표일 뿐이다.** 어려운 10줄과 쉬운 1,000줄이
   같은 값을 받는다. Prechelt 의 중앙값은 여러 구현을 평균 낸 값이라
   개별 변경에 적용하면 흩어짐이 크다.
5. **사람 실측 정답 0건.** 이 프로젝트의 다른 요율과 마찬가지로 외부
   문헌 anchor 이지 동일 작업을 사람에게 시킨 paired measurement 가
   아니다. 절대값보다 **변경 간 상대 비교** 용도.
6. **생성 코드·보일러플레이트 미구분.** 자동 생성 파일이나 락파일이
   diff 에 섞이면 그대로 과금된다. 넣기 전에 걸러야 한다.
