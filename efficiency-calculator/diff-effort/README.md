# diff-effort — 코드 라인 변경수 → 사람 노동 환산

`diff` 의 추가/삭제 라인 수만 가지고 "사람이 직접 짰다면 몇 분"을
환산한다. 세션 트랜스크립트가 없을 때 쓴다.

---

## 0. 실행 절차 (이대로 하면 된다)

**Claude 에게 시킬 때는 이 절 하나만 읽히면 된다. 순서대로 실행할 것.**

### 0-1. 보정 계수 재기 — 대상 저장소에서 한 번만

```
cd efficiency-calculator/diff-effort
python measure_ratios.py <대상저장소경로>
```

여러 저장소면 경로를 나열한다: `python measure_ratios.py repoA repoB`
기간을 좁히려면 `--since 2025-01-01 --until 2025-12-31`.

결과가 **`ratios.json` 으로 저장된다**(이 폴더). 아무것도 복사하지 않는다.

### 0-2. CSV 돌리기

```
python csv_report.py <사용량CSV경로>
```

`ratios.json` 을 자동으로 읽어 보정을 적용한다. 끝이다.
사람별 표와 전 인원 합산 3지표가 나온다. 출력 맨 위 `[가정]` 블록에
어떤 설정 파일을, 어느 저장소·기간에서 잰 것으로 썼는지 찍힌다.

옵션: `--out report.csv` (CSV 저장) · `--json` · `--band slow`
(느린 밴드) · `--sort x_user` (정렬) · `--config <경로>` (다른 설정 파일)

### 판단이 필요한 경우

| 상황 | 어떻게 |
|---|---|
| 대상 저장소에 접근이 안 된다 | 0-1 을 건너뛰고 0-2 만 실행. `ratios.json` 이 없으면 보정 없이 돌고 "보정 없이 돌렸다" 경고가 찍힌다. **절대 시간은 믿지 말고 사람 간 순위만 읽는다** (보정 없으면 2배쯤 과대) |
| CSV 에 필수 컬럼이 없다 | 스크립트가 없는 컬럼 이름을 찍고 멈춘다. 그 컬럼을 채워 오거나 작업 불가를 보고한다 |
| 결과 폭도 보고해야 한다 | `--band fast` 와 `--band slow` 로 한 번씩 더 돌린다 (±20%) |
| `ratios.json` 이 이미 있는데 다른 저장소를 잰다 | 0-1 을 다시 돌리면 덮어쓴다. 남기려면 `--out other.json` 으로 쓰고 0-2 에서 `--config other.json` |
| 남이 만든 `ratios.json` 을 쓰고 싶다 | 하지 마라. 저장소·기간마다 다르다. 그래서 이 파일은 git 에 올라가지 않는다 |

### 보고할 때 반드시 같이 적을 것

- 출력 맨 위 `[가정]` 블록 전체 (설정 파일 경로·잰 대상·밴드·구성비·유효 라인 비율)
- 보정 없이 돌렸다면 **"보정 미적용, 절대값 과대"** 라고 명시

### 필수 CSV 컬럼

`employee_id` · `lines_added` · `lines_removed` · `cli_active_sec` ·
`user_active_sec` · `total_cost`

### 파이썬에서 직접 부를 때

```python
from diff_effort import diff_effort, mix_factor, effective_ratio

diff_effort(320, 180)["minutes"]                                # 724.5
diff_effort(320, 180,
            mix=mix_factor(0.44, 0.315, 0.244),
            eff_ratio=effective_ratio(0.25, 0.10))["minutes"]   # 326.7
```

---

아래는 왜 이 숫자인지에 대한 근거다. 실행만 하면 되면 여기서 멈춰도 된다.

## 1. 수식

```
유효추가 = 추가줄 x 유효라인비율
유효삭제 = max(0, 삭제줄 x 유효라인비율 - 유효추가)      # 교체 쌍 제거

분 = (유효추가 x 2.26 + 유효삭제 x 0.30) x 구성비계수
```

| 항 | 분/줄 | 줄/시간 | 뜻 |
|---|---|---|---|
| 작성 (`W_new`) | **2.26** | 26.5 | 코드를 짜는 전체 노동 |
| 삭제 (`W_del`) | **0.30** | 200 | 지울 코드를 확인하는 노동 |

| 계수 | 기본 | 뜻 |
|---|---|---|
| 구성비계수 (`mix`) | 1.0 (전부 코드) | 코드/문서/데이터 비율에서 나오는 실효 요율 배수 |
| 유효라인비율 (`eff_ratio`) | 1.0 (미보정) | 주석·빈 줄·자동생성물을 걷어낸 비율 |

두 계수는 **기본이 꺼짐**이다. 안 켜면 절대값이 크게 과대하다 —
비율을 실측해서 넣어야 의미 있는 값이 나온다. 켜면 리포트에 무엇을
가정했는지 같이 찍힌다.

## 2. 근거

### 2.1 작성 2.26분/줄 — Prechelt [R8]

Prechelt 의 7개 언어 80개 구현 비교는 소스 생산성 중앙값을
**22~31 non-comment LOC/시간**으로 보고한다. 이 값은 **설계·작성·시험을
다 포함한** 전체 작업 시간 기준이다.

```
26.5 줄/시간 (밴드 중앙)  →  60 ÷ 26.5 = 2.26 분/줄
```

상식 대조: 하루 8시간이면 176~248줄/일. 업계 통념(하루 100~200줄)과
같은 크기다.

### 2.2 삭제 0.30분/줄 — 인스펙션 속도 [R13]

지우는 일은 **짜는 일이 아니라 읽고 판단하는 일**이다. 지워도 되는지
확인해야 지운다. 그래서 작성 생산성이 아니라 코드 인스펙션·리뷰 속도를
앵커로 쓴다.

Fagan 의 인스펙션 보고는 결함을 잡아내는 촘촘한 검토 속도를 **시간당
100줄대**로 둔다 [R13]. 현대 코드 리뷰 가이드는 시간당 200~400줄대를
쓴다. 삭제 판단은 결함 탐색만큼 촘촘할 필요가 없으므로 그 밴드에서
**보수적으로 느린 쪽인 200줄/시간**을 채택한다.

```
200 줄/시간  ->  60 ÷ 200 = 0.30 분/줄
```

이 값은 **작성 밴드(22~31줄/h)를 따라 움직이지 않는다.** 읽는 속도가
짜는 속도와 같이 변할 이유가 없어서 별도 상수로 뒀다.

**종전 1.30분/줄에서 내린 이유.** 처음에는 Xia 의 이해 시간 분율
58%를 승계해 `작성 x 0.58 = 1.31분/줄`로 뒀다. 그런데 Xia 의 58%는
**작업 전체에서 이해에 쓴 시간 비중**이지, 지워질 줄 하나하나에 드는
비용이 아니다. 그대로 옮기면 "삭제 줄 하나가 새 줄 하나의 58% 노동"이
되어 과대다. 그 승계를 버리고 실제로 하는 행위(읽고 확인)의 속도
문헌으로 갈아탔다. 결과적으로 4.4배 작아졌다.

### 2.3 순삭제 = max(0, 부분삭제 − 추가) — 교체 쌍 제거

`git diff` 는 한 줄을 고치면 `+1 / −1` 쌍으로 잡는다. 추가와 삭제를
둘 다 과금하면 **타이핑 한 번을 두 번 센다.** 그래서 겹치는 만큼을
빼고, 남은 순삭제만 삭제 요율로 받는다.

**파일 통째 삭제는 따로 다루지 않는다.** 집계 데이터에 그 구분이
애초에 잡히지 않고(파일 단위 정보가 없다), 삭제 요율 자체가 확인
비용 수준(0.30분/줄)으로 내려와 있어 따로 뺄 실익이 없다.

### 2.4 왜 규모에 정비례(선형)로 두나

줄 수가 늘면 줄당 비용도 늘어난다는 관측이 있다. Boehm 의 COCOMO II
는 공수를 `Effort = A x Size^E` 로 두고 지수 `E = 0.91 + 0.01 x SF합`
으로 계산하는데, 실무 범위에서 **E 는 1보다 크다(대략 1.01~1.26)**.
규모가 두 배면 공수는 두 배 넘게 든다는 뜻 — **규모의 불경제**다 [R11].

그런데 그 초선형의 실체는 **코드가 커져서**가 아니라 **사람이 여러
명이라서** 생긴다. Brooks 는 이를 의사소통 경로로 정식화했다: 인원 n
명이면 경로가 `n(n-1)/2` 개로 **제곱에 비례해** 늘어난다 [R12].
COCOMO II 의 지수를 밀어 올리는 척도인자(SF) 목록 자체가 그 증거다 —
`TEAM`(팀 응집도), `PMAT`(조직 프로세스 성숙도), `ARCH`(아키텍처
선행 해소), `PREC`(선례 없음). **전부 여러 사람이 같이 일할 때만
의미가 있는 항목**이고, 코드 자체의 성질이 아니다 [R11].

즉 대형 프로젝트 데이터에서 뽑은 초선형 계수는 **다인 협업
오버헤드**를 규모의 함수로 옮겨 적은 값이다.

이 모듈이 쓰는 Prechelt 의 값은 그런 데이터가 아니다. **개별 참가자가
같은 사양의 프로그램을 각자 혼자 구현한 80개 구현**의 생산성이다.
협업 오버헤드가 애초에 들어 있지 않다.

재는 대상도 마찬가지다. 이 모듈의 입력은 하나의 diff — **한 주체(사람
한 명 또는 에이전트 하나)가 만든 변경**이다. 인원이 늘어서 생기는
오버헤드가 발생할 자리가 없다.

**요율과 대상이 둘 다 단독 작업이므로 규모에 정비례로 둔다.** 초선형
계수를 얹으면 이 diff 에 존재하지 않는 협업 비용을 과금하게 된다.

덧붙여, Prechelt 자신이 이 데이터에서 "시간당 줄 수는 언어와 무관"이라는
규칙 — COCOMO 와 Capers Jones 의 함수점수 표가 깔고 있는 가정 — 이
성립함을 확인했다 [R8]. 단독 구현 범위 안에서는 줄당 비용이 상수로
다뤄도 되는 값이라는 뜻이다.

한 가지 결과: 아주 큰 변경을 현실에서는 여러 명이 나눠 했을 수 있고,
그렇다면 실제 투입 시간은 여기 나온 값보다 **크다.** 이 모듈의 값은
그 경우 하한으로 읽으면 된다.

### 2.5 구성비 계수 — 코드만 있는 게 아니다

`lines_added` 를 전부 코드 요율로 치면 문서와 데이터를 과대 계상한다.
사람 절차가 셋 다 다르기 때문이다 — 코드는 짜고, 문서는 쓰고,
데이터(JSON·YAML·CSV)는 손으로 치지 않고 **뽑는다**(생성 스크립트).

`../agent-effort/rates.json` 의 `human_write_model` 이 이미 갈라 놓은
비율을 그대로 승계한다:

| 종류 | 타이핑 요율 | 코드 대비 배수 | 요율의 출처 |
|---|---|---|---|
| 코드 | 0.08 분/단어 | **1.000** | 문헌 유도 (Prechelt ÷ Xia 편집분율) |
| 문서 | 0.05 분/단어 | **0.625** | 문헌 앵커 (Karat CHI'99, 20 wpm) |
| 데이터 | 0.01 분/단어 | **0.125** | seed (문헌 없음) |

**배수의 출처와 구성비의 출처는 다르다.** 위 배수는 문헌·seed 에서 온
요율의 비율이고, 아래에서 예시로 쓰는 구성비(44/31.5/24.4)는 **실측**이다.
섞어 읽으면 안 된다.

구성비를 넣으면 정규화해서 가중평균한다:

```
mix_factor(code, doc, data) = Σ (비율_k / 합) x 배수_k

mix_factor(0.44, 0.315, 0.244) = 0.668
```

즉 코드 44% / 문서 31.5% / 데이터 24.4% 인 변경은 전부 코드로 쳤을
때의 **0.668배**다. 비율은 합이 1이 아니어도 되고(내부에서 정규화),
줄 수를 그대로 넣어도 된다.

**예시로 쓴 44/31.5/24.4 의 출처.** 이 프로젝트가 Claude Code 세션
트랜스크립트(`~/.claude/projects/**/*.jsonl`)를 훑어 **Write/Edit 도구로
나간 단어**를 확장자별로 집계한 실측이다 — 근거는
`../session-api/record_actions_code_api.md` §2.5, 요율표 주석은
`../agent-effort/rates.json` 의 `human_write_model._comment`. 즉 사람이
직접 짠 코드의 구성비가 아니라 **에이전트가 만들어낸 산출물의 구성비**다.
같은 문서의 다른 집계 시점에는 42.5 / 30 / 26 으로도 잡혀 있다 — 기간에
따라 흔들린다는 뜻이다.

**단위가 다르다는 점에 주의.** 그 실측은 **단어** 기준이고, 이 모듈과
`measure_ratios.py` 는 **라인** 기준이다. 종류마다 줄당 단어 수가 다르므로
(코드 4.94단어/줄, 문서·데이터는 다름) 단어 구성비를 라인 구성비 자리에
그대로 넣으면 오차가 생긴다. **자기 데이터를 라인 기준으로 재서 넣는
쪽이 맞다** — `measure_ratios.py` 가 그걸 한다 (§2.7).

**고정 계수를 코드에 박지 않는다.** 0.668 은 위 실측에서 나온 예시일
뿐이고, 조직·기간마다 다르다. 안 넣으면 1.0(전부 코드)으로 동작하고
리포트에 "미지정 → 전부 코드 요율 (문서·데이터 과대)" 이라고 찍힌다.

**가정 하나.** 이 배수(1 : 0.625 : 0.125)는 **타이핑 축**에서 잰
비율인데, 전체 작업 축으로 옮겨도 같다고 본다. 문서·데이터의 '전체
작업 생산성' 문헌이 없어서 쓰는 가정이다. 코드에 그대로 적으면
문서 = 42줄/h, 데이터 = 212줄/h 라는 뜻이 된다.

### 2.6 유효 라인 비율 — 주석·생성물은 어떻게 반영하나

Prechelt 의 요율은 **non-comment LOC** 기준인데 `lines_added` 원시값은
주석·빈 줄·자동생성물을 다 포함한다. 그래서 **요율이 아니라 라인 수
쪽을 보정한다** — 원시 라인 수를 요율의 기준(non-comment, 사람이 실제로
쓴 줄)으로 되돌리는 계수다.

```
유효라인비율 = (1 - 주석·빈줄 비율) x (1 - 자동생성물 비율)

effective_ratio(0.25, 0.10) = 0.675
```

두 비율을 곱하는 이유: 서로 다른 축이다. (생성 파일 안의 주석을 두 번
빼는 오차가 있지만 방향이 안전한 쪽 — 과소 추정 쪽 — 이다.)

**여기서도 기본값을 박지 않는다.** 주석·빈 줄 비율은 언어와 팀 규약에
따라 15~35% 로 흩어지고, 자동생성물 비율은 저장소마다 0~50% 다. 추정치를
기본값으로 박으면 그게 또 하나의 근거 없는 seed 가 된다. 대신:

- **주석·빈 줄**: `cloc` 류로 한 번만 재면 정확한 값이 나온다
  (`code` / `comment` / `blank` 를 그대로 보고한다).
- **자동생성물**: 락파일·`.min.*`·마이그레이션·스냅샷·vendored 디렉터리를
  경로 규칙으로 골라 라인 수 비중을 낸다.

둘 다 **한 번만 재면 되는 값**이고, 재고 나면 이 계수는 추정이 아니라
실측이 된다. **§2.7 의 `measure_ratios.py` 가 둘 다 재 준다.** 재기 전까지는 1.0(미보정)으로 두고, 리포트에 "미보정 →
주석·빈 줄·자동생성물 포함 (과대)" 이라고 찍힌 채로 쓴다.

**정공법은 따로 있다.** 애초에 `cloc` 이나 `git diff` 필터로 걸러낸
라인 수를 입력에 넣는 것이다. 이 계수는 집계 CSV 처럼 **원시 라인 수만
받을 수 있을 때**의 차선책이다.

### 2.7 계수는 어디서 얻나 — `measure_ratios.py`

기본값을 안 박는다고 했으니 **잴 도구를 같이 둔다.** 세 계수를 저장소에서
실측해 `ratios.json` 에 써 둔다. `csv_report.py` 가 그 파일을 자동으로
읽으므로 사람이 값을 옮길 일이 없다.

```
python measure_ratios.py /path/to/repo
python measure_ratios.py repo1 repo2 --since 2025-01-01
python measure_ratios.py /path/to/repo --author someone@corp.com
python measure_ratios.py /path/to/repo --out other.json   # 다른 경로에
```

무엇을 어디서 재는지:

| 계수 | 재는 대상 | 방법 |
|---|---|---|
| 구성비 | `git log --numstat` 의 diff 라인 | 확장자로 코드/문서/데이터 분류 (자동생성물 뺀 뒤) |
| 자동생성물 비율 | 같은 diff 라인 | 경로 규칙 (락파일·`node_modules`·`dist`·`.min.*`·스냅샷·마이그레이션 등) |
| 주석·빈 줄 비율 | 현재 체크아웃의 코드 파일 | `cloc` 이 있으면 cloc, 없으면 내장 근사 계수기 |

확장자 분류는 `../human-effort/requirement-actions` 의 `write_kind` 와
같은 목록이다(그 모듈은 폴더명에 하이픈이 있어 import 가 안 돼 옮겨 적었다).

이 저장소에서 실제로 돌린 결과:

```
[구성비] diff 라인 39595줄 기준 (자동생성물 제외)
  코드       20175줄   50.9%
  문서       17417줄   44.0%
  데이터      2003줄    5.1%
  (기타 3153줄은 구성비에서 제외 — 확장자 미분류)

[자동생성물] 전체 diff 42831줄 중 83줄 = 0.2%

[주석·빈 줄] 코드 12856줄 기준 23.8%  (출처: builtin)

[저장] .../diff-effort/ratios.json
  csv_report.py 가 이 파일을 자동으로 읽는다. 실행:
    python csv_report.py <사용량CSV경로>
```

저장 파일은 수치만이 아니라 **언제·어느 저장소·어느 기간을 어떤 기준
(diff 라인)으로 쟀는지**를 같이 담는다:

```json
{
  "_schema": "diff-effort/ratios@1",
  "mix": { "code": 0.5095, "doc": 0.4399, "data": 0.0506 },
  "comment_ratio": 0.2384,
  "generated_ratio": 0.0019,
  "measured": {
    "at": "2026-08-27T16:02:36+09:00",
    "repos": ["C:\\Users\\joung\\avatar-efficiency"],
    "since": null, "until": null, "author": null,
    "basis": "diff lines (git log --numstat)",
    "diff_lines_by_kind": { "code": 20175, "doc": 17417,
                            "data": 2003, "other": 3153 },
    "comment_source": "builtin"
  }
}
```

리포트의 `[가정]` 블록이 이 기록을 그대로 찍으므로, 결과만 봐도 어떤
조건으로 잰 계수인지 알 수 있다.

`ratios.json` 은 `.gitignore` 에 들어 있다 — 커밋해 두면 남의 저장소에서
잰 계수가 다른 사람 실행에 자동 적용되기 때문이다. 각자 재서 만든다.

**이 숫자를 그대로 베끼지 마라.** 저장소·기간마다 다르다 — 이 저장소는
문서가 44%나 되는 특이한 구성이다. 자기 데이터에서 재고, 리포트에 어떤
조건(기간·저자·저장소)으로 쟀는지 남긴다.

한 번 재면 끝나는 값이다. 재기 전까지는 계수를 켜지 말고, 켜지 않은
상태의 출력은 절대 시간이 아니라 상대 비교로만 읽는다.

## 3. 왜 기존 요율(0.08분/단어)을 안 쓰나

`../agent-effort/rates.json` 의 `human_write_model.code_min_per_word`
는 **0.08분/단어 = 152줄/시간**이다. 이 모듈의 26.5줄/시간과 5.7배
차이가 나는데, 틀린 게 아니라 **다른 것을 재고 있다.**

```
152 줄/시간 = 22~31 줄/시간 ÷ 편집 시간 분율 14.5%
```

세션 기반 측정기(`../session-api`)는 이해를 `read` 축, 탐색을 `search`
축, 숙고를 `think` 축이 **따로** 받는다. 그래서 쓰기 요율에 전체 작업
속도를 넣으면 이중계상이 된다. 그걸 피하려고 편집 분율로 나눠 놓은
값이 0.08이다 — **순수 타이핑 몫.**

diff 만 있으면 그 축들이 존재하지 않는다. 그러니 나눈 것을 도로 곱해
Prechelt 원값으로 복귀시킨다. 그게 2.26이다.

**따라서 `edit_factor` 0.4 도 적용하지 않는다.** 0.4는 "수정은 신규보다
덜 친다"는 타이핑 비율인데, 전체 작업 관점에서는 기존 코드 수정이
오히려 비싸다(이해 몫 58%). Prechelt 는 백지에서 짠 측정이라 이해 몫이
이미 들어 있다.

## 3.5 CSV 배치 — `csv_report.py`

한 줄에 한 사람씩 담긴 사용량 CSV 를 읽어 **사람마다** 환산·지표를 낸다.

```
python csv_report.py usage.csv
python csv_report.py usage.csv --mix 0.44,0.315,0.244
python csv_report.py usage.csv --mix 0.44,0.315,0.244 --comment-ratio 0.25 --generated-ratio 0.10
python csv_report.py usage.csv --band slow --sort x_user --out report.csv
python csv_report.py usage.csv --json
```

보정 옵션은 §2.5·§2.6 의 두 계수를 켜는 것이다. 안 켜면 1.0 으로
동작하고, 켜든 안 켜든 무엇을 가정했는지 리포트 맨 위에 찍힌다.
**넣을 값은 `measure_ratios.py` 로 잰다 (§2.7)** — 저장소를 훑어
`ratios.json` 에 써 두고, 이 스크립트가 그 파일을 자동으로 읽는다.

필수 컬럼: `employee_id` · `lines_added` · `lines_removed` ·
`cli_active_sec` · `user_active_sec` · `total_cost`. (없으면 어떤 게
없는지 알려주고 종료한다.)

| 지표 | 정의 | 단위 |
|---|---|---|
| `effort_min` | `diff_effort(lines_added, lines_removed)` | 분 |
| `x_total` | `effort_min ÷ ((cli_active_sec + user_active_sec) / 60)` | 배 |
| `x_user` | `effort_min ÷ (user_active_sec / 60)` | 배 |
| `min_per_usd` | `effort_min ÷ total_cost` | 분/$ |

출력 예 (보정 켠 경우):

```
[가정]
  밴드          mid — 작성 2.264분/줄 (26.5줄/h), 삭제 0.300분/줄 (200줄/h)
  구성비        코드 44.0% / 문서 31.5% / 데이터 24.4% → 실효 요율 배수 0.6680
  유효 라인     주석·빈 줄 25.0% + 자동생성물 10.0% 제외 → 유효 라인 비율 0.6750

employee_id      added    removed   effort_min   effort_h    x_total     x_user  min_per_usd
--------------------------------------------------------------------------------------------
oseok.kim       179887      25046     183659.5     3061.0       12.5      297.8         17.3
jane.doe         20000      31000      21907.5      365.1       12.9      109.5         18.2
zero.user            0          0          0.0        0.0          -          -            -
--------------------------------------------------------------------------------------------
TOTAL(n=3)      199887      56046     205567.0     3426.1       12.6      251.7         17.4
```

전 인원 합산은 표 아래에 식과 함께 따로 찍는다:

```
[전체 합산 TOTAL(n=3)]
  사람노동 합                       205567.0 분  (3426.1 시간)
  CC+사용자 세션시간 합              16362.0 분  (272.7 시간)
  사용자 세션시간 합                   816.8 분  (13.6 시간)
  달러비용 합                       11839.20 $
  ----
  사람노동합 / (CC+사용자)세션시간합 = 12.56 배
  사람노동합 / 사용자세션시간합      = 251.69 배
  사람노동합 / 달러비용합            = 17.36 분/$
```

- 분모가 0이면 `-` 로 두고 계산하지 않는다. 정렬해도 그런 줄은 항상 끝.
- 합산 비율은 **합계 ÷ 합계**다. 사람별 비율의 평균이 아니다 — 라인 수가
  많은 사람이 그만큼 더 반영되는 게 맞다. `--no-total` 로 끌 수 있다.

**이 CSV 를 그대로 쓸 때의 함정 (§4 와 별도로 여기서만 생기는 것)**

1. **교체 쌍 제거가 사람 단위 총합에 걸린다.** `max(0, 삭제 − 추가)` 는
   원래 커밋 단위 연산이다. 한 사람의 1년치 총합에 걸면 대개
   `추가 >> 삭제` 라 **삭제 몫이 통째로 0이 된다.** 위 예의 oseok.kim
   도 25,046줄 삭제가 전부 교체 쌍으로 흡수됐다. 커밋별 추가/삭제가
   있으면 커밋마다 계산해 더하는 쪽이 정확하다.
2. **보정을 안 켜면 절대값이 크게 과대다.** 같은 데이터를 보정 없이
   돌리면 oseok.kim 이 `effort_h = 6,788시간`이 나온다(보정하면 3,061시간).
   같은 행의 `user_active_sec` 은 10.3시간이다. 구성비·유효 라인 비율을
   자기 데이터로 재서 넣기 전에는 절대 시간으로 읽지 말 것.

즉 이 스크립트의 출력은 **사람 간 상대 비교**(누가 더 많이 만들었나,
1달러가 누구에게서 더 많은 산출을 샀나)로만 읽는 게 맞다.

## 4. 한계 — 쓰기 전에 읽을 것

1. **세션 측정기와 섞으면 안 된다.** 이 모듈의 결과를
   `record_actions_code_api` 의 분자에 더하면 이해·탐색을 두 번 센다.
   둘 중 하나만 쓴다.
2. **보정 계수는 기본이 꺼져 있다.** 구성비(§2.5)와 유효 라인 비율
   (§2.6)을 안 넣으면 문서·데이터를 코드 요율로 치고 주석·생성물까지
   과금한다. 둘을 합치면 대략 2배 과대다. `measure_ratios.py` 로 자기
   데이터에서 재서 넣어야 한다 (§2.7).
3. **밴드를 같이 낼 것.** 22~31줄/시간이면 결과가 ±20% 흔들린다.
   `--all-bands` 또는 `diff_effort_band()` 를 쓴다.
4. **라인 수는 노동의 대리 지표일 뿐이다.** 어려운 10줄과 쉬운 1,000줄이
   같은 값을 받는다. Prechelt 의 중앙값은 여러 구현을 평균 낸 값이라
   개별 변경에 적용하면 흩어짐이 크다.
5. **사람 실측 정답 0건.** 이 프로젝트의 다른 요율과 마찬가지로 외부
   문헌 anchor 이지 동일 작업을 사람에게 시킨 paired measurement 가
   아니다. 절대값보다 **변경 간 상대 비교** 용도.
6. **구성비·유효 라인 비율은 사람마다 다르다.** 이 스크립트는 전원에게
   같은 계수를 먹인다. 문서만 쓰는 사람과 코드만 짜는 사람이 섞여
   있으면 그 차이는 반영되지 않는다. 사람별 확장자 분해가 있으면
   `diff_effort(..., mix=...)` 를 사람마다 다르게 주는 쪽이 맞다.
7. **삭제 요율은 문헌 인접 앵커다.** 0.30분/줄은 인스펙션 속도 밴드에서
   고른 값이지 삭제 작업 자체를 잰 실측이 아니다 (§2.2).
