# record_actions_code_api — 측정 방법서

`record_actions_code_api.py`의 기능·휴먼화 원리·요율을 한곳에 정리한 문서.
코드 독스트링·`rates.json` 주석·CHANGELOG에 분산된 내용의 통합본이며,
수치·규칙의 원 출처는 각 § 표기를 따라 `../CHANGELOG.md`에서 찾는다.

## 1. 기능 개요

Claude Code 세션 기록(`.jsonl`) 1개를 받아 **LLM 호출 0회, 완전 결정론**
(같은 입력 = 같은 결과)으로 다음을 계산한다:

```
speedup = human_min(분자) ÷ agent_min(분모)

분자 human_min = "일을 아는 사람이 직행했다면" 걸렸을 분 (휴먼화 ON 기준)
분모 agent_min = AI 경로의 추정 비용 = 기계(machine) + 추정 사람 감독(hitl)
                 (§49 용어: 동작 카운트는 실측이나 요율 다수가 seed라
                  "실제 비용"이 아니라 추정 비용 — instruct만 실측 보정)
```

- 분자·분모 모두 세션 기록의 **단서(무엇이 만들어졌고 읽혔나) × 요율표**로
  계산한다. wall-clock(세션에 흐른 시간)은 원칙적으로 쓰지 않는다 — 사람
  노동은 세션 밖에서 몰아 할 수 있어 시간 측정으로 못 잡는다(측정 기조).
  **예외 2곳**: ① 분자의 **실행 대기**(§59) — 사람이 명령을 돌려놓고
  기다리는 시간은 추정할 게 아니라 기록에 있다. ② **분모의 AI 몫 전체**
  (§62) — 요율 계산을 버리고 턴 실측으로 바꿨다. 아래 §4.2 참조.
- **병렬 서브에이전트 기록(isSidechain): 분자는 포함, 분모는 제외 (§59).**
  종전에는 양쪽 다 제외했는데, "병렬이라 실소모 시간에 못 더한다"는 것은
  **분모 규칙**이다. 분자는 "사람이 직렬로 다 한다면"이므로 서브에이전트가
  한 일을 반드시 세어야 한다. 실측: 서브에이전트를 실제로 부린 세션은
  분자가 최대 2.2배 틀려 있었다(배율 3.54 → 7.67배).
- 초소형 세션은 측정 제외(`excluded`) — 완료조건 고정비로 5~7배 역부풀림
  실측(§9). **판정 기준은 세션 러닝타임 5분 이하**(§64) — 첫 기록부터
  마지막 기록까지. 종전 단어수 기준(검토·입력 100단어 미만 그리고 산출물
  50단어 미만)은 타임스탬프가 없는 구 기록의 폴백으로만 남는다.
  `force=True`로 우회 가능.

```python
from record_actions_code_api import measure, measure_batch
r = measure("session.jsonl")                      # rw ON · act ON (기본)
r = measure("session.jsonl", humanize_rw=False)   # rw OFF · act ON
r = measure("session.jsonl", humanize_act=False)  # rw ON · act OFF
r = measure("session.jsonl", humanize_rw=False, humanize_act=False)  # 로레코드
r = measure("session.jsonl", include_think=False)  # 전략 생각(§3) 미계상
r = measure("session.jsonl", subagent_paths=[])   # 서브에이전트 0원 (구 동작, §59)
```

반환에 `channel_audit`이 붙는다 — 통로별 결산과 미계상 양(§5). 미계상이
문턱을 넘으면 `notes`에 자백이 실린다.

전략 생각(think, §3)은 **기본 ON**이며 휴먼화 2축과 독립 — 위 4조합
모두에 동일하게 가산된다(끄려면 `include_think=False` / CLI `--nothink`).

조합 순서 규약(모든 표·리포트 공통): **rw ON·act ON → rw OFF·act ON →
rw ON·act OFF → rw OFF·act OFF(로레코드)**. 휴먼화를 끌수록 "AI 궤적을
사람이 그대로 따라 한 셈"에 가까워지며, 항목별로 ON ≤ OFF 단조성이
구조적으로 보장된다(§43·§46 클램프).

## 2. 휴먼화 3축 — 어떻게 깎는가

공통 원리: **"결말에 기여한 것만 사람의 노동이다."** AI의 전수 탐색·
시행착오·번복을 걷어내고, 직행하는 사람의 최소 경로로 환산한다.
판정은 전부 코드 실측(결정론) — 아래 신호들이 근거다.

### 2.1 읽기 — 3등급 분해 (humanize_rw, §13~15·25~27)

AI가 읽은 파일(조회형 도구·셸 sed/cat류 읽기 포함, §27·§47)을 등급 분류:

| 등급 | 판정 | 요율 |
|---|---|---|
| 기여(DEEP) | 5신호 중 1개+: ① 이후 편집 ② 마무리 답변에 이름 언급 ③ 같은 구간 2회+ 재방문 ④ 탐색 착지(턴의 마지막 검색 직후 첫 읽기) ⑤ 내용 겹침(6단어 연속 조각·변별 식별자가 답변에 등장) | 핵심 블록만 정독, 나머지 훑기 |
| 훑은 후보(SKIM) | 비기여 파일이 항해 중(그 턴의 마지막 기여 읽기 이전)에 읽힘 | 훑기 0.00222 (450 wpm, 정독의 2.25배속 — §66) |
| 헛읽기(WASTE) | 비기여 파일이 기여 확보 이후에만 읽힘 | **0** — 사람은 열지도 않음 |

기여 파일도 전량 정독이 아니다 — 200단어 블록으로 갈라 증거(변별 식별자
2개+, 또는 답변·편집 원문과 6단어 겹침)가 닿은 블록만 정독, 나머지는
훑기(§26 구간·블록 분해). 같은 구간 재읽기는 단어수 1회만 집계.
**검색 결과 판독(§73)**: Grep/Glob/셸 grep·MCP 검색 결과는 읽기 단위(파일)가
아니지만 사람이 결과 목록을 훑어 위치를 고르는 시간은 실재 — 실행 출력과 같은
눈금(호출당 앞 200단어 정독·나머지 훑기)으로 rw ON 읽기에 가산. rw OFF는
`reviewed` 전량 정독에 이미 들어 있어 가산 없음.
**예외 — 조회형(§70)·범위 지정 Read(§75)**: 셸 `cat`/`sed -n`·MCP 조회 결과와
`Read(offset/limit)`로만 읽은 파일은 AI가 범위를 이미 집어서 본 것이라 후보
훑기가 아니라 목적 읽기 → 기여 판정이면 블록 분해 없이 **전량 정독**(비기여면
종전대로 훑기/헛읽기; 통째 읽기가 섞인 파일은 블록 규칙).
**바닥(§75)**: 기여 판정된 파일은 증거 블록이 없어도 **최소 앞 200단어 정독** —
실행 출력·검색 결과·hitl 결론의 "앞 200 읽고 넘어간다"와 같은 규칙. 종전엔
기여 파일 70%가 정독 0단어였다.

### 2.2 쓰기 — 순계 재생 (humanize_rw, §31)

"결말에 살아남은 단어만 노동" — 쓰기 순서열을 재생해 순계를 구한다:

- 세션이 만든 파일(Write 기점): 편집을 실제 재생해 최종본 복원 —
  만들었다 갈아엎은 왕복은 자동 0. 순계 전체 = 신규 작성(draft).
- 기존 파일(Edit 기점): 이후 편집의 원문이 앞서 써넣은 문구를 덮으면
  왕복으로 폐기. 부분 겹침은 놓치는 보수적(덜 깎는) 근사. 순계 = 수정(edit).
- 실패한 편집(툴 에러)은 제외. **마무리 답변(또는 StructuredOutput 보고,
  §33)은 파일 산출물 유무와 무관하게 draft(문서 요율)** — §73부터. 종전엔
  파일이 있으면 0이었다(사람도 인수인계 메모·결과 보고는 쓴다).
- **Edit는 변경 단어만 (§66)**: `edit_delta(old, new)`가 단어열 diff로
  3단어 이상 연속 일치(위치 잡으려고 다시 뱉은 앵커 — 실측 new_string의
  31%)를 빼고 `added`만 센다. old 단어를 하나도 지우지 않은 **순수 추가**는
  수정이 아니라 신규(draft), 나머지가 edit. 세션이 만든 파일에 대한 Edit는
  파일 출처상 신규.
- **서브에이전트 보고 (§68)**: 서브의 도구 행동(읽기·쓰기·실행·검색)은
  §59부터 분자에 들어간다. 서브가 부모에게 돌려주는 텍스트 보고는 사람이
  직렬로 했다면 **머릿속에 있던 것을 다음 단계로 넘기는 것** — 밖으로 나온
  생각이라 draft(20 wpm)가 아니라 **think 요율(0.005)로 전량** 계상한다
  (§3 참조). 산출물 유무로 가르지 않는다(§67의 "산출물 없는 서브의 마지막
  보고 = draft"는 위임하면 같은 계획이 10배 비싸지는 불연속이라 하루 만에
  대체). 양 모드 동일 가산. 채널 결산 `sub_report_words` → 생각 축.
- **OFF 총량도 같은 원리 (§66)**: 종전에는 도구명(Write=draft, Edit=edit
  ×0.4)으로 갈라 세션이 만든 파일을 Edit로 키우면 OFF가 ON보다 작아지는
  역전이 16/55세션에서 났다. 총량도 파일 출처·변경 단어 기준으로 분류해
  `gross_draft_by_kind`/`gross_edit_by_kind`로 넘기고, rw OFF 분기의 전역
  share 비율 분배는 폐지. 이로써 쓰기 항목 ON ≤ OFF가 구조적으로 성립.

### 2.3 행동 — 건수 순계 (humanize_act, §46~48)

읽기·쓰기의 원리를 건수형 행동에 적용:

- **검색 = 착지-기여 문서당 1건, 검색한 지시 턴당 최소 1건(§70)** — 검색
  끝에 기여(DEEP) 파일에 도달한 횟수를 세되, 검색을 1회+ 쓴 지시 턴은 착지가
  기여 안 됐어도 1건(숙련자도 새 지시가 오면 위치 확인은 한 번 한다). 종전
  하한은 세션당 1이었다(검색한 턴 568개 중 198건만 계상). 쿼리 다듬기(항해
  검색)는 그 1건의 요율에 흡수. 셸 속 grep·find류도 검색으로 재분류(§47).
- **실행 = 정규화 명령 신원당 1건** — 같은 명령 반복(편집→재실행 왕복)은
  신원 1개로 접힘. 무효 호출은 순계에서 상쇄(§48) — §69부터 **환경·타이핑
  실수·거부 서명**(command not found·No such file·ModuleNotFoundError·
  tool use was rejected 등)이 있을 때만 무효, 종료코드≠0(테스트 실패)은
  숙련자도 짜서 돌리는 정상 작업이라 생존. 셸 속
  sed·cat류는 조회형 읽기로 재분류, 리다이렉트(>)·히어독(<<)·sed -i는
  실행 잔류(§47). **건수에 곱하는 고정 요율은 §59에서 4토막 공식으로
  대체됐다 — 아래 2.4 참조.**
- 클램프: 실행은 흔적 있으면 최소 1건, 검색은 **검색한 지시 턴당 최소 1건**(§70) · 상한 기록 호출 수.
- 마무리 verify 1건(산출물 있을 때)은 켬/끔 공통(§43 — 역전 방지).

끄면(act OFF = 로레코드): 행동 횟수를 기록 그대로(검색 호출 수·실행
호출 수) — "AI가 한 행동을 사람이 똑같이 했다면".

### 2.4 실행 — 4토막 환산 (§59)

종전에는 실행 1건을 **건당 2.0분 고정**으로 매겼다. 그 값으로는 즉석
스크립트(heredoc·`python -c`, 건당 평균 97단어)와 `git status`가 같은
값이 된다. 사람이 실제로 하는 일은 네 토막이므로 각 토막을 실측 재료에
붙인다.

| 토막 | 사람이 하는 일 | 재료 | 요율 |
|---|---|---|---|
| 수단 구성 | 명령·스크립트를 친다 | 명령문 단어수 (첫 신원만) | `human_exec_model.compose_min_per_word` 0.05 |
| 실행 대기 | 돌아갈 때까지 기다린다 | tool_use→tool_result 타임스탬프 실측 | — (실측 그대로) |
| 결과 판독 | 출력을 읽고 판단한다 | 출력 단어수 (호출마다 앞 200단어 정독, 나머지 훑기) | `human.read` / `skim` |
| 기계 조작 | 터미널 전환·엔터·확인 | 새 명령 / 재실행 | 0.25 / 0.1분 |

- 구성 요율에 코드 요율(0.08)이 아니라 작문 요율(0.05)을 쓰는 이유: 설계를
  거치지 않고 바로 치는 글이라서.
- **결과 판독은 종전에 분자에서 전액 0원이었다** — "실행형 도구는 읽기가
  아님"이라는 규칙 때문. 사람은 테스트 로그를 읽고 다음을 정한다.
- act OFF(로레코드)에서는 매 호출이 새 명령으로 계상된다(구성 전량·기계
  조작 전량) — 항목별 ON ≤ OFF 단조성 유지.
- `human_exec_model`이 없는 구 요율표에서는 종전 건당 2.0분으로 폴백.
- **무효 호출(§69)**: 구성 단어는 신원별 첫 호출만 세되, `is_error`가 붙었어도
  종료코드≠0(테스트 실패·traceback)은 정상 작업이라 센다. 환경·타이핑
  실수·거부 서명(command not found·No such file·ModuleNotFoundError·tool use
  was rejected 등)이 있을 때만 무효 → 구성 0, 순계 제외.

실측 재구성 결과, **건당 2.0분은 이 4토막의 하한과 같은 값**이었다 —
짧은 한 줄에는 맞고(전체의 12%), 절반을 차지하는 즉석 스크립트에는
3~5배 모자랐다.

### 2.5 쓰기 종류 분해 — 코드·문서·데이터 (§59)

Write/Edit로 나간 단어의 실측 구성은 **코드 44% / 문서 31.5% / 데이터
24.4%**인데 종전에는 셋 다 한 요율(0.05)이었다. 종류마다 사람 절차가
다르므로 `human_write_model`로 가른다 — 코드는 짜고, 문서는 쓰고,
데이터(JSON·YAML·CSV)는 손으로 치지 않고 **뽑는다**(생성 스크립트).
수정(edit)은 같은 종류 신규의 **0.5배**(`edit_factor`, §66 — 문서 0.025 =
40 wpm), 적용 단위는 Edit `new_string` 전량이 아니라 **변경 단어**(앵커
제외, §2.2). 값과 근거는 §4.1·§8.3·§8.4.

## 3. 전략 생각(think) — 분자의 판단 노동 (§53, 기본 ON)

휴먼화 2축이 AI의 장황함을 **깎는** 장치라면, think는 분자에 빠져 있던
판단 노동을 **보충하는** 장치다. 도입 전의 분자는 "정답을 아는 사람이
정답으로 직행"만 계상해 판단 노동이 깊은 세션에서 과소였다(§6 한계 4번).
사람 요율이 전부 **척척 해결하는 숙련자의 속도**에 맞춰져 있어, 고민거리가
섞인 일("이걸 어떡하지"가 드는 세션)에서 분자가 실제보다 작게 나오는
문제다. 2026-08-12부터 Claude Code 트랜스크립트에 생각 토큰 수가 기록되어
이 몫을 세션 내부 실측으로 보충할 수 있게 됐다.

**도구 중간 생각은 계상하지 않는다(§59 재확인).** 전량 계상을 검토했으나
① 실행 4토막의 기계 조작분과 겹치고 ② 근거가 없어 보류했다. 미계상 크기는
`human.think.mid_tokens`로 함께 보고된다(토큰이 기록된 신 포맷만 — 구
포맷의 중간 생각 블록은 집계에도 안 잡힌다, `PENDING_CONSIDERATIONS.md` #6)
— 실측상 세션 생각 토큰의 74%가
여기 해당한다(분자 계상은 26%). 계상 시 전체 배율 영향은 +1.7%였다.

**§73 — 메인 진행 나레이션.** 마무리 답변을 뺀 메인 assistant 텍스트("먼저
확인하겠습니다", "수정했습니다")는 §68과 같은 논리로 think 요율 — 사람이 혼자
했다면 속으로 정리한 것. `detail.narration_words`.

**§68 — 서브에이전트.** 서브 기록도 같은 선별 규칙으로 훑어 서브의 전략
생각(부모 프롬프트 직후 첫 응답)을 더하고, 서브가 부모에게 낸 **보고문
전량(단어)**을 think 요율로 더한다. 위임 불변: 직접 생각(토큰×0.75×0.005)
≈ 위임(서브 생각 토큰×0.75×0.005 + 보고 단어×0.005). breakdown think 행의
`detail`에 strategy_words / fallback_words / sub_report_words로 분해.

### 3.1 근거 원리 — 왜 생각 전량이 아니라 선별인가

1. **작업자는 실무 도구 사용에 생각을 쓰지 않는다.** 분자의 사람은 "일을
   아는 사람"(숙련 가정) — 도구를 어떻게 쓸지, 다음 호출로 무엇을 볼지
   같은 조작 판단은 숙련자에게 자동화된 동작이라 계상하지 않는다. AI의
   생각은 도구 호출 사이사이마다 발생하므로 이 몫을 걸러야 한다.
2. **작업자는 답변을 어떤 형식으로 낼지에도 생각을 쓰지 않는다.** 출력
   직전 생각(무엇을 어떤 순서·형식으로 쓸지 다듬는 몫)은 숙련자가 늘
   쓰던 형식으로 처리하는 부분이라 계상하지 않는다. 1번과 같은 숙련
   가정의 출력 쪽 대칭.
3. **사람 고민은 문제를 어떻게 풀지 전략 짤 때 든다.** 과제를 받았을 때
   접근을 설계하는 순간 — "이걸 어떡하지"가 드는 지점 — 이 사람 판단
   노동의 실체다. 따라서 계상 대상은 **지시 직후 첫 응답의 생각**이다.
4. **사람의 추가 지시 없이 AI가 진행 중 스스로 방향을 튼 생각은
   미계상.** 어디까지가 새 전략 수립인지 가르는 결정론적 기준이 없어
   포함하지 않는다 — 과소 방향의 의도적 선택(§6 한계 9③).

이 원리로 "생각량이 사람 고민 시간에 비례하는가"라는 비례성 문제도
좁혀진다: 전량 비례 가정은 근거가 없지만(실측 반증 — 아래 §3.3 기각 대안), 전략
생각으로 선별하면 세션 내부 실측이 비례의 근거를 제공한다.

### 3.2 선별 방법 (결정론, LLM 0회)

```
지시      = user 메시지 − 도구 결과 회신(tool_result) − meta − 사이드체인
전략 지점 = 지시 직후 첫 assistant 메시지에 생각 흔적이 있는 경우
생각량    = usage.output_tokens_details.thinking_tokens
            (2026-08-12 Claude Code 업데이트부터 기록 — 생각 내용은
             여전히 빈 문자열이므로 §52의 "내용 측정 불가"는 그대로)
think(min) = Σ 전략 지점 생각 토큰 × 0.75(토큰→단어) × 0.005분/단어
```

- 요율 0.005분/단어 = **200wpm 상당, 분자의 정독(`human.read` 0.005)과
  같은 속도**로 둔 seed (§57). 종전 0.0025(400wpm)를 "정독의 3배"로
  불렀으나 그 3배는 검토용 정독(0.008, 125wpm) 기준이어서 분자의
  정독(0.005)과 어긋났다 — 기준을 분자 정독 하나로 통일하고 배수 표현
  대신 절대 속도로 적는다.
- **구 포맷은 건당 1.5분 고정 (§58)**: 2026-08-12 이전 기록은 생각 블록의
  존재만 남고 토큰 수가 없다. 전략 지점은 감지되므로(`fallback_points`)
  그 지점마다 **1.5분**을 계상한다 — 요율(`rates.json` think)이 바뀌어도
  건당 분은 고정이다(분을 단어로 역환산해 더하므로 breakdown 단위는
  일관).
  1.5분은 실측 **평균(796토큰 = 2.98분)이 아니라 중앙값(396토큰 =
  1.49분)** 에 맞춘 값이다. §55에서 폐기한 것은 "지점당 실측 평균
  1,454토큰"을 붙이는 방식으로, 그 단가는 생각의 양이 아니라 지시 건수를
  재는 것이 되고(계상 토큰 대 전략 지점 수 상관 0.99) 소형 세션을 실측의
  7~27배(중앙 7.2배)로 부풀렸다. 중앙값 기준 고정분은 그 왜곡이 없다 —
  토큰이 실제 기록된 16세션에 이 규칙을 적용하면 실측 대비
  **중앙 1.14배**(최소 0.28배 ~ 최대 7.41배)로, 과대·과소가 양쪽으로
  갈리고 한 방향으로 쏠리지 않는다.
  다만 **깊은 고민을 한 지점도 "보통 한 턴"으로만 인정**하므로 구 기록
  세션의 판단 노동은 여전히 과소 방향이다(보수적).
- 같은 메시지의 스트리밍 중복 기록은 메시지 id로 1회만 집계.

### 3.4 켬/끔과 한계

- `include_think=True` 기본 — 기존 소비자가 파일만 갈아끼우면 생각
  계상이 켜진 채 동작한다. 끄기: `include_think=False` / CLI `--nothink`.
- 휴먼화 2축과 독립: 4조합 모두에 동일 가산 → 항목별 ON ≤ OFF
  단조성(§43) 불변.
- 요율은 임의 seed다 — 분자 정독과 같은 0.005(200wpm)를 채택했고,
  0.0025(400wpm)·0.0016(625wpm)로 두면 보정이 각각 1/2·1/3로 줄지만
  세션 간 상대 순서는 그대로다(모든 세션에 같은 상수를 곱하는 구조).
  위 표가 세 값의 민감도다. 채택값에서 생각은 신 포맷 세션 분자의
  23.6%를 차지한다 — 실측 근거 없는 seed가 분자의 1/4를 좌우한다는
  점은 인용 시 함께 밝힐 것.
- 한계는 §6 (9번 항목): 요율 seed, reasoning effort 의존, 중간 재전략
  미계상, 구 포맷의 건당 고정 단가(§58).

## 4. 요율표 (rates.json)

절대값 주의: **P50 seed가 다수** — 실측 보정된 것은 표기함. 절대값보다
세션 간 상대 비교 용도(agent-effort/README.md 한계 절).

### 4.1 분자 — 사람 요율 (human 카드 중 이 API가 쓰는 것)

| 행동 | 단위 | 분/단위 | 출처 |
|---|---|---|---|
| read (정독) | 단어 | 0.005 | seed (§23~24에서 1/5 보정 이력) |
| skim (훑기) | 단어 | **0.00222 (=450 wpm, 정독의 2.25배 속도)** | **읽기 연구** (§8.2, §66) |
| **draft — 코드** | 단어 | **0.08** (=152 LOC/h) | **문헌 유도** (§8.3, §59) |
| **draft — 문서** | 단어 | 0.05 (=20 wpm) | 문헌 앵커 (Karat, §7.3) |
| **draft — 데이터** | 단어 | 0.01 | seed (§7.3 — 사람은 데이터를 뽑지 친다고 보지 않음) |
| edit (수정) | **변경 단어** (앵커 제외, §66) | 같은 종류 draft × **0.5** (`edit_factor`) → 문서 **0.025 (=40 wpm)** | **revision-burst 실측** (§8.4, §66) |
| search (검색) | 건 (착지-기여 문서, **검색한 지시 턴당 최소 1건** §70) | 2.0 | seed |
| **execute (실행)** | **에피소드** | **4토막 공식 (§2.4)** — 구성(0.05/단어) + 실측 대기 + 판독(0.005/0.00222) + 조작(0.25/0.1) | 실측 3 + seed 2 |
| verify (확인) | 건 | 3.0 | seed |
| think (생각) | 단어 — 전략 생각 토큰×0.75(메인+서브 §68) + 구 포맷 지점 1.5분 환산(§58) + **서브 보고문 전량**(§68) + **메인 진행 나레이션**(§73) | 0.005 (분자 정독과 동속, 200wpm) | seed (§53, §3, §57, §68, §73) |

구 요율 `human.draft` 0.05 / `human.edit` 0.025(§66) / `human.execute` 2.0은
**폴백으로만 남는다** — `human_write_model`·`human_exec_model`이 없는
요율표에서만 쓰인다.

분자 = Σ(등급별 읽은 단어 + 입력 단어)×읽기 요율 + 순계 draft/edit×**종류별**
쓰기 요율 + 검색 건수×요율 + **실행 4토막** + verify + 전략 생각×think 요율.

### 4.2 분모 — AI 기계 요율 (agent 카드)

| 행동 | 단위 | 분/단위 |
|---|---|---|
**§62부터 AI 몫은 요율이 아니라 타임스탬프 실측이다.**

```
AI 시간 = Σ(턴)  Σ(그 턴의 AI 기록 사이 간격, 단 간격 하나당 10분 상한)
```

- **깨운 입력** = tool_result가 아닌 user 레코드 — 사람 발화, 배경 작업
  알림, 시스템 주입, 중단. 그 직전까지 AI는 놀고 있었으므로 거기서 끊는다.
- **AI 기록** = assistant 응답, 또는 tool_result가 든 user 레코드.
- **간격 하나당 10분 상한 (§65)** — 그 초과분은 방치로 보고 버린다.
  관측된 도구 실행 최대가 10.0분(Bash 타임아웃)이라 그대로 담기고,
  며칠 벌어진 방치만 걸러진다. 상한 없이 재던 §62는 턴 끝 도장 없이 며칠
  벌어진 턴에서 방치를 통째로 삼켰다 — 9.1일 열린 세션의 AI 시간이 8.3일로
  잡힌 사례가 보고됐다. 불변식 `AI 시간 ≤ 세션 러닝타임`을 회귀 테스트로
  박아뒀다.
- AI가 끝낸 뒤 다음 입력까지는 **사람 시간**이라 제외. 턴 끝 도장
  (`system` 레코드)·화면 표시용 줄은 세지 않는다 — 그 뒤의 빈 시간이
  사람이 자리 비운 시간이라 통째로 섞여 들어온다(실측 354시간).
- 상한·계수·모델별 상수가 하나도 없다. 느린 환경이면 간격이 그만큼 길게
  실측될 뿐이라 **어느 PC에서도 그대로 돈다.**

요율 계산은 타임스탬프가 없는 구 기록의 **폴백**으로만 남고,
`breakdown.machine_rate_estimate`에 대조용으로 병기된다:

| 행동 | 단위 | 분/단위 |
|---|---|---|
| execute | 도구 호출 | 0.3 |
| read | 결과 단어 | 0.0005 |
| draft | 출력 단어 (§52) | 0.002 |

실측 대비 이 요율 계산은 **1.29배 과대**였고 세션별로 1.25~3.94배로
흩어졌다(중앙 2.10배). 전환 효과: 전체 4.43 → 5.00배, 세션 중앙 2.86 →
4.10배 — 세션 하나하나의 정확도가 오른 것이 본질이다.

### 4.3 분모 — 사람 감독(hitl) 요율

| 항목 | 계산 | 출처 |
|---|---|---|
| instruct (지시) | 건당 0.5분 + 단어당 0.05분 (60단어 상한 — 붙여넣기 과금 방지) | **실측 보정** (지시 1,456건, 2026-08-16) |
| review (검토) | **턴 확인 모델 (§50·§77)** — 사람은 AI 출력을 전량 정독하지 않는다. 확인 시점 = 실질 지시 턴(5단어 이상, §49 문턱과 동일) + 세션 끝. 시점마다: 대화는 결론(직전 답변)만 단어당 **0.005**(정독 200 wpm, **건별 200단어 상한 §51·§74**), 진행 보고는 단어당 **0.00222**(훑기 450 wpm) / **파일 확인 (§77)**: 그 구간에 파일 생성·수정이 있으면 유형 무관 1건 = `min(2.0, 0.5 × ln(1 + 구간 쓴 단어/100))` — 200단어 0.55분, 1,000단어 1.20분, 5,300단어+ 2.0분(상한). 구 코드 동작 확인 2.0·규모 비례 대조(코드 0.005/문서 0.0025)·파일당 표본 확인 0.5·검증 위임 강등은 §77에서 폐지 | seed (상한 2.0은 사용자 결정) |
| correct (교정) | **§77 폐지.** 종전 interrupt당 4.0분. interrupt 뒤 다시 친 지시는 instruct가 세고, instruct 요율 자체가 "직전 응답→지시 간격" 실측이라 재정향 시간을 이미 포함 — 이중 계상. 이 PC 실측 비중도 hitl의 2.7%뿐이었다. interrupts·corrective_instructions 카운트는 감사용으로 유지 | — |

**긴 도구 대기를 분모에 얹지 않는 이유 (§60 — §59에서 넣었다가 철회)**:
건당 0.3분 고정은 0.5초짜리 `git status`와 10분짜리 벤치를 같은 값으로
만든다. 그래서 §59에서 30초 초과분을 실측으로 얹었는데, **타임스탬프
실측과 대조하니 얹기 전이 더 정확했다**:

| | 모델/실측 합계 | 세션별 \|log오차\| | 허용범위(0.5~2.0배) |
|---|---:|---:|---:|
| 얹기 전 | **0.98** | **0.625** | **42/63** |
| 얹은 뒤 | 1.11 | 0.643 | 40/63 |

이유는 건당 0.3분이 **0.5초짜리 수천 건에서 과금한 몫으로 드문 장시간
호출을 이미 상쇄**하고 있었기 때문이다. 개별 호출로는 틀리지만 총합에서는
맞는 구조였다. 집계(`long_wait_min`)는 감사용으로 남기고 가산만 뺐다.

**파일 확인은 결과물 단위·로그·상한 (§77, §61·§63 대체)**: 사람은 AI가 쓴
코드를 줄줄이 읽지 않고, 만든 **수단**(엑셀을 뽑는 생성 스크립트)이 아니라
**결과물**을 본다. 종전 모델은 거꾸로였다 — 스크립트(.py)에 동작 확인 2.0 +
규모 비례 대조를 물리고, Bash로 만들어진 엑셀은 0. 그래서 확인 시점(실질
지시 턴·세션 끝)마다 그 구간에 파일 쓰기가 있으면 유형 무관 **1건**:
`min(2.0, 0.5 × ln(1 + 구간에 쓴 단어/100))`. 실측(§63, 짝 233개)이 이미
"확인 비용은 변경 규모와 거의 무관"(1~200단어 7.5분 → 4,000단어+ 3.6분)
이었으므로 선형 대신 로그, 상한 2.0분은 사용자 결정. 코드/문서/기타 요율
구분, 파일당 표본 확인, 테스트 통과에 따른 강등(`automation_saved_min`, 이제
항상 0)은 모두 폐지. 남은 한계: Bash가 만든 파일(엑셀 등)은 여전히 포착
안 됨 — Write/Edit 본문 단어만 구간 단어에 들어간다.

검토는 **누적** 기준(Edit 수정 단어 누적) — AI가 내놓는 것을 살펴보는
노동은 번복분까지 실재하므로 분자의 순계와 다른 것이 맞다(분모는 AI
경로의 추정 총비용, 분자는 직행 가정).

## 5. 부속 장치

- **의심 자백(§38)**: 미등록 도구 입력으로 글 50단어+가 나갔는데 잡힌
  산출물이 없으면 "쓰기 포맷 미등록 의심"을 결과에 자백 — 무증상 과소
  측정의 가시화.
- **전 세션 리포트**: `record_actions_code_api_all_sessions.bat/.sh/.py` —
  `~/.claude/projects` 전체를 4조합으로 측정해 마크다운 리포트 생성
  (진행 중 세션은 10분 유예로 제외). **AI 호출 세션 제외(§54)**:
  프로그램이 SDK로 돌린 세션(첫 user 레코드 `entrypoint="sdk-cli"` /
  `promptSource="sdk"` — 예: 측정기 자신의 견적 엔진 구동)은 사람의
  업무 세션이 아니므로 모집단에서 제외 — 서브에이전트 제외와 같은
  원리. 필드 없는 구 기록은 사람 세션으로 간주(보수적).
- **채널 결산 (§59)**: 세션에서 오간 글이 **어느 축으로 갔는지** 통로별로
  결산해 `channel_audit`으로 낸다. 구멍은 늘 "이 통로는 실행이니까/도구니까
  빼자"에서 났다 — 셸 명령문 속 코드(35.9만 단어)·실행 출력 판독(46.8만
  단어)·서브에이전트 전량이 그렇게 0원 처리돼 있었다. 어느 축에도 안 잡힌
  양이 2,000단어를 넘으면 `notes`에 자백한다. 현재 알려진 미계상: 이미지(스크린샷) 판독(건수만 보고)과 미등록 쓰기 도구(§38 경보). 종전 미계상이던 서브에이전트 보고문은 §68부터 think 축, 검색 결과 판독은 §73부터 읽기 축으로 옮겨져 `_CHANNEL_AXIS`에 축 이름이 붙어 있다. 어느 축에도 안 잡힌 양이 2,000단어를 넘으면 `notes`에 자백한다.

- **절감율 하한 표지 (§76)**: 분자가 바닥(agent_total × 2/3) 미만이면
  바닥으로 올리되, **출력 필드는 늘리지 않고** `notes` 한 줄로 흔적을
  남긴다 — 숫자만 보고 실측이라 오해하지 않도록. 바닥 안 걸린 세션은
  notes에 해당 줄 없음.

  ```json
  "human": {"min": 13.39},   ← 바닥 적용값 (speedup·절감율 계산에 쓰임)
  "agent": {"machine_min": 10.41, "hitl_min": 9.68, "total_min": 20.09},
  "speedup": 0.67,
  "notes": ["절감율 하한 -50% 적용 — 분자 실측 12.1분 → 바닥 13.4분 (agent 20.1분 × 0.667, §76)"]
  ```
  (실제 세션 a8138f7a 출력.) 실측 원값은 notes 문장 안 숫자(소수 1자리)로만
  남는다. **주의**: 전 세션 리포트(`record_actions_code_api_all_sessions.py`)의
  표는 `human.min`만 실어 바닥 여부를 표시하지 않는다.

## 6. 한계 (해석 주의)

1. **사람 실측 정답 0건** — 모든 절대값의 상한. 상대 비교·구간
   (휴먼화 ON~OFF) 제시가 안전하다.
2. **추정÷추정** — 분자·분모 모두 요율 기반. 요율 민감도에 결론이
   좌우될 수 있다.
3. **산출물 장황함 왜곡** — 과정 장황함(헛읽기·번복·재실행)은 휴먼화가
   걷어내 정상 벌점이지만, **살아남은 산출물**이 필요 이상 크면(사람이
   코드 한 줄로 해결할 것을 모듈로 구현) 분자가 분모보다 빨리 커져
   효율이 부풀 수 있다. 측정기는 "그 분량이 필요했는가"를 판정하지
   않는다.
4. 판단 노동 과소 — verify가 규모 무관 고정 1건. §53의 전략 생각
   계상(§3)이 상당 부분 보정하나, 실행 단계 판단(verify 몫)은 여전히
   고정 1건이다.
5. 여러 세션 파일로 이어진 작업은 기여 승격이 파일 경계를 못 넘는다(§17).
6. **발화형 교정 미감지 (§49)** — correct는 interrupt만 센다. 끊기 없이
   말로 바로잡는 교정("아니 그게 아니라…")은 결정론으로 못 갈라 지시로만
   계상 — 교정 노동 과소 방향. interrupt당 4.0분의 과대 가능성과 반대
   방향으로 공존하므로 순편향 미상 — seed 민감도 병기가 이를 커버한다.
7. 결론 승격 문턱(5단어)은 seed — 짧은 승인("좋아 커밋해") 직전의 진짜
   결론도 훑기로 강등되는 과소 방향 트레이드오프(§49). 결론 정독의
   건별 200단어 상한(§51·§74)도 seed — 분자의 실행 출력·검색 결과 "앞 200
   정독" 상수와 통일한 값. 실측 분포(결론 평균 173단어)에서 방어 장치 수준.
8. **기계 몫의 thinking 미계상 (§52)** — 내부 사고 블록은 기록에 내용이
   저장되지 않아(전수 빈 문자열) 단어×요율로 측정 불가. 파일 본문·
   서브에이전트 지시문 보충(§52) 후에도 요율 환산이 실측 가동시간보다
   약 14% 작은 잔여 격차의 주 원인 — 기계 몫은 약간 보수적(과소)이다.
   (2026-08-12 신 포맷부터 토큰 **수**는 기록되므로(§53) 분모 보충
   여지가 생겼으나 미적용 — 분자 think와 달리 분모는 전량이 대상이라
   별도 설계 필요.)
9. **서브에이전트 보고문 — §68로 해소, 잔여 한계는 생각 토큰 미기록** —
   §59~§67에는 서브가 부모에게 낸 보고문이 미계상이었다. §68부터 전량을
   think 요율(밖으로 나온 생각)로 계상하고 서브의 전략 생각도 합산한다.
   남은 한계: 이 PC 서브 기록은 생각 토큰 수가 없어(블록만) 서브 전략 지점
   전부가 §58 하한 1.5분으로 들어간다 — 서브당 상수라 세션 간 변별력 없음
   (`PENDING_CONSIDERATIONS.md` #9).
10. **이미지(스크린샷) 판독 미계상 (§59)** — 사람이 화면을 보고 판단하는
   시간이 0원. `channel_audit`에 건수만 보고된다.
11. **실행 구성 요율의 가정 (§59)** — 즉석 스크립트를 "사람도 똑같이 짠다"고
   본다. 사람은 GUI·수동 조작으로 대체할 수도, 자동화가 없어 더 칠 수도
   있다 — 이 가정은 실측으로 못 정한다. 4토막 재구성의 밴드는 하한(구성
   50wpm·조작 15초)에서 상한(구성 20wpm·조작 1분)까지 실행 몫이 1.0~2.3배.
12. **전략 생각(think)의 seed 성격 (§53·§57)** — ① 요율 0.005분/단어
   (200wpm, 분자 정독과 동속)는 사람 숙고 속도의 실측 근거가 없는
   seed — 민감도 대상. 0.0025·0.0016을 쓰면 신 포맷 세션 분자
   +30.8% → +15.4% → +9.9%로 줄지만 세션 간 상대 순서는 불변(§3.3 표).
   채택값에서 생각 몫이 신 포맷 분자의 23.6%로, seed 중 영향이 가장 크다.
   ② 생각량은 모델의 reasoning effort 설정에 의존 — 같은 과제도 설정에
   따라 토큰이 달라진다(세션 간 비교 시 설정 차이가 섞일 수 있음).
   ③ 막힌 뒤 도구 사용 중간에 다시 전략을 짜는 재전략 생각은 "지시
   직후" 선별에 안 잡힘 — 과소 방향(발화형 교정 미감지 6번과 같은 부류).
   ④ 구 포맷(2026-08-12 이전) 기록은 생각량이 없어 **건당 1.5분 고정**
   (§58, 실측 중앙값 1.49분) — 지점 수는 알고 양만 모르는 상태에 대한
   하한 대입이다. 깊게 고민한 지점도 보통 한 턴으로만 세므로 그 세션들의
   판단 노동은 여전히 과소 방향이며, 세션 간 비교 시 **생각이 많았던 구
   기록 세션이 상대적으로 손해**를 본다는 점에 주의. §55에서 폐기한
   "지점당 실측 평균 토큰" 대입과는 다르다 — 그쪽은 지시 건수를 재는
   셈이었다. 신 포맷 기록이 쌓일수록 해소되는 한계.
   **§59 재보정 검토**: AI 호출 세션(§54)을 제외한 실측 442지점의 중앙값은
   622토큰 = 2.33분, 평균 973토큰 = 3.65분이다(§58 당시 55지점 표본에는
   그 부산물이 섞여 있었다). 즉 1.5분은 실측 중앙값보다 **더 낮은 하한**
   이며, 2.33분으로 올리면 전체 배율이 +1.3%다. 하한 성격을 유지하기로
   하여 1.5분을 존치한다.

13. **절감율 하한 −50% — 인위적 바닥 (§76)** — 절감율 = 1 − agent/human 은
   위로 100%에서 막히지만 아래로는 한계가 없어(agent가 human의 3배면 −200%)
   세션별 평균이 음수 하나에 끌려간다. 분자에 바닥 **human ≥ agent_total ×
   2/3** (= agent / (1 − (−0.5)))을 깔아 절감율이 −50% 밑으로 못 내려가게
   한다. 이는 실측이 아니라 보고용 보정이므로 `notes`에 표지를 남긴다(§5
   "절감율 하한 표지" 참조). 이 PC 67세션 중 걸리는 세션 1(a8138f7a,
   −66% → −50%). 절감율 보고는 세션별 평균 대신 Σhuman·Σagent 합산 1회
   나누기를 권장(§8.7). `SAVINGS_FLOOR = None`이면 끔.

## 8. 사람 요율의 외부 연구 근거

`rates.json`의 사람 요율은 작업별 사람 실측 정답에서 직접 추정한 값이 아니라
seed가 다수다. 다만 읽기·작성·타이핑·검색은 인간 수행 연구와 대응시켜
현재 값의 규모가 현실 범위에 있는지 확인할 수 있다.

근거 수준은 다음처럼 구분한다.

- **직접 실증**: 현재 측정 단위와 상당히 유사한 인간 과제의 실측값이 존재.
- **인접 실증**: 관련 인간 수행 실측값은 있으나 현재 행동과 과제가 완전히 같지는 않음.
- **모델 가정**: 일반적인 단일 인간 속도로 환원하기 어렵고 현재 값은 seed로 봐야 함.

### 8.1 read — 200 wpm

Brysbaert의 읽기 속도 메타분석은 **190개 연구, 18,573명**을 종합해
성인의 영어 비문학 묵독 평균을 **238 wpm**, 일반적인 주요 범위를
**175~300 wpm**으로 추정한다. 현재 200 wpm은 이 범위 안이며 평균보다
약간 보수적이다. 따라서 `read = 0.005분/단어`는 외부 인간 연구로 가장
직접 방어할 수 있는 요율이다.

### 8.2 skim — 450 wpm (§66)

읽기 연구에서 skimming은 일반 묵독(≈200~300 wpm)보다 약 **2~4배 빠를 수
있지만 이해도와 정확도가 떨어지는** 행동이다[R2]. 종전 값 `read의 1/20`
(0.00025 = 4,000 wpm)은 사람 읽기 속도로는 방어가 안 되어 "비기여 텍스트의
5% 비용 등가"라는 해석에 의존해야 했다.

§66부터 `skim = 0.00222분/단어 = 450 wpm` — 정독 200 wpm의 2.25배로, 문자
그대로 "훑어 읽는 속도"로 방어 가능한 값이다. 파일 훑기(기여 파일의 비정독
블록·항해 중 열어본 후보 파일)와 실행 출력의 200단어 이후 판독에 공통 적용.
효과: 55세션 ON/ON 읽기 2,020 → 6,438분, 실행 판독 +1,223분 (배율
4.66 → 5.19배의 대부분).

### 8.3 draft — 코드 152 LOC/h · 문서 20 wpm · 데이터 가정 (§59)

#### 코드 — 문헌 두 편의 나눗셈

Prechelt의 7개 언어 80개 구현 비교는 소스 생산성 중앙값을 **22~31
non-comment LOC/시간**으로 보고한다 [R8]. 이 값은 **설계·작성·시험을 다
포함한** 전체 작업 시간 기준이다. 논문은 "시간당 줄 수는 언어와 무관"이라는
규칙(COCOMO·Capers Jones 함수점수 표가 깔고 있는 가정)이 이 데이터에서
성립함도 확인한다.

그대로 draft에 쓰면 안 된다 — 이 측정기는 **이해를 read 축, 탐색을 search
축, 숙고를 think 축이 따로 받으므로** 전체 작업 속도를 쓰기 요율에 넣으면
이중계상이다. 그래서 편집(코드를 실제로 치는 행위)이 차지하는 시간 분율로
나눈다.

Xia et al.의 현장 연구(전문 개발자 79명, 7개 프로젝트, 3,244 작업시간)는
활동을 이해·탐색·편집·기타로 나눠 측정했다 [R9]:

| 활동 | 비중 |
|---|---|
| 이해(comprehension) | ~58% |
| 탐색(navigation) | 18.4~22.5% |
| **편집(editing)** | **13.9~15.3%** |
| 기타 | 1.3~8.2% |

```
22~31 LOC/h ÷ 13.9~15.3% = 순수 편집 144~223 LOC/h
                          → 0.054~0.084 분/단어 (줄당 4.94단어 실측)
```

**보수적(느린) 끝인 0.08(=152 LOC/h)을 채택한다.**

종전 값 0.05(=243 LOC/h)는 아래 산문 작문 앵커를 코드에 그대로 쓴 것이라
코드 근거가 없었고, 검토 과정에서 한때 넣었던 0.15(=81 LOC/h)는 문헌
밴드를 두 배 벗어난 값이라 폐기했다.

#### 문서 — 20 wpm

Karat et al.의 CHI 연구는 사용자가 주어진 내용을 베껴 쓰는 transcription과
직접 내용을 만들어 쓰는 composition을 구분했다. Composition은 업무·사회적
메시지에 대한 짧은 답변을 직접 구성하는 과제였으며, 이 연구의 keyboard
composition 결과는 약 **19 corrected wpm**으로 보고됐다. 현재
`draft = 20 wpm`과 거의 일치한다.

따라서 문서 draft는 단순 키 입력 속도가 아니라 **무엇을 쓸지 생각하면서
최종 문장을 생산하는 속도**로 설명하는 것이 맞다.

#### 데이터 — 문헌 없음

JSON·YAML·CSV는 실측 구성의 24.4%를 차지한다. 사람은 20만 단어짜리 설정
파일을 손으로 치지 않고 **생성 스크립트를 짜서 뽑는다.** 0.01은 그 우회
절차의 등가 비용으로 둔 seed이며 대응 연구가 없다. 다행히 영향이 작다 —
0.002~0.05로 25배를 흔들어도 전체 배율은 5.25~5.77배 범위에 머문다.

### 8.4 edit — 40 wpm, 변경 단어 기준 (§66)

수정은 기존 문장을 읽기 → 문제 판단 → 삭제/삽입 → 다시 확인하는 과정이라
연구에서는 words/min 하나로 재지 않고 revision event 수·삭제/삽입 문자 수·
revision burst 시간으로 측정한다. keystroke-logging 자료에서 L1 작성자의
revision burst는 평균 **7.59초 동안 22.69 characters** — 5자 = 1단어 관례로
환산하면 22.69/5 ÷ 7.59 × 60 ≈ **36 wpm**(L2 자료도 ≈36 wpm). 그래서
**실제 변경된 단어 수**를 기준으로 수정 공수를 계산할 때 문헌에 가까운 값은
30~40 wpm이고, §66은 그 보수적 끝 **40 wpm = 0.025분/단어**를 쓴다
(`edit_factor 0.5` × 문서 0.05; 코드 0.04, 데이터 0.005).

종전 50 wpm(0.02)의 근거였던 Dhakal et al.[R4]의 51.56 wpm은 주어진 문장을
입력하는 text-entry 과제라 편집 과정 자체의 측정이 아니다. 오탈자·표현
다듬기 같은 가벼운 수정에는 50 wpm도 가능하지만, 의미·논리·구조를 바꾸는
substantive revision은 훨씬 느리다(proofreading만 해도 오류 유형에 따라
읽기 속도가 299 → 226 wpm으로 떨어지며, 이것은 고치기 전 검토만 잰 값).

**적용 단위가 바뀌었다**: 종전에는 Edit `new_string` 전량(위치를 잡기 위해
다시 뱉은 앵커 줄 포함 — 실측 31%)에 요율을 곱했고, §66부터는
`edit_delta`의 변경 단어(앵커 제외)에만 곱한다. "변경 단어 × 요율" 방식이라
40 wpm 근거와 단위가 맞는다. 순수 추가(old 단어를 하나도 지우지 않음)는
수정이 아니라 신규 작성으로 draft 요율.

WPM은 5 characters = 1 word 관례이므로, 공백 기준 단어 집계인 현재 구현에서
한국어·코드의 절대값을 직접 동일시하지 않는다.

### 8.5 search — 2분/기여 착지

Aula et al.의 Google 연구에서 성공한 정보검색 과제는 평균 **176.2초
(2.94분)**가 걸렸고 평균 **4.98개 query**가 사용됐다.

현재 측정기는 query 하나마다 2분을 부과하지 않고 **여러 query refinement를
거쳐 실제 기여 문서에 착지한 search episode 하나**에 2분을 부과한다.
따라서 연구의 2.94분과 정확히 같은 값은 아니지만 같은 크기이며, 단순
검색 호출당 요율보다 현재 정의와 더 잘 대응한다.

### 8.6 execute·review·verify — 인간 상수가 아니라 episode 비용

HCI의 Keystroke-Level Model에서는 숙련 사용자의 키 입력·포인팅·명령
실행 같은 저수준 조작은 대체로 초 단위로 모델링한다.

따라서 `execute = 2분/건`을 **명령을 입력하고 실행 버튼을 누르는 시간**으로
설명하면 근거가 맞지 않는다. 본 측정에서는 다음이 합쳐진 **execution
episode 비용**으로 해석한다.

```text
무엇을 실행할지 판단 → 명령 구성 → 실행 → 결과 확인
```

review도 동일하다. NASA의 software inspection 지침은 inspection별 총 투입
시간과 참여자가 개별 검토에 쓴 시간을 실제 데이터로 기록하도록 한다.
이는 리뷰 비용이 고정 인간 상수라기보다 대상과 검토 수준에 따라 달라지는
작업이라는 해석과 맞는다.

hitl 코드 검토의 턴 확인 과금(§50, §4.3)도 같은 근거 위에 있다 —
modern code review 연구(Google의 대규모 change 분석 등)는 review를
"파일 하나"가 아니라 **변경(change) 단위 활동**으로 다루므로, 기본
"돌려 확인" 비용은 사람이 실제로 멈춰서 살펴보는 **확인 시점(실질 지시
턴·세션 끝)당 1회**만 계상하고, 변경 규모는 규모 비례 확인 항으로만 반영한다.
구 파일당 고정비는 저장소의 파일 분할 방식이 hitl을 좌우하는 편향이라
폐지했다(§49에서 에피소드화 → §50에서 턴 확인으로 일반화).

따라서 `review 125 wpm`, `execute 2분`, `verify 3분`, `correct 4분`은
현재 단계에서는 **실증 인간 평균이 아니라 모델링 seed**로 유지한다.

### 8.7 외부 설명 시 권장 표기

요율의 근거를 외부에 설명할 때는 다음과 같이 구분한다.

- **문헌 직접 anchor:** read 200 wpm, 문서 draft 20 wpm
- **문헌 유도 anchor:** 코드 draft 152 LOC/h (전체 생산성 ÷ 편집 분율, §8.3)
- **문헌 인접 anchor:** skim 450 wpm(묵독의 2~4배 범위 안, §8.2), edit 40 wpm
  (revision burst 실측 환산, §8.4), search 2분/기여 착지(검색한 턴당 최소 1건)
- **실측(요율 아님):** 분자의 실행 대기 — 타임스탬프 그대로; Edit 변경 단어·
  앵커 — 단어열 diff 그대로
- **모델링 seed:** 데이터 draft 0.01, 실행 기계조작 0.25/0.1분, 앞-200 정독 상수
  (실행 출력·검색 결과·기여 파일 바닥·hitl 결론 공통), 코드 확인 0.005·문서
  확인 0.0025·표본 확인 0.5, verify 3분, correct 4분,
  think 0.005분/단어(§53·§57 — 분자 정독과 동속 200 wpm으로 두었으나
  숙고 속도의 문헌 anchor는 없음; 서브 보고·나레이션도 이 요율 §68·§73)
- 분모 검토 읽기(결론 정독·훑기)는 분자 read·skim과 **같은 값**(§71) — 요율표
  안에 같은 행위가 다른 값으로 남아 있지 않게 유지할 것
- 외부 문헌은 현재 요율이 인간 수행 범위에서 크게 이탈하지 않는지 확인하는
  anchor일 뿐, 이 측정기와 동일 과제를 사람이 수행한 ground truth는 아니다.

따라서 §6의 **"사람 실측 정답 0건" 한계는 그대로 유지**한다. 향후 동일
작업을 사람에게 직접 수행시킨 paired measurement가 확보되면 해당 실측이
외부 문헌보다 우선한다.
